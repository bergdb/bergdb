BergDB's API for Java: start a database, put values at keys, and get them back. BergDB runs inside your program and keeps its data in a directory, or in memory. This page shows the main uses with short examples, then gives the rules in full. Together with bergdb.pub.util, this package is the Pub API.

A first program

import bergdb.pub.Connection;
import bergdb.pub.Database;
import bergdb.pub.Factory;

public class Hello {
    public static void main(String[] args) {
        try (Database db = Factory.database().memory().start()) {
            Connection c = db.connection();
            c.put("/a.txt", "Hello world!");
            System.out.println(c.get("/a.txt", String.class));    // Hello world!
        }
    }
}

memory() gives a database in memory, gone when it closes; create(dir) keeps one in a directory, as the overview's program does. The try block closes the database when the block ends.

The examples below continue that program: put them in order at the end of its try block, where c is the connection and db the database. Each uses the data of the ones before it and prints what its comments say. The class Account goes beside main, and two more imports are needed: bergdb.pub.Kv and bergdb.pub.Time. The examples run as shown, so an AI assistant that writes your code can start from them as well as you.

Text and bytes

A key is a path, such as "/notes/a.txt" in the directory "/notes/". Put text, a String, at a key with the suffix ".txt", and bytes, a byte[], at a key with another suffix, such as ".bin"; a key without a suffix is for objects (next). The suffix tells a reader that does not know the type what the value is: a get as Object.class gives a String at a ".txt" key, a byte[] at a ".bin" key.

c.put("/notes/a.txt", "Hello world!");
c.put("/data/b.bin", new byte[] {1, 2, 3});
System.out.println(c.get("/notes/a.txt", String.class));         // Hello world!
System.out.println(c.get("/data/b.bin", byte[].class).length);   // 3
c.delete("/data/b.bin");
System.out.println(c.get("/data/b.bin", byte[].class));          // null

Objects

An object of a Data Object class, a public class with public fields and a public no-argument constructor, is put at a key without a suffix, and a get gives a new object of the class with the same values. The class, beside main:

public static class Account {
    public String owner;
    public long balance;

    public Account() {}

    public Account(String owner, long balance) {
        this.owner = owner;
        this.balance = balance;
    }
}

And its use:

c.put("/acc/1001", new Account("Ann", 100));
Account a = c.get("/acc/1001", Account.class);
System.out.println(a.owner + " " + a.balance);    // Ann 100

Several writes at once

A write-only transaction, w(), puts and deletes several keys at once: all of them, or none. Every put above was a transaction of its own.

c.w().put("/acc/1002", new Account("Bob", 20))
     .put("/acc/1003", new Account("Cecilia", 60))
     .execute();

Read, then write

A read-write transaction, rw(), runs an action that reads and writes through its environment, env. Here Ann pays Bob 30:

c.rw(env -> {
    Account from = env.get("/acc/1001", Account.class);
    Account to = env.get("/acc/1002", Account.class);
    from.balance -= 30;
    to.balance += 30;
    env.put("/acc/1001", from);
    env.put("/acc/1002", to);
});
System.out.println(c.get("/acc/1002", Account.class).balance);    // 50

If another transaction changes what the action has read before the action's writes are made, BergDB runs the action again; so an action should have no effect but its reads and writes through env.

Earlier states

BergDB keeps the earlier states of the database: a connection reads at its lookup time, the latest state unless you set an earlier one.

Time t = c.currentTime();
c.put("/notes/a.txt", "Hello again!");
c.setLookupTime(t);
System.out.println(c.get("/notes/a.txt", String.class));    // Hello world!
c.setLookupTime(Time.MAX);                                   // the latest state again
System.out.println(c.get("/notes/a.txt", String.class));    // Hello again!

The keys of a directory, in order

usePrimary() lists the keys of one directory in key order, with their values:

for (Kv<Account> kv : c.usePrimary(Account.class).dir("/acc/").kvs()) {
    System.out.println(kv.key() + " " + kv.value().owner + " " + kv.value().balance);
}
// /acc/1001 Ann 70
// /acc/1002 Bob 50
// /acc/1003 Cecilia 60

Indexes

A user index lists the objects of a directory in the order of their fields: here the accounts by balance, from 60 on. start() builds the index from the data there, join() waits until it is built, and the database keeps it as the data changes. If the build fails, join() throws an exception (see Good to know). An index is stored in the database: create it once.

db.indexBuilder("by-balance").dir("/acc/").type("long").field("balance").start().join();
for (Account x : c.useIndex("by-balance", Account.class).from(60, true).objects()) {
    System.out.println(x.owner + " " + x.balance);
}
// Cecilia 60
// Ann 70

Good to know

  • Close, or stop, every database that you start: nothing else stops it, not even the garbage collector. close() waits until everything is written; stop() returns at once. A transaction whose commit has begun completes; another call that runs at the stop, such as an rw() whose action runs, throws IllegalDbStateException and writes nothing ({@link Database#stop()}). Before System.exit(), and in a shutdown hook, call close(): the JVM does not wait for the background close of stop() then.
  • Each started database holds a write buffer of 10 MB of heap until it closes, whatever its size: many small databases open at once need heap accordingly ({@link DatabaseBuilder#startupDistanceInMb(int)}).
  • A transaction is written to storage soon after it returns; sync() waits until it is durable, and so does close().
  • A long key costs many times its length in the stream and in memory, as a key is stored as a path of nodes, one for each 7 bytes: keep keys short ({@link Connection}, "Keys"). A key has at most 111 bytes (Limits).
  • A Connection is for one thread: db.connection() gives each thread its own, the same object at each call in the thread, and is the one to use; db.newConnection() makes another, for a second view, such as a reader at another lookup time. A call of a connection while another thread is in a call of it throws IllegalStateException ({@link Connection}, "Threads"). An rw() action may use its environment from several threads, until it returns ({@link RwEnvironment}).
  • Earlier states are kept forever, until Database.setRetainDuration() limits them: a deleted value stays readable at the lookup times before its delete until then.
  • If the database fails, on an I/O error for example, the call throws DbFailedException, or the Error that failed it, and the application should end its process; the next start recovers the database as after a crash ({@link Database}, "Errors").
  • join() of an index's build throws {@link bergdb.pub.util.IndexBuildException} if the build failed: the index was deleted while it was building, the build met a value that it cannot index (an object written by BergDB 2026.3 or before), or it met another exception, a bug. The exception's getStatus() and getCause() say why. The database goes on, and the next start builds an index that was not deleted again. getStatus() of the job follows a build without an exception.

The rules in full

Limits

Keys, values and transactions have fixed limits, the same for every database (bergdb 024-17, section 6). A call over one throws, and writes nothing; the database goes on. A later release may raise them, never lower them.

  • A key is at most 111 bytes as stored: its UTF-8, and one byte more for each part, so each "/" counts two. About 100 characters as a rule of thumb: ASCII letters and digits are one byte each, each "/" two, letters such as å, ä and ö two bytes each (UTF-8). "/customers/12345678" is 21 bytes. A put or a delete of a longer key throws IllegalArgumentException.
  • A value is at most 8 MiB, 8,388,608 bytes as stored: a byte[]'s bytes, a String's UTF-8, an object's stored value, counted before anything is copied. A put of a larger one throws IllegalArgumentException. A larger file is put in chunks, under keys of their own, and a key that lists them written last.
  • An indexed value's levels, as an index entry holds them, are at most 111 bytes, as a key's: a string level takes its UTF-8 and a byte, a long or a double 8 bytes. A put of an object whose levels for an index of its directory are longer throws IllegalArgumentException; index such a value by a hash of it, or by a prefix as a level of its own. An index built over objects put before it gives such an object no entry.
  • A transaction (a put, a delete, a w() or an rw()) has at most 500 operations, the keys it puts or deletes, and at most 32 MiB of keys and values. An object put at a key of a directory with k indexes is up to 1 + 2k operations (the object and, for each index, the entry of its old value deleted and of its new one put): 500 objects without indexes, 166 with one. BergDB's own keys of the transaction, its index entries among them, take at most 56 KiB. A transaction over these is refused with DbException at its commit. Larger work is done in several transactions, with a key written last that readers look at first.

The API and its jar

The API is the packages bergdb.pub and bergdb.pub.util, the Pub API, BergDB's stable, default and preferred API; and the Core API, bergdb.core.Db and the classes that its Javadoc names ("The Core API"; bergdb 020-27, Q1), for low-level control and the most performance, less stable (it may change faster between releases) and less safe, and mostly the layer that the Pub API is built on. The Core's Db reaches every key, the Pub API's own too; its Javadoc, in its source java/src/bergdb/core/Db.java and not in this Javadoc, says which keys a Db may write in a database that the Pub API uses, and what a write of the others does to the Pub API's data (bergdb 020-22). Everything else, bergdb.pubimp included, is not API, whatever is public in it, and may change in any release. The jar that a release ships, which java/build.sh makes as build/bergdb-release.jar, holds the classes of BergDB's src directory only. Objects and user indexes, experimental in 2026.3, are part of the API since 2026.4.

Strings

Every string that BergDB stores is Unicode text: a sequence of Unicode scalar values, stored as well-formed UTF-8 (RFC 3629). It is a rule of BergDB's stream, the same in every language that writes or reads a database, not a detail of Java. It holds for every string: a key, a String value, each string in an object (a field's value, an array's element, at any depth, and a field's name), and an index name.

A put refuses a string that cannot be stored so, with IllegalArgumentException, before anything is written. In Java that is a String with a lone surrogate: a char of U+D800 to U+DFFF that is not part of a surrogate pair (a high surrogate followed by a low one), such as a String cut between the two chars of a pair, or "\ud800" decoded from JSON. The reason: UTF-8 cannot hold a lone surrogate, so the string read back would differ from the one put, in Java and in every other language, and BergDB does not change data silently. A call that takes a key, a get too, refuses a key with one in the same way. A put refuses also a String value whose UTF-8 takes more than 8 MiB, counted before it is made (Limits).

A reader may rely on the rule: a string in the database is well-formed UTF-8, and a string put reads back equal, in any language.

Data that is not text, such as a String that may hold a lone surrogate, is stored as data: as a byte[] value, or in an object as a byte[] or a char[] field; a char[] keeps any chars and reads back exactly. Or the application repairs such a String before the put, for example with U+FFFD in place of each lone surrogate.

Objects

A value that is neither a String nor a byte[] is an object: a put of a Data Object stores it, and a get of a class reads it into a new object of the class. BergDB stores an object in its own format, format 2 (bergdb 020-07): a set of named fields, each of one of seven types, Binson's: boolean; integer, signed, 64 bits (Java's byte, short, char, int and long are each one integer, stored in the fewest bytes); double (float and double; every NaN is one value, its payload not kept, and -0.0 is kept); string; bytes (a byte[]); array, its elements of any of the types; object. A field's name has 1 to 255 bytes in UTF-8; an object is nested at most 16 levels deep, objects and arrays counted alike, the top object level 1.

Objects written by BergDB 2026.3 and before (format 1) are not read: a get throws ObjectCreationException, a byte[] put of one in an indexed directory DataFormatException, and a build over one fails; a put over one and a delete of one work. A database whose index definitions are of 2026.3 does not start; such a database is made again from its data.

An object is put only at an object key: a key whose name, its last part, has no suffix, or the suffix ".obj". The suffix is what follows the name's last '.': "txt" for "/notes/a.txt", "h" for "/d/.h", none for "/notes/a" or "/d/x."; a '.' in a directory's name, as in "/v1.2/k", is not a suffix. A suffix is case-sensitive: "/k/x.OBJ" is not an object key, and "/k/notes.TXT" is not a key with the suffix ".txt" (bergdb 020-24-05, U5-8). A put of an object at a key with another suffix is refused with IllegalArgumentException ("Bad key"), before anything is written; a String or a byte[] may be put at any key. A get as Object.class, the primary scan and the indexes take a value as an object only at an object key. A get as Object.class gives a stored object at an object key as a DbObject, a value at a key with the suffix ".txt" as a String, and any other value as its bytes (Connection.get()).

A Data Object class is public, with a public no-argument constructor. BergDB stores its public fields that are not static and not transient, and those of its superclasses; every other instance field must be transient. A public field is not final, as a get could not set it (so an immutable class with public final fields is not a Data Object), and no field hides a field of a superclass of the same name (bergdb 020-09, V3 and V8; 020-24-05, U5-6). It is a top-level class or a static nested class: an inner class, one not static, is not a Data Object, even with a public no-argument constructor in its source, and neither is a local or an anonymous class (V1). A superclass that declares a stored field is public too (V4), and no class of the Java platform is a Data Object or its superclass, so a class that extends ArrayList, Number or Date is not one (V5); a public abstract superclass is taken (bergdb 020-24-12, U12-3). The class that declares a stored field is in a package that its module exports to BergDB, as every package on the class path is (bergdb 020-14, X3). Each stored field is of a type on a closed list: boolean, byte, short, char, int, long, float, double, their wrappers, String, byte[], arrays of these of any dimensions, and Data Object classes. Not on it: Object, interfaces, enums, records, abstract classes, the classes of the Java platform, a type variable, such as the T of a field public T value in Box<T>, whatever its bound and also in a subclass such as StringBox extends Box<String> (V9), and DbObject and the other value classes (DbValue). A class that is not a Data Object, or that reaches one through its fields' types, is refused at a put with IllegalArgumentException and at a get with ObjectCreationException, also at a key without a value; the message names the class, where it is, and why. The rules in full: bergdb 020-09.

A put is exact: each field is stored by its declared type, and a get into the same class reads it back equal. It refuses, with IllegalArgumentException and before anything is written, what cannot be stored so, naming its place from the top object, such as "inner.names[3]": a null array element (see below); a value whose class is not its field's type, such as a subclass; a reference cycle; nesting deeper than 16 levels; a string with a lone surrogate (see Strings); a stored value of more than 8 MiB (Limits; DbObject alone takes up to 2^31 - 9 bytes, the largest Java array), counted before anything is copied, the message naming the place where the count passes it (bergdb 021-23). An object or an array that the object refers to twice is stored twice, and a get makes two equal ones: a stored object holds no references (bergdb 020-09, section 4.5), so an array of a thousand references to one array of 1 MB stores 1 GB. An array put at a key is stored as an object with the field "array", a primitive's wrapper with the field "p".

A put of a large object needs heap for its copies while it runs: about 4 to 5 times the object's stored size, beside the object itself. With a heap of 4 GB, an object of 0.5 GB was stored and one of 1.05 GB was not; with 5 GB it was (bergdb 020-24-12, U12-2). put() and WBuilder.put() convert the object at the call, so an OutOfMemoryError there fails only the call; an OutOfMemoryError in an rw(), whose action converts it, or in the transaction of any of them, fails the database, as any Error there does (Database, "Errors"). Either way the application should end its process. So keep an object's stored size below a fifth of the heap that the application leaves free.

A get is best effort: a stored field is matched to the class's field of its name; a value that fits the field's type is set exactly, else the nearest value (an integer clamped, never wrapped; a text read as a number, a number written as a text), but for a double read into an integer field, and a text with a fraction: it is cut toward zero, as Java's (long) cast cuts it, then clamped, so 12.7 and "12.7" read as 12, -12.7 as -12 and NaN as 0 (bergdb 020-09, section 5.4); where no sensible conversion exists, the type's zero (0, false or null); a stored field that the class does not have is left out. A get never throws for the data. It throws ObjectCreationException for a class that is not a Data Object, for a constructor that throws (its exception the cause), and for a value that is not a stored object. To read a stored object exactly as it is, get it as a {@link DbObject}.

Among the conversions of a get (bergdb 020-09, sections 5.4 to 5.7; 020-24-05, U5-7): a char is stored as an integer, its code, so a char read into a String gives its number, "65" for 'A', and a text read into a char is read as a number, "66" as 'B' and "B" as 0; a boolean reads into a number as 1 or 0, and into a String as "true" or "false"; a number reads into a boolean as true if it is not 0 (NaN as false), and a text only if it is "true", in any case; bytes read into a String are decoded as UTF-8, each ill-formed part as U+FFFD, and a String read into a byte[] gives its UTF-8 bytes; a scalar read into an array other than a byte[], or an array or an object into a scalar, gives the type's zero.

A text read into a number (bergdb 020-09, section 5.5; 020-24-12, U12-5) is read by Java's grammar, not a portable one. Into an integer field or a char: the text is trimmed of the chars up to U+0020 at both ends; an optional sign and ASCII digits give the number exactly, clamped; else, if Double.parseDouble() reads it, the double, cut toward zero and clamped; else 0. Into a double, Double.parseDouble() of the text, and into a float, Float.parseFloat(); else 0. So "042", "4.2e1", "42d", "42f" and "\t42\n" read as 42, "0x1p4", a hexadecimal number with a binary exponent, as 16, "Infinity" as the type's greatest and "1e3" into a byte as 127; and "", "0x2A", "42L", "4_2", "1,5", "inf", "nan", a text with a no-break space and one with digits of another script, such as Arabic-Indic, read as 0. A text read into a boolean is not trimmed: " true" reads as false.

A float is stored as a double, its value exactly, (double) f (bergdb 020-09, section 4.2; 020-24-12, U12-6): 0.1f is stored as 0.10000000149011612. So an index of type "double" on a float field finds it by eq(0.1f), not by eq(0.1); a float field read into a String gives the double's text, "0.10000000149011612", not Float.toString()'s "0.1"; an element of a float[] takes 9 bytes, as a double's. A double read into a float field is Java's (float) cast, the nearest float: beyond the float's range it is an infinity, so 1e300 reads as Infinity, not as Float.MAX_VALUE, and 1e-300 as 0.0.

Bytes count as a scalar here (bergdb 020-09, sections 5.4 and 5.7; 020-24-12, U12-8): a stored byte[] read into an array field other than a byte[], such as an int[], a Byte[] or a String[], gives null. The other way, a stored array read into a byte[] field is converted element by element, each as into a byte, clamped: an int[] of {1, -1, 300, 70000} reads as {1, -1, 127, 127}, a char[] {'A', '\uD800'} as {65, 127}. So a field changed from byte[] to int[] reads null, and a read-modify-write of an object written before then drops it.

A get and a put of the object back, the usual read-modify-write, store what the object holds, no more: a stored field that the class does not have is not in the object, so the put drops it, and a value that the get converted is stored as converted, such as a long clamped into an int field. So after a change of a class, a field renamed or removed or its type narrowed, a read-modify-write of an object written before loses what the class does not keep, and the object leaves the user indexes of the fields it lost (bergdb 020-24-02, I-4).

A get may give an array with null elements, which a put refuses: an element that has no sensible conversion gets its type's zero, null for an object, a String or an array, as a stored String in a Tag[] field or a stored object in a String[] field. So an object that a get of another version of its class made, the usual case after a change of a class, can be put back only after its null elements are set (bergdb 020-09, section 5.7; 020-24-05, U5-3).

Null and absent fields

BergDB stores no null. An object is a set of named fields, and a field that is there holds a value of its type: a string, an array, a nested object, never null. A field that has no value is absent. It is a rule of BergDB's object format, the same in every language that writes or reads a database, not a detail of Java.

A put leaves a null field of the object out, at any depth: the field is absent. A null Integer, or another wrapper, is absent too. A get of an absent field leaves the field as the class's no-argument constructor set it: a field without an initial value reads back as null, one with an initial value as that value. A get meets absence also in an object written before its class had the field, or written in another language.

A put refuses a null element of an array, at any depth, such as an element of new String[3] not set (an array has no absent elements), and a null value at a key, with IllegalArgumentException, naming its place. An application that needs "no value" apart from "not written" stores it explicitly, as a field of its own; an array with gaps stores a placeholder.

A user index gives an object no entry for a field that is absent.

Encryption

Release 2026.4 has no encryption. The releases up to 2026.3 could encrypt a database's stream with a crypto key (DatabaseBuilder.cryptoKey()), and that encryption is removed: it gave every write at one position of the stream the same keystream, in two databases with one key, in a copy written on beside the database, and after a crash cut the stream's tail, so one who saw both versions of the files could learn the data; and it did not keep the data from being changed (bergdb 020-24-07). To keep the data secret on disk, use full-disk encryption, such as FileVault on macOS, LUKS on Linux or BitLocker on Windows, or encrypt the values in the application before it puts them. start() refuses a database that an earlier release encrypted, and writes nothing; the release notes of 2026.4 say how to move its data.

The package's dependencies

Depends on: common, nanotest, pub.util, pubimp. Only test code (the @Nano methods) uses nanotest. Factory uses pubimp to create a DatabaseBuilder: the circular package dependency pub -> pubimp -> pub is by design. Time also uses pubimp's TimeResolver, and DbObject and its value classes pubimp's ObjectFormat (the codec of the stored object format) and DataObjects (the conversion of Data Objects; bergdb 020-10, step B3).
