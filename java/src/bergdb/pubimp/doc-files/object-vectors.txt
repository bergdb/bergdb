# second implementation written from the spec alone (check.py, same directory). The format
# of this file: 020-07, section 13. A draft, with 020-07, for Frans's approval under
# 018-01's rule (020-02, section 4.12).
#
# A record starts with a line "KIND ID"; its attributes follow, one per line, each line
# starting with two spaces: "  KEY REST". A blank line ends a record. A line starting with
# '#' is a comment.
#
#   valid ID       bytes HEX     a stored value; a reader accepts it, a writer writes it
#                  value VN      what it means
#                  binson HEX    the same object in Binson (BINSON-SPEC-1.1)
#                  lookup PATH RESULT   any number: a field's value by its path, or absent
#                  note TEXT     optional
#   invalid ID     bytes HEX     a byte string that is not a stored value; a reader refuses it
#                  rules CODES   the conditions it breaks, comma-separated
#                  note TEXT     optional
#   generated ID   recipe TEXT   how to make the bytes; length N; sha256 HEX of the bytes;
#                  then "valid", or "rules CODES"
#   binson-in ID   binson HEX    a Binson object; then "bytes HEX", the stored value it
#                  converts to, or "rules CODES", why it does not convert
#
# HEX:  pairs of hex digits; "(HH..*N)" is the bytes HH.. repeated N times. Spaces none.
# VN:   {NAME:VALUE,...}  [VALUE,...]  true  false  iDECIMAL  dHHHHHHHHHHHHHHHH (the 64-bit
#       pattern of a double, most significant digit first)  sTEXT (a string)  bTEXT (bytes);
#       NAME and TEXT are "..." (printable ASCII; \" \\ and \xHH for any byte) or <HEX>.
#       No spaces outside "...". The members of an object are listed in the stored order.
# PATH: NAME.NAME... from the top object. RESULT: a VN value, or absent.
