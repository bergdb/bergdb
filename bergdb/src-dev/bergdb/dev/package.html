BergDB developers: read this first; this package should contain the documentation you should need to modify BergDB for your needs. If you just want to use the BergDB library, look elsewhere.

This package is not needed for production use and may be omitted from the final build.

Depends on: bergdb.* (any bergdb package)

General assumptions

The database performance is optimized for a modern 64-bit server. Typically 4 to 16 cores. 1 to 2 CPUs. SSD or ordinary disk(s). But the database also has good performance on very small devices. There is only one code based; no differentiation between large server and small devices (Android phone for example).

There is only *one* DB stream format for all supported devices, operating systems and programming languages.

Logically, the database uses a single append-only stream (interface stream.AppendOnlyStream).

Serial writes. While many transactions (both read and write) may run in parallel, write transactions are serialized for storage.

Anti-assumption: We DO NOT assume the system is running on a 64-bit server with atomic operations on "long" and "double".

Developement

GENERAL
* Use Java 1.5.
* Generics is allowed.
* Annotations are only allowed for non-production code (test code).

CODE STYLE
* Follow Sun's (Oracle's) Java code style unless otherwise
    specified here. Deviations that are useful and deliberate are allowed.
* Use 100 column max line width (same as Android project) instead of 80.
* Treat acronyms as words. Eg.: getId(), getHtml(), setUrl() (same as Android).
* Android has a good code style almost identical to Sun's original at
    http://source.android.com/source/code-style.html
* Use "public" in front of interface methods.
* Do not use "throws..." for runtime exceptions, document with @throws instead.
    (This follows JDK approach, see Integer.parseInt() as example.)

JAVADOC
* Use Javadoc. Class comments, method comments. Use few tags: @param, @return, @throws, @author, @deprecated
* Use Javadoc "@author firstName lastName" for top-level classes/interfaces.
* ALL classes/interfaces of the Pub API must be have Javadoc comments. Most methods too.
* ALL packages/classes/interfaces should have Javadoc comments.
* See Oracle's: "How to Write Doc Comments for the Javadoc Tool".
  http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html

TESTING. Use Nanotest (com.bergdb.nanotest). Use it for unit tests (nanotest group unit) and functional tests (f) A major reason for using Nanotest is to be able to self-test easily (even when compiled with GCJ, IKVM, ..). Nanotest is very simple and small compared to JUnit and it allows test methods directly in the classes to be tested. I like when the test follows the testee with moves/renaming/deletion. A "unit" test should run within 0.1 s, an "f" test should run within 10 s. The difference between "unit" tests and "f" tests is not strictly functional, but mainly about execution time. Both of the test types, test that the code is working properly.

    Test type   Max time    Run with    Comments
    
    unit          0.1 s     Unit        Fast tests, typically unit tests. Run before every commit.
    f            10.0 s     F           Slower tests. Run every dev day.
    night      1000.0 s     Night       Long-running test, often needs filesystem. Run over night.
    
    Above test are automatic tests. Additionally, the package bergdb.test.manual contains manual
    tests. Tests that require human interaction or manual inspection of the result.
    bergdb.dev.props.CORE is the standard way of measuring Core Performance.

Code markers. Use NOTE in addition to TODO and XXX. NOTE is used for something we may want to modify at in the future. Possible improvements, considerations. NOTEs can be kept in the code indefinitely, while XXX are temporary and should be gone before each commit. Most TODOs should be gone before a release. Use backlog for future tasks.

Access rules. "protected" keyword is not allowed and package access is seldom used. This is to keep things simple. We need more advanced access rules anyway; they cannot be enforced by the Java compiler. Instead, allowed access is determined by the specified allowed package dependencies.

package.html. Use Javadoc package.html files to document the Java packages. Each package should specify its allowed package dependencies with a statement like: Depends on: list-of-packages. bergdb/jdepend.sh is used to verify that these rules are followed.

Global stuff / static. Do not use JVM global stuff (non-final "static" fields). It should be possible to run multiple BergDB instances in one JVM. Easy testing, limited dependencies. BergDB should run well in the same JVM together with other software. So no global state is set by BergDB (for example: default exception handler, logging).

Logging. Do not use java.logging. This is global stuff, and its benefits does not outweigh the added complexity, especially when BergDB is used in-JVM with other applications and other BergDB instances.

Input/output

With few exceptions, input and output is data read from / written to the database.

System.out is never used. System.err is never used. System.in is never used.

Build

The source is built with vastly different targets in mind. It is build to a Java jar with Java byte code, of course. Also it is build to native machine code and to .NET (IL).

Java JAR

The source is built to one jar: "bergdb.jar".

Android

The database runs on Android without modifications.

IKVM

Works well, no problems at all. See build/ikvm.

Versions and releases

Version. Version "2014.1" is used as the first BergDB release in 2014. 2014.2, 2014.3, 2015.1, 2015.2 are used for the following public releases (assuming 3 releases in 2013). There must be no more than 9 releases during one year. The version int is 141, 142, 143, 151, 152 for the above example releases. The version int makes it simple to compare versions. It should be used internally only. The version ID and the version int are available from the class db.BuildInfo. The year (2013, 2014) is the major version number, and the second number if the minor version number.

New methods and features can be marked with "since" in Javadoc, example: "@since 2013.2".

A BergDB software release is one single zip file made available from bergdb.com.

Build. Builds are used internally by BergDB developers. Build IDs has HHMM added to the build ID. Examples: "2013.1.130401.1330", "2013.2.130630.1500".

Documentation

All documentation needed to use and modify BergDB should be included in the Javadoc files (possibly by including files in doc-files/ directories). HTML and TXT files are allowed. JPEG/PNG images are also allowed.

Known issues/limitations

-- Key replace --

1. If we have code: Connection.store("/d/${transactionTime}/d2/myObject.obj", obj); 
We cannot check if directory is indexed. In theory the directory d/${transactionTime} could 
replace into an existing indexed directory.

Possible solution: We could disallow key replacement except in the last part of the key.

2. Consider: If there would be an indexed object with key "/d/1230.obj" and an KV 
with replace key "/d/${transactionTime}.obj" evaluates to the same key -> we have a problem!
The old index entries are then not removed!

Possible solution: Throw an exception if such a key already exists. Inform user that it is not
allowed to have a *.obj key with replacements to replace an existing KV. 
This may require a new setIfNotExisting (insert) feature in DB. We could disallow it only 
for indexed directories.
