## 1. Conclusions and recommended direction

Direct Java references between resident nodes are compatible with eviction.
There is no identified fundamental conflict between those requirements.
The proposed BergDB implementation remains conditional on resolving the
design gates below; it is not yet a complete, proved algorithm. The
necessary bookkeeping belongs at node loading, pointer creation and
replacement, transaction boundaries, and eviction. Resident reader
traversal should keep its existing path.

Use an incremental sweep of resident objects' outgoing memory pointers,
with complete reference and lifetime accounting. A shared child becomes
releasable after its last persistent incoming memory reference disappears
and its pins have been released, provided required version information is
also preserved. Start with stored immutable value nodes, then add clean
index nodes. Add incoming-reference lists only if measured
sweep cost warrants their memory and maintenance overhead.

Two Level 3 properties that look settled are not, and the plan treats them as
gates. **Level 3 assumes that a memory pointer stays a memory pointer**: all
its pointer-race repairs and tests cover the one-way change stream to memory
(reader swizzling). Eviction adds the reverse change and breaks the
assumption in code that is correct today; see section 4.5.1. **Reclaim reads
the whole database** in every iteration (every index node and every live
value), which is free when everything is resident and not when it is not;
see section 5.1.

The first go/no-go gate is **version authority independent of residency**:
prove how a writer obtains the right version and serialized reference after
canonical bodies and snapshots are unloaded. A sweep and balanced counts
do not establish this. Settle that gate, coherent pointer publication, and
bounded retirement before committing to the full cache implementation.

Use Lean to develop a separate cache representation over the existing
self-indexed-stream model. Prove lookup correctness and preservation under
cache operations, then prove that subsequent transactions and abstract
stream records are independent of cache residency. Reclaim and concurrent
readers require additional lifetime properties.

Level 3 now supports concurrent readers with the accepted expiry contract:
an admitted operation can expire if a cut overtakes its actual snapshot.
A read below the cut does not poison the stream or storage manager. Retention
changes, exact cuts, restarts and crashes have regression coverage. The
public `Kv.time()` and `Connection.time()` methods are removed; transaction
times remain, while internal entry times remain inexact.

Retention pacing, current-row storage, the older cut point, index-aware
budgeting and a 16 KB scan target remain implemented. The final KV can
exceed that scan target. Record-byte counters and measured commit tails
are available, but neither the 200-index-node measurement target nor the
scan target is a worst-case latency guarantee. Correct eviction does not,
by itself, bound dirty memory or establish hardware power-loss durability.

The larger W4 grid and latency figures in `levels.md` describe their
recorded implementation versions. Establish a fresh matched performance
baseline through the new Level 3 plan and use it in step 0; do not assume the
new copying locks have no cost merely because resident traversal is unchanged.

The first implementation should preserve the current format layout and
writeout scheduling where the proof gates permit it. A cache hit should
not add a node-ID lookup, a reference count update, or an extra handle
dereference to resident reader traversal.

### 2.1 Checks performed in this self-review

Compiled the current Java source with OpenJDK 27 and `--release 8` into a
disposable directory. A small harness used the production `NodeCollection`,
`Cache3` and `StoredTopNode` paths, with a test `NodeStream` serving known
node versions. It produced:

```text
Runtime reload: stored size=4, loaded size=2; entries after startup time discarded.
Writer resolution: preferred newer snapshot present=200, absent=100; serialized edge depends on table contents.
```

The first case loads a key-node version with entries at times 10 and 20,
through a stream reference at position 200, with remembered startup time
15. The four klongs become two. A runtime reload must preserve the later
entries when those entries belong to the required state.

The second case gives a canonical dirty parent a snapshot child at position
100. Registering a newer snapshot of that same node at 200 makes
`resolvePointers` and actual top-node serialization emit 200; without the
table entry they emit 100. These are component-level states, not a proved
reachable full-database trace. The model must either show why the relevant
writer invariants exclude such a difference, or make resolution independent
of discretionary cache entries. This behaviour cannot be assumed away.

The pointer-publication concern was subsequently reproduced by Level 3
reader stress and repaired for serialization without eviction. The independent
review also reproduced an incoherent key-node copy during a one-way reader
swizzle and repaired copying, array growth and top-node inheritance. See
[levels.md](levels.md), "Independent review, 13 October". The memory-pointer
fast path still assumes that a memory pointer stays one, which eviction breaks. Section 4.5
is therefore still a design gate. The remaining cache proposals and memory
bounds have not been experimentally validated.

## 3. The contract to establish

For the same transactions, transaction times, retention settings and
writeout policy, arbitrary supported cache schedules must preserve:

* Correct latest and historical gets, ordered searches and scans at the
  actual finite snapshot selected at admission. A successful operation must
  match that snapshot. With reclaim, an operation may expire when that
  snapshot falls behind the frontier; differing cache schedules need not
  produce the same success/expiry outcome for an already expired snapshot.
  An available snapshot must not fail merely because its data was evicted.
* Complete state for subsequent writes, correct node IDs and one current
  mutable canonical object per node ID.
* The dirty/writeout bookkeeping and the bytes appended to the stream.
  Cache activity alone must not append transactions or alter reclaim's
  logical decisions. All comparison runs must have the same externally
  supplied transactions and times, including the same logical read/scan
  trace; cold/warm outcomes may differ.
* Restart and crash recovery after eviction, including recovery after
  a reclaim cut.

Physical object identity may change across unloading and reloading. Tests
should require shared references to agree on the current canonical object
when resident, rather than require the same Java object to survive eviction.

The resource contract must separately specify the managed resident-memory
target, pinned memory, temporary operation memory and storage buffers.
The existing `cacheSizeIndicator` is a suitable starting API for a soft
target. It is not a promise about total JVM heap use or bytes retained by
application callers.

The byte-equality goal applies to cache variants of the corrected writer.
If a common reference-resolution repair changes records relative to an
older binary, document that change and its compatibility consequences.
Preserving the current format layout is an initial design preference, not
permission to keep a cache-dependent writer or an assumption already proved.

Keep Frans's Level 3 decisions: admitted reads may expire, no exact value
write time is exposed, and f stays 0.25. Full-operation retention protection
would be an additional API/performance choice, not a prerequisite silently
implied by the word eviction. Do not add value timestamps or alter the
stream format as part of cache work without a separate reason and decision.

## 4. Cache representation and eviction algorithm

### 4.1 Track objects and logical nodes separately

Maintain a resident-object registry keyed by Java object identity. Each
entry records the node ID, representation/version role, estimated bytes,
incoming structural reference count, explicit root pins and retirement
state. Keep the preferred node-ID table as a separate index into this
registry, with a separately defined role for version authority. Releasing
a physical object does not automatically permit forgetting its node's
latest required position. Older snapshots or pinned parents can still
depend on that information for canonicalization and serialization.

A possible representation keeps a lightweight version entry after releasing
the body, while explicit resident/writeout dependencies need it. Prove its
expiry condition and its bound in terms of resident dependencies, pinned
state and actual startup-section metadata. A directory of every node ever
seen is not an acceptable substitute. Retaining a merely "latest known"
position is not sufficient unless the invariants show that it is the
version the writer requires. Select this representation after the first
proof gate, not by extending the current cache entry blindly.

The registry covers canonical objects and cached snapshots. Operation-only
loads that bypass caching have a temporary lifetime and must not be added
to a permanent registry. They still participate in stream-read lifetime
protection. Do not permanently swizzle a cached child into an unregistered
temporary parent: its eventual disappearance would bypass ownership
accounting. Use the child as an operation-local result, or explicitly make
the parent resident before publishing and counting that edge. Apply the
same rule to parents already being retired.

Count edges from every registered parent, including copied edges in time
and space splits and top-node skip pointers. Separately pin the current
super root, dirty/writeout state, transaction work lists, and loads being
prepared for publication. Do not treat the table's own strong reference
as a reason to retain an otherwise releasable cache entry forever.

All pointer changes need one ownership protocol: remove the old edge,
install the new representation, and account for the new edge. Preserve
the existing direct array access on reads; centralize accounting on the
paths that mutate the graph. Startup can register its completed graph in
one pass before readers are admitted, rather than maintain counts during
every intermediate reconstruction step.

Debug audits must also detect strong references left in unused array slots
or reusable copy buffers. Logical `getSize()` alone need not describe all
Java reachability. Obsolete arrays still held by readers belong to temporary
lifetime accounting; clearing unused slots must respect publication and
active-reader rules.

Use the graph's acyclic forward structure for reference accounting. An
incoming-reference-list variant adds backward metadata links, which must
be explicitly removed when a parent retires; otherwise that metadata can
retain the objects it was intended to release.

### 4.2 Distinguish eligibility from selection

Eligibility is a correctness condition. Coldness only chooses among
eligible targets.

A stored value is eligible when its record is complete and readable,
its required backing bytes are retained, and transaction/publication pins
have ended. `ValueNode.isDirty()` is always false, including before its
first write, so that flag alone cannot establish eligibility.

A canonical index object is eligible when it is outside the pinned dirty
and writeout state, and a retained stored version reconstructs all state
needed by permitted reads and future writes. A historical snapshot must
have a backing version correct for the contexts in which its parents can
use it; it must not be promoted for writing merely because it answers one
historical read correctly.

The parent need not be clean to detach a clean child. Requiring that would
allow a dirty ancestor to retain arbitrarily much clean data. Dirty target
objects remain pinned; cache hints cannot override this requirement.

For each detached edge, use either:

* A retained, complete stream reference suitable for the edge's permitted
  lookup times; or
* A proof that the edge is outside every still-available snapshot, with
  removal subject to the object lifetime protocol. An older in-flight
  operation may abort under the expiry contract. If protected mode is
  added, its still-valid tickets must also be respected.

The second case matters after reclaim. Simply refusing to unload every
object whose old position is below the cut would retain obsolete history
forever. An expired slot may keep an inert numeric historical position,
as current serialized histories do, provided an available snapshot cannot
follow it and an expired traversal reports expiry rather than using deleted bytes.
Do not erase logical entries or top-node routing links based only on age.
Prove the expiry condition for the traversal algorithm. The existing
`KeyNode.getMaxValidTime()` is a candidate building block, not a proof of
the complete condition for every kind of parent.

### 4.3 Incremental outgoing-pointer sweep

Run the sweep in bounded batches over all registered resident parent
objects. It must cover older physical snapshots as well as preferred
table objects.

For the initial implementation, perform eligibility decisions and detachment
under writer exclusion at a stable transaction boundary, together with the
slot's pointer lock and the prescribed metadata protocol. Recheck the
actual target, backing version, pins and role before replacing the
reference and decrementing that exact object's incoming count. The pointer
lock alone does not protect target dirtiness or transaction membership.
In particular, `Db.store` clears dirty flags before appending the record;
that intermediate state must not make an object evictable.

Allocation/registration callbacks should account and signal pressure, not
start a sweep reentrantly in a half-built transaction. Initially exclude
sweeping during recovery/replay as well; account its peak and perform an
initial sweep after reconstruction is complete. Releasing dirty targets
is never a response to startup or transaction pressure.

Detachment must not change logical dirtiness or append stream data.

When an eligible object's incoming count and root pins reach zero and it
is chosen for release, begin retirement.
After the lifetime condition in section 6 is satisfied, release its
outgoing ownership counts and remove its resident entry. Remove or replace
a preferred body reference only if it still names that exact object, and
keep any required lightweight version authority until its separate expiry
condition holds. Outgoing releases can make more clean objects releasable;
process this cascade in bounded batches as well.

Counts change on graph mutation, not on every pointer follow. The sweep
cost is proportional to examined resident pointer slots. A shared victim
may require a full sweep before its last edge disappears. This is an
explicit initial tradeoff; measure examined slots per released byte.

Bounded slot counts do not establish bounded latency: a slot lock may be
held by a cold load doing I/O in the current follower. Measure this wait,
and consider read/recheck publication with I/O outside the slot lock as a
separate cold-path improvement. Do not label a batch nonblocking merely
because it examines few slots.

Use the existing access-data representation for an initial age policy,
with a clock that advances during cache allocation/loading in read-only
workloads as well as writes. Do not call the system clock at every node
hop. Under pressure, a fair complete sweep must also be able to detach
eligible references despite recent access; otherwise a working set larger
than the budget can prevent progress indefinitely.

If scans are expensive, add incoming slot lists to locate a victim's
references directly. They cost storage per resident edge and maintenance
at splits and replacements, but need no additional resident-reader work.
This is a measured alternative, not a prerequisite for the first version.

The principle follows the original
2012 eviction note.
The old [Cache2.java](../java/src/bergdb/core/Cache2.java) implements
an outgoing-pointer sweep; its eligibility and synchronization rules are
not a validated substitute for the new design.

### 4.4 Loading and writer correctness

Split recovery-time reconstruction from ordinary runtime loading.
Recovery may cut a version back before replay. A runtime reload must keep
the state appropriate to its pointer and operation; it must not blindly
cut everything back to the process's original startup time.

Use an explicit reconstruction/runtime phase distinction. Merely checking
whether a position exceeds the startup-section start, or even lies in the
original section, does not determine whether a runtime object should be
cut. A version originally written in that section may be reloaded after
replay has finished and need its full history.

Preserve Rule R and the distinction between historical snapshots and
canonical writer objects. Before promoting a cold object for a write,
establish that it has the complete required history and current state.
Cache absence must never mean that any older version is safe to promote.

Evaluate explicit representation options at this gate: separately maintained
reload/serialization references alongside the direct Java reference;
lightweight version authority retained while resident or writeout
dependencies need it; or a deterministic reference-normalization rule
derived from logical state. The first option may require changing the
overloaded access-data field or adding bounded slot metadata; it need not
add a handle on resident reads. Compare costs and prove the selected
option's update/expiry rules. None is established merely by naming it.

Unswizzling a memory edge should preserve the stream reference it would
contribute to serialization. Also prove that writer resolution remains
correct when some parents themselves are cold and must be reloaded from
older serialized versions. This is where the open Level 2 lemma about
latest child references, and lemma M about newer versions, become useful.
Unswept disk parents cannot be repaired by a RAM sweep.

Avoid a permanent latest-position directory for every database node: it
would itself grow with the database. Use valid concrete edge references,
the pinned dirty state and bounded reconciliation metadata. Demonstrating
that these suffice for current writes and historical reads is a design
gate. The reference chosen for a record must be determined by logical
write/reclaim state, not by which historical reads happened to leave newer
snapshots resident. If the existing invariants do not establish that,
design deterministic reference normalization or bounded version-authority
metadata before index eviction. Avoid a whole-stream search for a latest
version on an ordinary miss; that would defeat the lookup-cost requirement.

Revisit expired edges specifically. Today the resolver skips a numeric
position below the physical cut before it can obtain a node ID, but a
memory pointer can still supply that ID and find a newer object. Detaching
an expired memory edge can therefore remove information the writer used.
Prove cache-independent serialization of such slots, including a cold
parent reloaded from disk. An edge unneeded by queries can still affect
writeout; the expiry test in section 4.2 alone is insufficient for record
equality.

### 4.5 Coherent pointer publication and consumption

The pointer is a two-field representation. Both fields must be read from
one coherent state whenever their combination determines a stream address.
The following was reproduced and repaired in Level 3; it describes the
old serializer/copy race, not an unfixed current serializer:

```text
Serializer captures node = null from a stream pointer.
Reader installs a non-null node and then negative access data.
Serializer captures that negative numeric field.
Its captured node is null, so it treats the access data as a stream address.
```

The baseline now synchronizes `setPointer` on the parent node, takes a
coherent cold `getPointer` snapshot, protects `KeyNode.ensureCapacity` and
`lastVersionGivenDel` with that monitor, and uses `getPointer` for top-node
skip inheritance and serialization. These are common Level 3 repairs to
preserve, not new eviction machinery.

Before adding unswizzling, remove the assumption that an observed memory
slot remains a memory slot. In particular, `TopNode.getPointer` rereads its
reference on the memory fast path. A concurrent eviction could clear it
between the test and capture. Specify coherent pair consumers independently
of the direct-reference hot traversal: writer serialization and copying
can take locks without adding a lock or ID lookup to every resident read.

Writer exclusion prevents an evictor from racing a writer in the proposed
initial sweep, but it does not prevent reader-driven swizzling. Audit
[StoredKeyNode.java](../java/src/bergdb/core/StoredKeyNode.java),
[StoredTopNode.java](../java/src/bergdb/core/StoredTopNode.java),
split copying, skip-pointer inheritance, and every other consumer that
interprets both fields. Use the same slot lock for coherent snapshots, or
a separately proved publication/read protocol. Capture positions at the
appropriate point in same-record position assignment. Individual volatile
fields do not make the pair one atomic state.

This is a Java publication/refinement obligation as well as an abstract
algorithm obligation. Model the protected operation as atomic only after
its Java implementation has the required synchronization. The relevant
rules are in the [Java memory model](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.4.5).

### 4.5.1 The retired assumption: a memory pointer stays a memory pointer

Level 3 deliberately relies on this rule, and says so in the source
(`KeyNode.getPointer`: "Level 4 (eviction) must revisit this";
`TopNode.getPointer`: "A memory pointer stays one (no eviction yet)").
Every Level 3 pointer repair, and every regression for it
(`ReclaimReaderTester.testPointerPairIsCoherent`,
`testCopiesAreCoherentDuringReaderSwizzling`), covers **one-way** traffic:
a slot goes from stream position to memory reference and never back. The
fast paths take no lock for a slot that already holds a memory reference.
Level 4 makes the traffic **two-way** (memory to stream by eviction, stream
to memory by loading), so a slot observed as a memory pointer may stop being
one before the observer finishes. Do not reuse the Level 3 arguments as
they stand. Known consequences, to be handled in step 2 and checked in step 3:

* **Double read of the reference.** `TopNode.getPointer` tests the reference
  and then rereads it on its lock-free path; eviction between the two reads
  yields `node = null` with the access-data field. `KeyNode.getPointer`
  reads the reference once but then reads `pos[index]` separately, so it can
  pair a memory reference with a stream position. Either pair is
  incoherent. Every consumer must capture the reference once into a local
  and decide on that local only.
* **Lost update of the stream position.** `setPointerAccessData` writes the
  numeric field without synchronization and, in `TopNode`, asserts that the
  reference is non-null. A reader that saw a memory pointer can write
  access data after the evictor has stored the stream position in the same
  field, destroying the only saved address of the child. This is a
  silent-corruption path with no analogue in Level 3. Access data must be
  updated under the slot lock with a re-check, or kept outside the field that
  holds the position (the access clock then needs its own representation;
  decide this with section 5).
* **Detached targets.** A reader holding a reference to an evicted node
  still sees a valid Java object, but it is no longer the canonical one; a
  writer that reloads the child makes a second copy. Whether that reader's
  result is still correct is the retirement question of section 6, not
  something the pointer protocol settles.
* **Assertions and fast paths.** Replace `assert pointers[i] != null`
  style preconditions in access-data and getter code with defined behaviour
  for an evicted slot, rather than relying on them being absent without `-ea`.
* **Other pair consumers.** Re-audit the consumers already listed above
  (`StoredKeyNode`, `StoredTopNode`, splitting, copying, skip-pointer
  inheritance, `ensureCapacity`) under two-way traffic. Level 3 made them
  coherent against swizzling only. Keep `getPointer`/`setPointer` as the
  only accessors, so that the audit is a search for direct field reads.

Required tests, before any automatic eviction: extend both Level 3 pointer
regressions so that the slot alternates between memory and stream states
while readers, the serializer, copying and array growth run (the Level 3
tests alternate only one way); add a test in which a reader's access-data
update races an unswizzle and the saved stream position must survive; run
`ReclaimReaders` with forced eviction of random slots at every eligible
boundary. Model the slot as an explicit state machine (stream, memory,
evicting, loading) in the Lean cache model rather than as a field pair.

## 5. Capacity, admission and maintenance work

Estimate resident bytes for objects, arrays, payloads, the registry,
preferred indexes and retirement queues. Charge growing node arrays when
they grow. Shared value arrays may initially be conservatively charged
more than once; document that overestimate rather than claim exact heap
accounting. Track outstanding load reservations so parallel misses cannot
each consume the same apparent free capacity.

Use high and low watermarks with bounded work between them. Reserve headroom
for the current transaction, dirty-node bursts, temporary loads, retiring
objects and GC delay. A cache target can bound managed live retention;
physical heap recovery also depends on GC and caller-owned references.

Bound the retirement queue separately in bytes. Otherwise an old operation
epoch can retain every detached object while new misses continue allocating,
and the nominal cache size falls while heap use grows. Admission must count
retiring bodies, outstanding loads and temporary parsing/value-copy buffers.
Reserve for their peak, not merely the final cached payload. Exercise
deliberately stalled readers and concurrent large misses in capacity tests.

Full index eviction requires Level 2 writeout. In the Level 1 full-replay
configuration, index nodes may remain unwritten and required memory grows
with the database. Retain Level 1 as a compatibility gate; do not claim an
index larger than RAM works in that mode without changing its writeout
contract. Measure startup reconstruction peaks as well as steady-state
cache usage.

Admission applies both to loads and to newly written values. The existing
large-value read policy alone does not prevent fresh puts from retaining
large value objects through parent references. A bypassed new value may
be detached only after its record is readable. A reader bypass may use a
temporary object without permanently swizzling it into a parent. Writer
and recovery nodes that become dirty must still be registered and pinned.

Reclaim scans must use a maintenance policy that does not promote what they
read or mark it as hot application data; section 5.1 specifies how. Apply
the same principle to large application scans; cache admission must not
change scan results.

Measure three categories separately: required pinned state, discretionary
cache contents, and temporary/retiring state. Keep storage-buffer accounting
separate and include it in total database memory measurements.

If the minimum pinned state exceeds capacity, report that cause and apply
documented admission/backpressure behaviour. Never free dirty state to meet
a target. Writers may need reserved capacity to let ordinary writeout
progress; making a writer wait for writeout that only that same writer can
perform would deadlock. Define transaction limits or reserve requirements
before enabling a hard ceiling, and fail an unsupported request before
partial logical mutation.

Any new pressure-triggered writeout rule must be designed separately with
restart invariance in mind. Prefer the existing deterministic writeout
schedule for the first Level 4 release. Startup distance in stream bytes
alone is not a proven bound on dirty RAM.

### 5.1 Reclaim and the cache

What Level 3 reclaim does (`Reclaim.step`): an iteration runs as a series
of internal transactions in the transaction listener, that is, under the
write lock. Each step (a) reads the next range of KVs at the iteration's
`tStart` with `GetMany`, which loads each value to measure it; (b) calls
`getOne` for every KV, which loads the value again if needed and reports
its stream position `tpos`; (c) rewrites the values with `tpos < pCut`; and
(d) touches the whole key range (`Trans.touch`), which loads every index
node on the way, makes the ones stored before `pCut` dirty, and so forces
their rewrite. Per iteration the result is that **every live value and every
index node is read once**, in key order, and iterations start after the
stream has grown by twice the startup distance. With everything resident,
that read is free. With eviction it is the largest read workload in the
database, and the Level 3 allowance f = 0.25 limits only the bytes written.
Level 3 measurements say nothing about it.

Risks if reclaim uses the ordinary read path:

* **Cache pollution.** One iteration swizzles the whole database into the
  parents through the normal path and marks it recently used, evicting the
  hot application set. Hit rate drops after each iteration.
* **Write-lock stalls.** Cold loads inside a step happen while the write lock
  is held; a step over a mostly cold range puts disk latency into the tail of
  an unrelated user commit. The Level 3 tail target (at most 200 index nodes
  per user commit) says nothing about reads.
* **Read amplification.** Whole-database reads per iteration, in key order,
  which on disk is mostly random relative to the stream layout.
* **Pinned burst.** The step's touched and rewritten nodes are dirty and
  pinned until written, so a step needs reserved capacity; the 200-node
  measurement target is not an enforced cap and the final KV can exceed the
  scan target (section 1).
* **Snapshot objects.** The scan reads at an old `tStart`, which can load
  historical versions as additional objects next to the canonical ones
  (section 4.1) and adds version-authority entries.

Proposed policy (a design to validate, not a measured result):

1. **Maintenance reads bypass admission.** The scan and the `getOne`
   loads use a maintenance mode: values are read into temporary objects
   and are not swizzled into the parent; index nodes needed only for reading
   are read the same way, or are admitted with the coldest access data, so
   the first sweep releases them. They never advance the access clock and
   never count as hits for the hot set. This is the "reader bypass" of
   section 5 applied to reclaim; the temporary parent rules of section 5
   (no unaccounted child edges) apply.
2. **Dirty pins are the exception, and are bounded per step.** Nodes the
   step makes dirty (touched old nodes, rewritten values, the table row) are
   canonical and pinned exactly like any writer state, by the ordinary dirty
   rules; they become ordinary clean, eligible and cold after writeout.
   The step size must fit the reserved capacity. Make the step size a
   function of that reserve, enforced as a hard cap by splitting the
   step (the existing `RerunException` path already repeats a step later),
   not as the current measured target.
3. **Look for reads that need not happen.** The rewrite decision
   (`tpos < pCut`) depends on the value's position, not its bytes. If the
   index node gives the position (and the length for the byte estimate)
   without loading the value, then the scan need only read the values it
   rewrites, which are the oldest ones. Check what the node stores before
   relying on this; the saving could be most of the read volume.
4. **Account for the read cost.** Count reclaim's reads separately from the
   hot cache (loads, bytes, misses per iteration, in `Reclaim.Stats`) and
   decide in step 6 whether pacing must include them. The allowance f
   limits written bytes; if reclaim reads dominate on a large disk
   database, an I/O-based pacing term is needed, or iteration start
   spacing must grow with the database size. Do not assume the
   write-based allowance bounds read cost.
5. **Stall mitigation, decided by measurement.** First measure cold steps
   under the write lock. If the user-commit tail is unacceptable, read the
   next step's range ahead of the lock using the maintenance mode with a
   short-lived reservation (prefetched data that is not used may be
   dropped), or shrink steps on a miss-heavy range. Do not add a
   background thread to the first release unless the measurement requires it.
6. **Expiry of reclaim's own reads.** The scan reads at `tStart`, which is
   after the pStart of every earlier iteration, so a cut should not overtake
   it. Verify this with the retention-change tests; if it can, the step must
   be retried or the iteration restarted, never treated as a database
   fault, and `ReadBelowFirstPosException` must not reach the storage
   manager's error state.

Tests and measurements (added to section 9): a hot working set that fits the
budget, a database several times larger than the budget, and reclaim
active: the hot set's hit rate and latency with and without an iteration;
reclaim loads and bytes per iteration against database size; maximum commit
tail of the user transaction that hosts a step, cold and warm; pinned
bytes at the step peak against the reserve; stream bytes with and without
eviction unchanged (restart-invariance trace of section 9); no reclaim
object remains swizzled after its step, apart from nodes still dirty.

## 6. Readers, retirement and Level 3 cuts

Use a lifetime protocol shared by eviction and cold loading, while preserving
Level 3 decision D1 = A. The default operation can expire. It does not
promise to delay reclaim for an entire query or iterator. Establish three
separate lifetimes:

* The actual snapshot is fixed at admission. `Long.MAX_VALUE` and future
  requests are clamped by `DbClock.lookupTime`; retain that finite result
  for traversal, retry and expiry classification.
* An object epoch protects node/array references held during a traversal or
  scan chunk. Include gets, writer warm-up and temporary uncached loads in
  the protocol. End the epoch only after local graph references are discarded.
* A cold load needs a defined backing-byte lifetime. Either use a short
  byte-range pin for the complete load or allow a cut to abort it with the
  existing expiry exception. In either case, only a completely read, valid
  object may be registered or swizzled. Do not publish partial parsing state.

For the expiry-compatible default, cuts can proceed while older operations
run. A cold read below the cut must preserve `ReadBelowFirstPosException`
through the storage layers and become `LookupTimeNotAvailableException`
only when its actual snapshot expired. A miss or capacity retry must reuse
that snapshot; reusing the original `Long.MAX_VALUE` request would silently
move it forward. Warm memory may still answer an expired snapshot correctly;
the contract permits this. A still-available snapshot must remain readable.

The public `UseIndexBuilderImp.IndexIterator` already remembers the first
batch's actual time. Preserve it between chunks and after internal retries.
If a later chunk expires, report the exception; do not treat it as end of
data or continue at a later time. Define cleanup of a failed `GetMany`'s
partial results and operation fields. An iterator may have delivered a
prefix before expiry; document that distinction from an atomic scan result.

Protected snapshots (D1 = B) remain an optional later contract for a user
need. If selected, registration and frontier admission must be atomic,
physical cuts must wait for protected backing bytes, and internal retries
must reuse the ticket. A ticket validly admitted before the frontier moves
must not be rejected as a fresh request. Specify lease expiry, retention
changes and cancellation explicitly. Keep bounded object epochs between
chunks even when such a ticket spans a whole scan; one indefinitely held
object epoch would prevent retirement. Buffer delay supplies none of these
guarantees. Do not silently enable full-scan protection in the base Level 4
implementation.

Object retirement must prevent publication of new references to an object
while it is being released. On a cold path, either revive a retiring
object under the metadata protocol or wait/retry after its release. A
reader holding an existing Java reference can finish using a read-safe
object; the JVM protects its allocation, but does not solve canonical
identity, reference-accounting or stream-lifetime races.

Keep retired parent objects and their outgoing counts until earlier readers
can no longer use them. Prevent cold loads from permanently attaching new
children to a retiring parent. Clear reusable operation fields that retain
nodes after exit; leaving a `GetData` or iterator pointing at an old parent
can keep an entire subgraph alive. Returned value arrays belong to the
caller and are outside the cache's ability to reclaim.

A miss must not wait for an object's grace period while the same operation
holds the old epoch that prevents that grace period from ending. For
example: reader R enters an epoch, C begins retirement, and R then misses
on B; if allocation of B waits for C's retirement, and C waits for R to
exit, both wait forever. A read-side solution can discard local object
references and leave its object epoch before waiting or doing I/O, retain
the actual snapshot time (and a ticket only in protected mode), then
re-enter and restart at that snapshot or report its expiry. Alternatives
need an equally explicit progress argument. Writers
that have partially mutated state require reserved capacity and cannot
adopt an unproved restart/rollback scheme.

Record a lock-order specification before implementation. The existing cold
path takes a pointer lock before accessing the node table; an evictor must
not invert that order by holding the table lock while waiting for a pointer
lock. Candidate selection can snapshot metadata and release its lock before
locking and rechecking a slot. A miss holding a slot lock must release it
before requesting writer exclusion for sweeping or waiting for capacity;
otherwise it can form the cycle writer lock -> slot lock -> writer lock.
Reacquire and recheck the slot before publication. Coordinate eligibility
with the writer at stable transaction boundaries. Avoid holding a global
metadata lock across disk I/O or waiting for reader completion.

Account explicitly for the 128 shared pointer-lock stripes and the parent
node monitor added by the Level 3 repairs. A load holds its stripe across
I/O, so unrelated slots can block each other and the writer. Copying holds
the node monitor while copying local fields; do not acquire a stripe,
writer exclusion or capacity wait from inside that monitor. Decide and
test how a cold load releases locks before requesting capacity, then
rechecks the slot before publication. A bounded sweep is not a latency
bound if it can wait for one of these I/O-held stripes.

A sequential, quiescent prototype is useful for early proof and debugging.
Concurrent Level 4 is complete only after the lifetime protocol is tested;
GC reachability alone is not that protocol.

## 7. Lean model and proof plan

Add a separate cache model over [sis-model.md](sis-model.md) and
[lean/](../lean/README.md). Keep `P` as the complete logical specification,
not as the implementation's resident memory. The physical model should
include resident object identities, node IDs and histories, memory/stream
slots, preferred canonical objects, pins, and retained stream bounds.
Model shared children and distinct snapshots from the first examples.
Include actual snapshot times and the permitted expiry result in the
physical query model; cache retries must not select a later snapshot.

Define an operational lookup that follows the physical representation and
stream; it must not obtain its result from the reference `P`. Establish a
representation invariant relating its results to `P`. Derive safe fallbacks
from implementable eligibility conditions. Assuming the fallback already
answers every query correctly would merely assume the main result.

Version authority and reconstruction/runtime phase belong in that model.
`S.lv` can describe the required latest version in the specification, but
an operational resolver must use metadata and concrete references available
to the implementation. Defining it as a full-stream latest-version search
would conceal the main design problem. If writer-context invariants rule
out the component counterexample in section 2.1, prove that loading,
eviction, subsequent writes and restart preserve those invariants.

The existing `good` and `dirty` definitions in
[Stream.lean](../lean/SIS/Stream.lean), and `dirty_false_iff` in
[StreamLemmas.lean](../lean/SIS/Proof/StreamLemmas.lean), provide foundations.
The current proofs cover recovery and restart invariance under the exact
still-dirty test; `levels.md` lists the gaps between this and Java's
conservative tracking. Do not treat those gaps as already proved.

| Proof milestone | Required result |
|---|---|
| Eligibility and loading | The chosen retained version is complete for every permitted context; writer promotion preserves required state. Derive which version metadata can be forgotten after body release. Prove or explicitly scope lemma M and the latest-reference property needed by Java. |
| Cache operations | Loading, swizzling, unswizzling and unloading preserve the representation invariant and all permitted query results. Dirty/pinned objects remain resident. |
| Subsequent transactions | Cached execution refines logical execution, preserves dirty bookkeeping and appends the same abstract records under the same policy, regardless of cache schedule. |
| Reference release | Counts match physical edges and pins; removal/cascades leave no persistent cache root to released objects. Version-authority entries expire only when their dependencies end. Prove registry reachability, not a promise about when JVM GC runs. |
| Reclaim | Available snapshots remain correct; a successful in-flight result matches its original snapshot, and a cut-aborted expired read reports expiry without poisoning storage. Treat expired edges and optional protected tickets explicitly. |
| Concurrency | Object epochs, cold-load publication, coherent slots, retirement and cuts preserve those properties under permitted interleavings. Protected admission is proved only if that mode is added. The Java protocol must refine the abstract atomic operations. |
| Memory progress | Under stated bounds on pinned state, transaction sizes and fair sweeping, pressure eventually releases enough eligible cache bytes or identifies insufficient capacity. Prove there is no waiting cycle involving an operation's own epoch and that retirement/version metadata are bounded. |

The first Lean implementation can be sequential and use a fully retained
stream. Add reclaim and concurrency as extensions. Memory progress is a
separate theorem from safety. Use an executable example and randomized
cache schedules before the proofs; include a historical parent sharing a
child that is subsequently updated and evicted.

Run the same fixed-time trace with no eviction, eviction after every
eligible boundary, and seeded random eviction, each with and without
restarts and reclaim. Compare complete stream bytes, cuts, available lookup
frontiers and model-checked answers at recorded actual times. In concurrent
expiry tests compare permitted outcomes, not identical success/expiry counts.
Sample logical cut decisions separately from physically delayed file deletion.
Extend identity checks to distinguish
logical IDs, current canonical sharing and expected object replacement.

For larger-than-memory evidence, use real file storage and a capped JVM.
An in-memory backing stream itself consumes heap, so it cannot establish
that disk data larger than RAM works. Use `CutStream` for small exact-cut
regressions. Test total data at least several times the managed budget and,
separately, an index larger than that budget; value eviction alone is not
full Level 4. The oracle should use reproducible expected values or an
external process so that storing the whole reference database in the same
heap does not invalidate the memory experiment.

Measure warm all-resident gets, cold and mixed gets, historical gets,
uniform and concentrated updates, long keys, and reclaim-heavy workloads.
Report throughput, latency distributions, disk reads, hits/misses, bytes

sweep slots per released byte, dirty peaks and GC behaviour.

Use alternating matched builds and repeated runs for read comparisons.

above 5%; investigate anything larger before choosing it as a tradeoff.
This 5% figure is a proposed target, not an accepted or measured result.
The structural requirement remains no added per-hop ID-map lookup or cache
handle. Results for miss-heavy workloads should distinguish unavoidable
disk I/O from avoidable sweeping, allocation and contention costs.

## 10. Natural eviction and remaining design decisions

Progression writes dirty nodes and can make them eligible for unloading.
Reclaim expires old history and can make references unnecessary. Neither
event removes the strong references held by a cache and its resident graph.
An unchanged, unaccessed live value remains part of the current database;
its bytes belong on disk but need not remain in RAM. Explicit cache cleanup
is necessary. Reclaim may otherwise increase residency by scanning values
and touching index nodes.

Decide before implementation how reclaim reads are paced and bounded
(section 5.1), and how access data is stored once the position field can no
longer hold it safely (section 4.5.1). Decide how the soft target relates to dirty reserve,
how epochs and cold-load lifetime interact with expiry, how much sweep work can occur on a
foreground operation, and how writer promotion obtains complete state
after canonical eviction. Keep exact LRU, background eviction threads,
permanent disk-position directories and arbitrary early writeout out of
the initial design unless evidence requires them.

The main outstanding risk is whether required dirty/retiring state can be
bounded tightly enough for practical small budgets while reclaim is active,
and whether correct version authority can be maintained without memory
proportional to the entire database. Resolve the latter before implementing
generic index eviction; reference accounting alone cannot settle it.
The current Level 3 measurements show writeout bursts; conservative dirty
tracking and `TransSeq`'s fairness limit also deserve measurement. If those
requirements exceed capacity, a better selection policy cannot solve it.
The remedies belong in admission, transaction sizing, reader lifetimes and
the deterministic writeout design.

## 11. Research context and completion criteria

LeanStore's original paper demonstrates low-overhead resident access with
pointer swizzling and a cooling stage. Its implementation uses a single
owning reference, while discussing extensions for multiple incoming
references. This supports the general approach, not a ready-made solution
for BergDB's historical Dag. [LeanStore, 2018](https://db.in.tum.de/~leis/papers/leanstore.pdf).

The later retrospective identifies graphs and synchronization as important
swizzling difficulties and describes a move toward virtual-memory-assisted
buffer management. Those findings support measuring the costs of our
reference bookkeeping. That alternative would require a substantial change
from BergDB's Java-object representation and is outside this first plan.
[LeanStore retrospective, 2024](https://www.vldb.org/pvldb/vol17/p4536-leis.pdf).

Level 4 is complete when values and index nodes can both be unloaded and
reloaded under a managed memory budget; future writes and stream bytes are
preserved; reclaim, expiry-compatible readers, crashes and restarts remain correct;
and memory stabilizes in a real larger-than-cache workload. The Lean
claims, Java evidence, performance measurements and capacity limitations
should each be documented with their actual scope.
