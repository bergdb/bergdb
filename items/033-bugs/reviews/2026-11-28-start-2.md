Review of the start and recovery path after the changes of 2026-11-28
======================================================================

Created 2026-11-28 by Frans Lundberg. Status: done; the findings are for
028 and 033 to register.

A second independent review of BergDB's start and recovery, on `main` at
`2b3755ab` (2026-11-28). The first, of the same day
([2026-11-28-start.md](2026-11-28-start.md), on `ee8a8165`), is its
baseline and its method. Since then `main` got, in this order: 028-70 (a
refused start writes nothing: the recovery's writes are held in memory
and written after reclaim's check), 028-80 (a stream of zeros from 0 is
an incomplete creation; at most 5 MB a write), 028-79 with its E, F and
G (the walk refuses other bytes at a meta block's position; the first
block's reader passes over the fill's bytes and zeros), 028-81
(`created.txt`'s database ID compared before every other check), 028-82's
messages and 028-83. The start path's last change is `6ef2c7dd`; the
commits after it change no file of it. 028-70 and 028-79 were each
reviewed against their parents. This review reads the path as it stands
after all of them and runs it as a whole.

The question: which combinations of the day's rules, with kills, kills
inside a recovery, kills inside a start, power losses in a cut's batch,
zeros and other bytes after a kill, files of 200 kB, 1 MB and 5 MB,
forcing off and `created.txt`, lose or change data, refuse a sound
database, change a byte or a file in a start that refuses, or write
other bytes than the same history wrote on `ee8a8165`.

Decided or open elsewhere, and not findings here: 028-76's case (a), a
file before a gap whose first block is recovery's fill (Frans,
2026-11-28); 028-77 (the storage model; another database's file in the
middle of the stream is in its scope) and 028-78 (a deleted copy of the
same database passes C3's checks), both open for Frans; 028-79's notes
(C) and (D).

Method: the code read (`Db.startInner` and its checks,
`RecoverableStream` but its tests, `FileStream`'s open, cut, zero tail
and append, `Reclaim.initFromDb`, `StoredTrans.RECORD_CHECK`,
`MetaBlock`),
027-11 against it, then probes, in `2026-11-28-start-2-probes/` beside
this file; section 3 has the runs. Severities are 033's (S1 data lost or
wrong, S2 the database fails or will not start, S3 a call refuses
wrongly, S4 minor). Nothing in `java/` or `lean/` was changed.


# 1. Findings

No finding of S1, S2 or S3: in the runs of section 3 no start lost or
changed a value, none refused a sound database but in the decided cases,
no refused start changed a file, and no start wrote other bytes than
`ee8a8165`'s where both started. Three findings of S4, each a message or
a file beside the stream, and one doubt that a probe settled (2.6).

## F1. With created.txt, a stream of zeros or of a part of a creation is refused as a creation that did not complete

Severity S4, on a storage that lost bytes that it had forced, or after a
stream file was put in the place of the database's. Shown by probes
(`PubCreatedTxtProbe`, `CreationKillProbe`).

Where: `Db.refuseIncompleteCreation`
(`java/src/bergdb/core/Db.java:2086`) and
`RecoverableStream.isIncompleteCreation`
(`java/src/bergdb/storage/RecoverableStream.java:1040`; the zeros of
028-80 at :1045) read the stream only. `created.txt` is written after
the creation's sync (`Db.startInner`; 015-01, 028-18), so a directory
that has it held a database whose creation was durable, as
`DatabaseNotCreatedException`'s Javadoc says for the Pub API: "a start
that returned has made its creation durable, and the exception means a
crash inside that start". 015-01's rule for `created.txt` and no stream
byte follows from that (`DatabaseBuilderImp.refuseMissingStream`,
`java/src/bergdb/pubimp/DatabaseBuilderImp.java:276`): a
`DatabaseMissingException`, "held a database ... Restore the *.bergdb
files from a backup", for files "removed, not restored, or emptied"
(`DatabaseBuilder.start()`'s Javadoc). A stream file of 0 bytes gives
that; one of zeros, or of 1 to 415 bytes of the creation, gives the
other exception, of which the same Javadoc says "A database that holds
data never gives this exception".

The case: a directory with `created.txt` whose only stream file holds
zeros (up to 200,000 bytes), or a part of the creation's 416 bytes. No
kill of a database of the Pub API leaves that; a storage that lost the
file's bytes and kept its length does (zeros within a file's length are
what a power loss leaves on some file systems), or a file put there by
hand. The database was created, and may have held committed
transactions (its stream had not passed its first file). The start
says "The database was not completely created (a crash or a power loss
while it was created?) ... holds an incomplete creation, and no data.
Remove its files and start it again; the start then creates it": an
application that removes the files on this exception, as its Javadoc
says to, makes a new database where one was lost, with no sign of the
loss. For zeros this is 028-80's (until then a
`StreamFormatException`, "Could not find *any* valid meta block"); for
a part of the creation it is as since 005-33 and 015-01.

With the Core API and `DbBuilder.createdTxt` the case is also a kill's:
a Core start creates a database in a directory that has `created.txt`
and no stream byte, and a kill inside that creation leaves the older
`created.txt` beside a part of it. There the refusal says what is the
case.

The probes (2026-11-28). `PubCreatedTxtProbe`, through the Pub API: a
database made with `create()`, one value put and synced, closed (a
stream file of 528 bytes beside `created.txt`); with the stream file's
bytes zeros, and with the file cut to its first 100 bytes, `create()`
and `open()` both give "DatabaseNotCreatedException: The database was
not completely created (a crash or a power loss while it was created?):
its stream, of length 528, holds an incomplete creation, and no data.
Remove its files and start it again; the start then creates it (bergdb
005-33)." (of length 45 for the cut file); `open()` creates no
database. `CreationKillProbe`, through the Core API: the creation's
first write as zeros only, 1 to 272 bytes, with `created.txt` there:
`DatabaseNotCreatedException` in 272 of 272; every proper prefix of the
creation's 416 bytes with `created.txt` there: the same in 416 of 416.
No file changed.

What would settle it: with `created.txt`, the Pub API's start refuses
such a stream as a database whose stream is damaged, as it refuses one
with no stream byte, not as a creation; or the exception's Javadoc says
that it is also what a database whose only stream file was lost gives.

## F3. A created.txt that a kill or a power loss left empty or cut is not written again

Severity S4. Shown by probes (`PubCreatedTxtProbe`; `StartChain2` with
`-Dtxt=on` for a cut file).

Where: `Db.writeCreatedTxt` (`java/src/bergdb/core/Db.java:2221`) writes
the file with `Util.bytesToFile`
(`java/src/bergdb/common/Util.java:628`): a `FileOutputStream`, which
makes the file empty and then writes it, with no force. A kill between
the two, or a power loss before the system wrote the bytes, leaves a
`created.txt` that is empty or cut. `Db.writeCreatedTxtIfMissing`
(:1927) writes `created.txt` only where there is no such file, and
`Db.readCreatedTxtId` (:1982) gives no ID for a file without the whole
line "database ID:", so 028-81's comparison is not made
(`DbBuilder.createdTxt`'s Javadoc: "a missing created.txt, or one that
names no ID, is not compared, and the start writes a missing one
again").

So such a database starts as before 028-81 for good: another database's
first stream file, or another database's stream files in its directory,
is not refused by `created.txt`, and the file never names the ID. Since
028-81 `created.txt`'s ID decides a start; until then a start took from
the file its being there (015-01's mark, which an empty file still is)
and an earlier release's line "crypto key:" (020-28).

The probes (2026-11-28). `PubCreatedTxtProbe`, through the Pub API,
two databases with a value each: with A's `created.txt` empty, A's
start took its stream and left `created.txt` at 0 bytes; with B's
stream file then put in the place of A's, the start took it ("started,
/k/note.txt reads of b") and left `created.txt` at 0 bytes; the
control, the same with A's `created.txt` whole, was refused with
028-81's message. `StartChain2`: `created.txt` cut at a random length
before a start, 1,469 times: every start took the stream; in the two
runs that compare the file after the start, it was left as it was in
255 of 255.

What would settle it: a start that finds a `created.txt` without an ID
writes it again with the stream's ID, as it writes a missing one; and
the file is written whole (to a name beside it, then renamed).

## 2.1. The order of the start's checks

As 027-11, 1.2, 1.3 and 1.9 say, in `Db.startInner`
(`java/src/bergdb/core/Db.java:1471`): the storage's open (the lock,
the files' names and sizes, the gap, the tail of zeros left out); an
empty stream created; `created.txt`'s ID against the stream's first
valid block; an incomplete creation; the last valid block and its node
size; in `recover()` the block's record position, the files before a
gap, the walk of the tail, and the completion, held; `created.txt`'s ID
again; the startup pos, the section, the rerun, the startup distance's
KV; `Reclaim.initFromDb`, which refuses a stream that begins after the
cut before it cuts; the held writes; a missing `created.txt`.

* Every refusal of a stream that the start did not create comes before
  the first change of a stream file or of `created.txt` (the open makes
  `bergdb.lock` if it is not there). The first change is `initFromDb`'s
  cut (the truncation of the tail of zeros, then the deletes of the
  files before the cut and of the checked files before a gap, on the
  cut's thread), after its own last check; nothing that it runs after
  the cut reads the stream. The held writes follow, through the write
  buffer.
* `created.txt`'s refusal comes before a refusal of the tail
  (`RefusedStartProbe`: another ID together with a last byte of 7 gives
  028-81's message).
* The new order of a start's own writes, the cut before the completion
  (until 028-70 the completion came first), leaves after a kill at any
  point an image that the next start takes: `StartChain2`'s kills inside
  a start, 2.3.

## 2.6. The bound of the tail of zeros

The doubt: `FileStream`'s open leaves out the run of zeros at the end
of the last file if it is at most 8 MB (`zeroTailLength`,
`java/src/bergdb/stream/FileStream.java:1997`), and 028-80 bounds a
kill's zeros by the write that it cuts, 5 MB (`WRITE_MAX`, :322). The
open measures the run, not the kill's part of it: a value of zeros
before the kill's zeros would make the run longer, and a run above 8 MB
is left in the stream, where zeros past a record's end are refused.

It holds: the database's own zeros before a kill's are at most a meta
block distance long, as a valid block, which is not zeros, lies every
200,000 bytes, also inside a value. `ZeroValueTailProbe` (2026-11-28): a
stream of 249 MB, its last files of 20 MB, a value of 8,388,608 zeros
and a small record after it, written in two writes (5,000,000 and
3,396,480 bytes), the second zero from its first page boundary:
3,392,192 of the kill's zeros, a run of 3,579,008 at the end of the
file, left out; the stream ended right after the last valid block, and
the start took it with the 40 keys before. So the run is at most 5 MB
and 200 kB.
