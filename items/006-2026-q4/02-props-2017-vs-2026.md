-------

**CORE**, the speed of four Core tests (`get`, `get4t`, `getmany`, `set`),

(1.00 is cissi in 2013); **SS**, stream bytes per user byte in four scenarios.

its logs.

1. **2026 against 2017: CORE 6 percent better, MEM 16 percent, SS 4 percent;
   `set` 7 percent worse.** `get` is 17 percent faster and `get4t` 10 percent;
   `getmany` is the same. MEM goes from 271 to 227 bytes per KV, mostly
   because the 2026 code keeps fewer key node objects. The whole SS gain is
   the default startup distance, 20 MB in 2017 and 50 MB since 2026-10-13: at
   the same distance the two have the same SS. Under that, the 2026 code writes
   2 to 3 percent less for transactions of 100 KVs and 8 bytes more per
   transaction (`topPos`, the fix of M18) (sections 2 and 6).
2. **The new hardware: CORE 2.6 to 2.9 times faster for the same code.** The
   code that cissi ran on 2015-12-28 and 2017-07-29 gives 0.28 and 0.29 on F53
   against cissi's 0.81 and 0.76; each test is 2.4 to 3.2 times faster. That
   is the processor and JDK 27 together, as agreed; the two JVM defaults that
   changed since Java 8, the collector and the object header, do not explain
   it (0.28 with Java 8's). MEM and SS do not depend on the machine: with Java
   8's collector and header both codes give exactly cissi's MEM, 169, and SS of
   the 2017-07-29 code equals cissi's to within 0.01 (section 3; the code cissi
   ran in 2015 is known only to the day, section 5).
3. **The 2017 version is not the code that cissi measured; it is the slowest
   and largest of the four.** The import of 2017-08-01 comes two days after the
   last cissi run, two days of an unfinished rewrite of the node cache. On the
   same machine: MEM 166 to 271 (+63 percent), `set` 0.25 to 0.34 (+36
   percent), CORE 0.29 to 0.32, SS 1.52 to 1.56. A run of each commit in
   between, and class histograms, show the causes: a node table (Cache3) with a
   `HashMap` entry for every node, an id stored with every value node, and the
   table's split into 256 maps, after which every entry of the table is a
   `HashMap$TreeNode` (section 4).
4. **That tree bug is still in the 2026 code, and a one-line change removes
   it.** The way Cache3 picks one of its 256 maps puts about 17 node ids in
   each `HashMap` bin, and `HashMap` turns such bins into red-black trees.
   Choosing the map by a multiplicative hash instead
   ([maphash.patch](02-props-2017-vs-2026/maphash.patch), an experiment in
   this item only) gives MEM 191 instead of 227 (-16 percent) and `set` 1.60 us
   instead of 1.80 (-11 percent), with SS and the other tests unchanged. It has
   not been through the level checks (section 4). The fix is now
   [005-08](../005-todo/08-fix-node-table-tree-bins.md).
5. **Against "Typical output (2015-12-28)":** the 2026 code on F53 is 2.7
   times faster than the 2015 code was on cissi (CORE 0.30 against 0.81), uses
   34 percent more memory per KV (227 against 169) and has about the same SS
   (1.50 against 1.47). On the same machine it is 7 percent slower than the
   2015 code (0.30 against 0.28): `set` 42 percent slower, `get` 10 percent
   faster, `get4t` and `getmany` the same; MEM +44 percent. The node table and
   the ids of value nodes, both kept in 2026 (Level 4's eviction works on the
   table), add 107 bytes per KV, of which the smaller key nodes of 2026 save 39
   (section 5).
6. On the way (section 7): four threads read only about 2.1 times as fast as
   one, on F53 as on cissi; and `get4t` is the test that other work on the
   machine disturbs, including this session's own work (14 runs were set aside
   and repeated).


1. What was measured
--------------------

Props and its four Core tests are the same from 2015-12-28 to 2026, except for
renames and comments, so the yardstick is the same for every version.

* **MEM**: `Mem`: one million KVs (keys `"0"` to `"999999"`, empty values,
  100 per transaction, a `DummyStream`, the test setup: no eviction); the heap
  in use after `System.gc()`, after minus before, per KV.
* **CORE**: `Core`: `get` (one thread, random gets among 100k KVs, 2 s),
  `get4t` (four threads, 1 s; the time per get of all threads together),
  `getmany` (scans of 10,000 KVs; the time per KV), `set` (200,000 single-KV
  transactions on a `DummyStream`); five rounds in one JVM, the best time of
  each test divided by its baseline from cissi in July 2013 (1.0, 0.4, 0.2 and
  5.0 us).
* **SS**: `SS1` to `SS4`: 100 MB of KVs of 1,000 bytes (SS1, SS2) or 100 bytes
  (SS3, SS4), 100 KVs per transaction (SS1, SS3) or one (SS2, SS4), into a
  `MemoryStream` with the default builder; stream length over user bytes.

* **The node table.** Cache3 enters every node, value nodes too: 1.15 entries
  per KV in 2017, 1.10 in 2026. Every pointer the writer creates enters or
  counts its target in the table (`pointerCreated`), under one lock for the
  whole table (`getLock` returns `bigLock`, in 2017 and in 2026). With
  ordinary bins the table took 55 bytes per KV at `9d9a038` (MEM +41, as
  Cache2's 14 went) and 73 with `CacheEntry` at `87d5faa`; with the tree bins
  110 in 2017-08-01 and 105 in 2026. It is also two thirds of the slower
  `set`: 0.25 to 0.34 was +0.02 with Cache3, +0.03 with the ids and +0.04 with
  the node caching and the 256 maps.
* **The ids.** Value nodes grew from 24 bytes (2015) to 32 (by 2017-07-29) to
  40 (`290e766`, the id), and the id is stored in the stream (format 3 to 4 of
  `StoredValueNode`): 8 bytes more per KV, SS3 and SS4 +0.08.
* **The trees.** With the split into 256 maps (`fa338b0`) every entry became
  a `HashMap$TreeNode`, +37 bytes per KV. The ids of new nodes are
  consecutive odd numbers (`Spos.nextVpos`). Cache3 picks the map by the XOR
  of the id's eight bytes; `HashMap` picks the bin by the low bits of
  `h ^ (h >>> 16)`. For the ids of one map (below 2^24, as here), the low byte
  of that bin index is then the same for all ids that share their second byte,
  so ids pile up about 17 to a bin, and `HashMap` makes a red-black tree of every bin of 8 or more,
  searched by comparing `Long`s. The 2026 code has the same `mapIndex` (with
  a fix of 2026-10-13 for negative ids) and the same trees: 1.10 tree nodes
  per KV.
* **Key nodes in 2026**: 0.10 objects per KV against 0.15, and their arrays,
  39 bytes per KV less; probably D1 of 2026-10-16 (a transaction splits the
  nodes it created in place, and nodes no lookup reaches leave the dirty set;
  `docs/level2-alignment.md`, 10.4). Not checked further.

**The experiment.** [maphash.patch](02-props-2017-vs-2026/maphash.patch)
replaces the body of `Cache3.mapIndex` with the top 8 bits of
`id * 0x9E3779B97F4A7C15L` (Fibonacci hashing), so that the map no longer fixes
the bin. `run.sh maphash` builds the 2026 code with it, in
`java/build/props-006-02/` only. Four runs of each, alternating, and the
probe's `set`:

| `set`, best of 5, us per transaction | 1.765 (the first), 1.679 | 1.678, 1.681 | 1.761, 1.795 | 1.787, 1.804, 1.800, 1.797 |

* The distance moves SS by 4 percent and nothing else. At the same distance
  the two versions have the same SS, and the probe reproduces Props's SS of
  each version at its default exactly.
* Per scenario, from the exact stream lengths: the 2026 code writes 2.0 to
  2.8 percent less in transactions of 100 KVs (SS1, SS3), probably D1's
  in-place splits (`docs/level2-alignment.md`, 10.4, measured 1 to 14 percent
  fewer stream bytes on other workloads); and 8.2 to 8.8 bytes more per
  single-KV transaction (SS2, SS4): the 8 bytes of `topPos`, added to the
  record header on 2026-10-15 with the fix of the startup bug M18 (header 24
  to 32 bytes), and a little more.
* The larger distance saves 2.3 to 5.7 percent per scenario in both versions.
* `set` does not depend on the distance (a `DummyStream`).


7. Other observations
---------------------

* **Four threads read about 2.1 times as fast as one.** 2015 code on F53:
  `get` 0.29 us, `get4t` 0.13 us per get (0.325 times 0.4 us), a ratio of
  2.2; on cissi 2.1; the 2026 code on F53 2.0. F53 has eight performance cores
  for the four threads. Every `Db.getOne` enters `synchronized (readSync) {}`,
  one monitor for all readers, in every version since 2015, and key nodes lock
  their pointer reads (`KeyNode`, `synchronized (this)`); that the scaling
  stops there is likely but not measured.
* **`get4t` and other work on the machine.** Fourteen runs overlapped this
  session's own work (tool calls, writing files, the editor showing them):
  `get4t` was 0.43 to 0.53 in nine of them, against 0.31 to 0.39 in every
  other run. They were set aside by that criterion, decided from the session's
  times and not from the results, and repeated with the session idle
  ([runs/disturbed/](02-props-2017-vs-2026/runs/disturbed/readme.md)). A
  check with one busy process (`yes`) during the run: `get4t` 0.34 and 0.38
  against 0.33 and 0.33 without, the other tests within one step. So the
  four-thread test needs a quiet machine; the others hardly do.
* **`get` of the 2026 code is sometimes faster**: 0.21 to 0.24 in 5 of 31
  runs (the experiment's included), against 0.25 to 0.27 in the rest, with
  both collectors; perhaps a different compilation by the JIT in those JVMs.
  Not followed up; the medians do not depend on it.
* **SS and the machine.** SS was identical in every run of a version on F53,
  across collectors and headers. For the 2017-07-29 code it matches cissi's
  except SS4, 2.26 against 2.27; for 2015 see section 5. The databases of SS
  take their time from `SystemClock` (milliseconds, made unique per
  transaction); whether the 0.01 comes from the machine or from a slightly
  different code that day was not found.

* The tests are small: everything fits in memory, `set` writes to a
  `DummyStream`, nothing is evicted. They say nothing about I/O, eviction or
  the workloads of the 2026 harness (`docs/performance-harness.md`).

So the 69 bytes from 2015 to 2026 are: the node table, +91 (105 bytes a KV in
2026 against Cache2's 14), of which 35 are the tree bins; value nodes +16
(the `int` of 2016 and the id of 2017); D1's smaller key nodes, −39; other
+1.6.

The 2026 table, per entry (1.10 a KV): a `HashMap$TreeNode` of 56 bytes, a
`Long` of 16, a `CacheEntry` of 16, about 8 of arrays, 96 in all. With
005-08's fix the bin is a 24-byte `HashMap$Node` (MEM 191). What else could
come back, not measured: the 16-byte `Long` keys and the bin objects in a
table keyed by primitive longs (about 25 to 35 bytes a KV), the `CacheEntry`
if its count could live in the node (17.5), and the two 2016 and 2017 fields
of a value node if they are not needed (8 each; the id is also 8 bytes a KV of
stream). With all of them MEM would be about 130 bytes a KV, below 2015's 158
because of D1: a rough sum, not a measurement.
