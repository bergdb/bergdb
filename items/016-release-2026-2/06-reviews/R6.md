## 2. Faults

### R6-F1. A record whose size field is larger than its content is accepted, and the records it covers are lost
* Where: `core/StoredTrans.java`, `Parser.parse`, lines 278 to 373 at
  f5a5f66 (`lastPos` from the content, line 369, never compared with
  `byteSize`); `core/NodeStream.java`, `TransIterator.next`, lines 372 to
  393 (steps to the next record by the size field, line 393).
* Intended: a stream that does not follow the format is refused with a
  `StreamFormatException` (`DbStarter.validateTransactions`' Javadoc: "If
  a transaction does not follow the db stream format. This should only
  happen if the db stream is corrupt or was tampered with"; 005-74: "A
  database whose stream is corrupt should be refused with a clear error",
  and its option A, "confines nodes and the got-dirty list to its declared
  size"). A record's first 4 bytes are its total size
  (`RecoverableStream.append`'s Javadoc), so a record whose header, nodes,
  end marker, got-dirty list, padding and last byte end before its size
  says does not follow the format.
* Actual: the parser checks that the content fits in the declared size,
  not that it fills it: it computes `transSize` from the content (line
  368) and sets `lastPos` from it, and the iterator goes on at `tpos +
  size`. A size field that is larger than the record, and ends on a byte
  that is `LAST_BYTE` (the last byte of a later record) or 0, is taken,
  and every record inside it is skipped without a word.
* Effect: lost data at a start that succeeds; a database that does not
  fail when it should. The probe: three committed transactions, records A,
  B and C (puts of `/a`, `/b`, `/c`); A's size field set from 120 to 208,
  A's size plus B's, so that it ends on B's last byte. The start succeeds,
  with and without `-ea`, and `/b` is gone: `START ACCEPTED: /a=1,
  /b=null, /c=3`. No checksum covers a record's header (005-75 says so of
  its time field), and nothing compares the size with the content. With a
  size that reaches past the end of the stream (`R6SizeProbe2`, 4,392),
  recovery zero-fills to it, the record's last byte is then 0, and the
  start succeeds with all three gone, `/a=null, /b=null, /c=null`: that
  case is recovery's zero fill on a corrupt size, 005-83's question (now
  014-01), and the parser's check below does not reach it, as such a
  record is never parsed.
* Evidence: the test `DbTesterRestart.testEnlargedRecordSizeRefused`
  (`R6/R6-F1.diff`), `java -ea -cp build/bergdb.jar bergdb.dev.Unit -c
  bergdb.core.DbTesterRestart -m testEnlargedRecordSizeRefused`, fails on
  f5a5f66: `java.lang.AssertionError: started with A's size over B; /b =
  lost`. The probes `R6/R6SizeProbe.java` and `R6/R6SizeProbe2.java`
  (in package `bergdb.core`, before `build/bergdb.jar` on the class
  path) print the lines above.
* In 2026.1: yes (`git show release-2026.1:java/src/bergdb/core/StoredTrans.java`:
  the same `lastPos` from the content, no comparison; the iterator the
  same).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no. Valid records are unchanged; the serializer's `totalSize`
  is the content's size exactly.
* A fix: in `Parser.parse`, after the padding check, refuse `transSize !=
  byteSize` with a `StreamFormatException` ("the record's content ends at
  ... and its size says ..."). Records with last byte 0 (recovery's zero
  fill) are not parsed, so they are not affected. Tried in the clone, not
  kept: with it the new test passes, and so do the unit tests of
  `DbTesterRestart` (22), `StoredTrans` (22), `NodeStreamTester` (16) and
  `TransSeq` (18).

### R6-F2. A corrupt startupPos in the last record is accepted, and the transactions before it are lost
* Where: `core/Db.java`, `getStartupPosFromLastTransaction`, lines 766 to
  801 at f5a5f66 (`result = storedTrans.startupPos`, line 788, checked by
  an `assert result >= 0` only); `core/DbStarter.java`, `startup`, which
  takes the first record read as the startup state.
* Intended: the same as R6-F1: a corrupt stream is refused, not started
  with data missing (`validateTransactions`' Javadoc; 005-74; 005-75,
  which added order and range checks for the header's other unprotected
  field, the time, after one flipped bit of it failed the start).
* Actual: the startup pos is read from the last committed record's header,
  which no checksum covers, and nothing checks it against the records: not
  that it is at most the record's own position, not that it does not
  decrease from record to record, not that the record that moved it past a
  transaction wrote that transaction's got-dirty nodes. A start reads the
  section from any record start it names, and takes the index nodes of
  the stream at that record's time as the state, whether or not they were
  written.
* Effect: lost data at a start that succeeds. The probe: records A, B, C
  (puts of `/a`, `/b`, `/c`) at 264, 384 and 472 with a startup distance
  of 1 MB, so the startup pos never moved (0) and no index node was
  written after the creation; C's startupPos set from 0 to 384, B's
  position. The start succeeds, with and without `-ea`: `START ACCEPTED:
  /a=null, /b=null, /c=3`. Both committed transactions before C are gone;
  B's too, though B is the first record of the section the start read.
* Evidence: the probe `R6/R6StartupPosProbe.java` (in package
  `bergdb.core`), the line above.
* In 2026.1: yes (`git show release-2026.1:java/src/bergdb/core/Db.java`,
  `getStartupPosFromLastTransaction`: the same).
* A fix needs a design choice: yes. A checksum of the record header is a
  format change (`StoredTrans.RECORD_FORMAT`); without one, checks in the
  way of 005-75: the startup pos of each record of the section at most its
  own position and not below the previous record's (cheap, and they catch
  a flip of a high bit, but not this probe's value), and, to catch this
  probe, that every got-dirty id of the section's first transaction has a
  version in the section after it (the record that moved the startup pos
  there wrote it). Or Frans accepts it as outside the fault model, as the
  record header has had no checksum since 2015.

### R6-F3. MetaBlock's format comment: the last byte is 10, not 1, and the version is read as 2 bytes, not an int
* Where: `storage/MetaBlock.java`, the class Javadoc, lines 14 to 30 at
  f5a5f66; `MetaBlock.getVersion` (line 163) and
  `RecoverableStream.readMetaBlock` (line 697) read
  `bytesToUShortLE(..., 4)`; `initBlock` (line 73) writes
  `intToBytesLE(CURRENT_VERSION, block, 4)`.
* Intended: the format comment says "4 4 Version of BergDB stream format
  as an int (154 for this version)" and "127 1 META_BLOCK_LAST_BYTE. 1 is
  used to indicate that the block is valid".
* Actual: `META_BLOCK_LAST_BYTE` is 10 (line 33); the version is written
  as an int and read as an unsigned short, so a block whose int at offset
  4 is not 154 but whose low two bytes are is taken as version 154.
* Effect: a reader of the format is misled (the C clone was written from
  these comments and the code, 005-75's reason for fixing such comments);
  a meta block whose version int is 65,690 is accepted. No data is lost.
* Evidence: the probe `R6/R6MetaBlockProbe.java`: `meta block 0: int at 4
  = 154, last byte = 10`, then `copy: int at 4 = 65690` and `START
  ACCEPTED: /a=1`.
* In 2026.1: yes (`git show release-2026.1:java/src/bergdb/storage/MetaBlock.java`:
  the same comment and `intToBytesLE`; `readMetaBlock` the same
  `bytesToUShortLE`).
* A fix needs a design choice: no for the comment; reading the version as
  an int (refusing nonzero bytes 6 and 7) changes no valid stream, as every
  writer writes 0 there.
* A fix: the comment says "10" and "version, 2 bytes (an unsigned short),
  and 2 bytes that must be 0"; optionally `readMetaBlock` reads 4 bytes.

### R6-F4. Checks of stream data at a start that are asserts: without -ea a corrupt got-dirty id is accepted, with -ea it is an AssertionError
* Where: `core/DbStarter.java`, `canonicalNode`, line 490 at f5a5f66
  (`assert node.getId() == id`); the same kind: `topNodeOfLastTransaction`,
  line 314 (`assert newPos == null || newPos == pos`), and `core/Db.java`,
  `getStartupPosFromLastTransaction`, line 789 (`assert result >= 0`),
  with `StartupPos.set`'s `assert pos >= 0`.
* Intended: DbStarter's own rule since 2026-10-16 (line 284, the super
  root: "a check, not an assert, so that a stream that breaks it is refused
  also without -ea"); a corrupt stream is a `StreamFormatException`
  (`validateTransactions`' Javadoc; `Db.start`'s `@throws`; 005-74).
* Actual: these three compare stream data with what the start expects by
  `assert` only. `canonicalNode` reads the node at a got-dirty entry's
  stored position when its id is in neither the node table nor the
  section, and registers what it read as a canonical object and puts it
  in D, whatever its id. Without `-ea` nothing is checked; with `-ea` the
  start fails with an `AssertionError`, not a format error. A negative
  startupPos gives an `IllegalArgumentException` from the stream's read
  without `-ea` ("Negative position not allowed, -8"), and an unaligned one
  `IllegalArgumentException: bad transPos, 4` from the parser, in both
  modes: refused, but not as a format error.
* Effect: a database that does not fail when it should (without `-ea`),
  and a refusal of the wrong kind (`AssertionError`,
  `IllegalArgumentException`, where `Db.start` declares
  `StreamFormatException`). The probe's corrupt id leaves D's ids as they
  were (the node it read is in the node table already), so it shows the
  missing check, not lost data; a corrupt position of an entry whose node
  is in neither the table nor the section would put another node's
  version into the node table as canonical (section 3, D2).
* Evidence: `R6/R6GotDirtyIdProbe.java` (package `bergdb.core`): A's
  got-dirty entry 0, id 1 at 160, set to id 123456789; without `-ea`:
  `START ACCEPTED: /a=1, /b=2, /c=3; D's ids: 1 0`; with `-ea`: `START
  REFUSED: java.lang.AssertionError: ids differ, 1 != 123456789`.
  `R6/R6StartupPosProbe3.java` with `-Dsp=-8` and `-Dsp=4`: the lines
  quoted above.
* In 2026.1: yes (`git show release-2026.1:java/src/bergdb/core/DbStarter.java`:
  the same assert in `canonicalNode`; `Db.java` the same `assert result >=
  0`).
* A fix needs a design choice: no.
* A fix: in `canonicalNode`, `if (node.getId() != id) throw new
  StreamFormatException(...)` naming the entry, its transaction and the
  position; in `topNodeOfLastTransaction` the same for `newPos != pos`; in
  `getStartupPosFromLastTransaction`, refuse a startupPos that is negative,
  not a multiple of 8, or after the record's own position, with a
  `StreamFormatException` (part of R6-F2's checks).

### R6-F5. Db.setStartupDistance clamps to 400,000 to 10^9 bytes without saying so: a call with a setting in force below 400,000 writes 200 kB and changes the setting
* Where: `core/Db.java`, `setStartupDistance`, lines 316 to 374 at
  f5a5f66 (the clamp, lines 348 to 352, before the test for the setting in
  force, line 361).
* Intended: the Javadoc (new with 005-53 and 007-07): "Sets the startup
  distance, the target size of the startup section ... The new setting
  applies at once ... A call with the setting in force writes nothing
  (bergdb 005-53)". It names no range; `DbBuilder.startupDistance` takes 10
  to 2^31 - 1, and the core's tests use 100 to 2,000.
* Actual: the argument is clamped to 400,000 (`2 * META_BLOCK_DISTANCE`)
  to 10^9 first, and only the clamped value is compared with the setting.
  On a database whose setting is below 400,000 (or above 10^9), a call
  with that setting commits the 200 kB transaction and sets 400,000 (or
  10^9); any call sets the clamped value, not the one given.
* Effect: a call that should change nothing writes 200 kB and changes
  the take's target (the startup section grows to 400,000), and the setting
  that "applies at once" is not the argument. Only the core API and JMX
  (`Jmx.DbMonitor.setStartupDistance` passes its bytes as given): the Pub
  API clamps to 5 to 1000 MB first, inside the core's range.
* Evidence: the test `DbTester.testSetStartupDistanceInForceBelowClamp`
  (`R6/R6-F5.diff`), `java -ea -cp build/bergdb.jar bergdb.dev.Unit -c
  bergdb.core.DbTester -m testSetStartupDistanceInForceBelowClamp`, fails
  on f5a5f66: `java.lang.AssertionError: the setting, expected 2000, got
  400000.`
* In 2026.1: no, as a fault. The clamp is the same, but 2026.1's Javadoc
  said "Suggests a new startup distance", with no claim about a call with
  the setting in force (`git show release-2026.1:java/src/bergdb/core/Db.java`).
  New in 2026.2.
* A fix needs a design choice: yes, small: either the Javadoc states the
  range and that the clamped value is what is set (and the test for the
  setting in force compares the clamped value, as now), or the method
  refuses an argument outside the range with an `IllegalArgumentException`,
  or it clamps to the builder's range (10 to 2^31 - 1) and keeps the
  200 kB transaction, whose meta block is needed whatever the value.
* A fix: the first, two sentences in the Javadoc: "The value is clamped
  to 400,000 to 1,000,000,000 bytes, and the clamped value is set; a call
  whose clamped value is the setting in force writes nothing."

### R6-F6. DbStarter.canonicalNode's Javadoc gives a reason for the stored got-dirty ids that does not hold: a delete of a key that does not exist makes nothing dirty
* Where: `core/DbStarter.java`, `canonicalNode`'s Javadoc, lines 467 to
  476 at f5a5f66.
* Intended (the Javadoc): "The rerun does not reach every node in D: a
  delete of a key that does not exist makes the nodes on its path dirty,
  but it is not stored, so it is not rerun. D is rebuilt from the stored
  ids".
* Actual: an operation makes its nodes dirty only if it changed something
  (`Db.endOfOp(false)` after each put or delete in `Db.putKvs`; levels.md
  5, "Marking"), so such a delete adds nothing to D. The nodes of D that
  the rerun does not reach come from a touch (`touchRange`,
  `endOfOp(true)`, reclaim's steps), which the Javadoc does not name.
* Effect: a reader of the startup (and of the C clone's, written from
  it) is given the wrong case for the one path where a start reads a node
  of D from the stream (D2). No data effect.
* Evidence: the probe `R6/R6NonexistentDeleteProbe.java`: after 200 puts
  at a startup distance of 2,000, a transaction that deletes `/k/1050x`:
  `delete of a key that does not exist: record of 1224 bytes, got-dirty
  nodes in its TransInfo: 0`.
* In 2026.1: yes (the same Javadoc; `endOfOp(false)` the same).
* A fix needs a design choice: no.
* A fix: the Javadoc names the touch: "a transaction with a touch (a
  reclaim step) makes dirty every index node of its range, and the touch
  is not stored, so it is not rerun".

## 3. Doubts

* **D1. A crash inside `setStartupDistance`'s record, after its meta
  block, keeps the new setting and loses the record.** The probe
  `R6/R6DecreaseCrashProbe.java` (a database at 1 MB, 400 transactions,
  `setStartupDistance(500,000)`, whose record runs from 52,264 to 268,143
  with the meta block at 200,000, then 100 transactions; 233 cuts in and
  around that record): every start succeeds with the right data, and
  after a cut between 200,128 and the record's last byte the setting is
  500,000 though the transaction that set it is lost (79 of the 233 cuts
  have 500,000; in 72 of them the record is lost, in 7 it is whole).
  INV-CRASH (011-01) asks for "the database state after the last complete
  transaction before the cut"; whether the setting is part of that state
  is a question for Frans, not a verified fault. The Pub Javadoc says the
  setting "is written to the stream with a small transaction ... so a
  restart keeps it", which a cut before the meta block keeps as well (the
  old setting, with the record lost). No data is wrong in any cut.
* **D2. A corrupt got-dirty position could make a start register another
  node's version as a canonical object (R6-F4's harmful case).**
  `canonicalNode` reads at the stored position only for a got-dirty id in
  neither the node table nor the section; by the code, only a touch
  transaction (a reclaim step, `Db.putKvs`'s `touchRange` with
  `endOfOp(true)`) leaves such entries, as every other got-dirty node is on
  a rerun put's path or written in the section. Not verified for want of
  time: it needs a level-3 stream with a reclaim step in the section. What
  would verify it: such a stream, the step's got-dirty position of a cold
  node redirected to another node's version, a start without `-ea`, and a
  read under that node.

## 4. Checked and right

* `TransSeq.take` against its Javadoc and Lean's `takeLoop`,
  `takePolicy` and `javaPace`: the deadline `tpos <= length - max(2 sd,
  span)` is the model's `d <= cost(j, end)`; `span()` is
  `Stream.span` (from T(s+1) to T(i-1)); the stop rule in integers is the
  Javadoc's; `taken`, `dirtyCount` and `ownBytes` are updated per
  transaction taken; `last` is cleared when the sequence empties; the
  byte budget breaks before a transaction, also past the deadline, as the
  Javadoc and 007-08 say (the record limit, left out of the model).
* `shareFp`'s bounds and the 128-bit arithmetic (`multiplyHigh` on
  non-negative operands, two `divlu` with `u1 < v`); the clamp at `D <<
  16` changes no decision; `u * count` is a long product; no term reaches
  2^49 within the bounds. `ditherFp` is the top 16 bits.
* The pace's inputs at a restart: `DbStarter.rerunTransaction` computes a
  transaction's own bytes from its stored value nodes as `store()` does
  from `TransNodes.valueRecordBytes` (the same `getByteSizeLong` of the
  same nodes, deletes included); D's lists are the stored got-dirty lists,
  which `store()` writes after `handleStillDirtyNodes`; `endOfTrans` takes
  replaced nodes out of the current transaction only, so a list never
  changes after its record; each `TransInfo` is new per transaction.
* `Db.store`'s budget: `fixedBytes` counts the header, end marker, count,
  last byte and padding (48), the values, the own index nodes and 16 bytes
  per got-dirty entry, so a record that takes within `maxBytes` stays
  within the record limit.
* 005-68: `take` gets `getLength()`, which is where the record begins (the
  meta block is written with the record that ends at its position).
* The meta blocks at a start: `refuseOtherNodeSize` reads the last valid
  block before recovery writes, refuses 0 with a `VersioningStreamException`
  and another size with a `StreamFormatException` (both subclasses as
  `Db.start` declares); recovery copies the last valid block, so the
  blocks of a zero fill carry the node size and the startup distance;
  `readLastValidMetaBlock` reads only complete blocks; the fill-out
  template is invalid (last byte 0); `readMetaBlock` checks the magic bytes
  and the version before anything is written (005-40).
* Recovery's torn header: `transHeaderFixBytes` gives a size of at least
  17 and a multiple of 8 for every cut of 1 to 4 bytes (a real size's low
  byte is a multiple of 8, and the fix adds multiples of 256), so the next
  record is aligned; the iterator skips the zero-filled record.
* `StoredTrans.Parser` (005-74): the minimum size, nodes inside the
  declared size, the node size at least 8, the got-dirty count bounded,
  room for the padding; a format other than 5 is a
  `VersioningStreamException`; the node parsers check their own format
  bytes. What it does not check is R6-F1.
* `DbStarter.validateTransactions` (005-75): positions and times strictly
  increase and times are in the 56-bit range, before the rerun.
* T3 on Java's take, by running (`R6/R6SpanProbe.java`): after each of
  6,000 commits in each of six configurations (sd 100, 2,000 and 20,000;
  node sizes 8 and 30; random transactions of 1 to 3 puts or deletes, one
  in twenty of 40, values of 0 to 300 bytes; three restarts each),
  `TransSeq.span()` (Lean's `Stream.span` after the commit) is below 2 sd:
  at most 3,976 of 4,000 and 39,984 of 40,000, never over.
* T2 with the take, by running (`R6/R6RestartSameStreamProbe.java`): 600
  transactions of 1 to 30 operations, a third of them deletes of keys
  that do not exist, node size 8, `setStartupDistance` at the 300th, at sd
  1,000, 30,000 and 1,000,000: the stream with a restart after every 50 is
  the stream without, byte for byte (`SAME`, 2,460,192, 2,134,408 and
  1,195,616 bytes).
* MetaBlock's compatibility claim (`CURRENT_VERSION`'s Javadoc: an older
  version "starts such a stream as before and passes the field on"), by
  running the probe `R6/R6Compat.java` (compiled against the 2026.1 jar,
  run with each jar) on files: created by f5a5f66, 600 transactions;
  started by the 2026.1 jar, 600 more; started again by f5a5f66, with
  every value of both.
* A start after a crash: `R6DecreaseCrashProbe`'s 233 cuts around a
  200 kB record and its meta block (D1) all start with the right data,
  run 20 transactions and start again right.
* `Db.setStartupDistance`: the state is checked first and a refused call
  restores the setting and the in-memory meta block (005-53); the Pub API's
  clamp, 5 to 1000 MB, is inside the core's (R6-F5 concerns the core
  only).
* `KvComparison.compare()` closes the restarted database in a `finally`;
  `comparisonWithRestarted` reads the main stream without a sync, which
  `R6/R6KvComparisonProbe.java` found harmless: 0 of 20 rounds differ,
  as the write buffer serves its unwritten bytes.
* `RecoverableStream.append` now checks the size at `offset` (005-75);
  every caller passes 0.
* `StartupPos`: `evictPos` is written by `releaseForEvict` (called after
  `store()`) and read by nothing; `getStartupPosForEvict` returns the
  startup pos itself, so `set`'s "not immediately available for evict" is
  not kept, but nothing reads the startup pos between `store()` and
  `releaseForEvict()` but `aux.updateStats()`. The same in 2026.1. Dead
  code, no effect.
