## 2. Faults

### R4-F1. A failed batch releases the writer lock before failing the database

* Where: java/src/bergdb/core/Eviction.java, EvictorRun.run, lines 543–547
  and 553–568; core/Db.java, executeInner, lines 1980–2009 and 2026,
  failByEviction, line 2594, and setFailed, lines 2102–2110.
* Intended: docs/levels.md section 3 and EvictorRun's failure comment:
  a batch that throws fails the database as the writer's batch does;
  no later transaction runs on partially changed state or appends more bytes.
* Actual: the catch is outside synchronized(writeLock). A waiting writer can
  acquire that lock and pass the active-state check while the failed evictor
  has not yet published FAILED. That writer need not check the state again.
* Effect: another transaction runs on the state the batch left, and can append
  and return successfully even after the eviction failure has been published.
  The existing fix does fail the database eventually; the remaining fault is
  the transfer of the write lock before that failure, not a missing failure.
* Evidence: R4/R4FailureWindow.java, run against the supplied jar with assertions.
  No production change. Commands and the four output lines are in
  R4/R4FailureWindow.txt. Output includes:
  `next writer returned=true; appended after FAILED=true; stream=384 -> 472`.
  The probe closes its database in finally.
* Forced interleaving (E: eviction thread; W: writer; C: controller):
  1. E holds writeLock and the Eviction monitor at sweep's existing hook,
     line 691. W passes execute's initial readSync block and reaches
     executeInner's writeLock acquisition (1979–1980).
  2. C acquires readSync. E throws from the hook and releases the Eviction
     monitor and writeLock. E's call to setFailed now waits on C's readSync.
  3. W acquires writeLock. E's unlock happens-before W's acquisition, so W
     may see everything the failed batch changed. State is still ACTIVE:
     no FAILED write has happened. W passes line 1984 and its go point,
     and pauses in its transaction's value-created listener.
  4. C releases readSync. E acquires it and writes FAILED (2107). The probe
     observes that volatile write before releasing W's listener latch.
  5. W continues, appends at line 2026 and returns. There is no failure
     publication before the writer lock was transferred, and no state check
     between W's go point and append. The latch also establishes that FAILED
     precedes this append in the probe.
* In 2026.1: no. Its afterLoad ran the sweep on the caller under writeLock;
  there was no eviction thread or this catch outside its lock (Eviction,
  lines 311–328 at that tag).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: catch a batch's exception and publish the database
  failure while still holding writeLock. Release the lock only after FAILED
  is visible; then clear the thread's request/running state as today.

### R4-F2. A batch processes a whole map even past its handle limit

* Where: core/Eviction.java, sweep, lines 647–653 and 659–668;
  core/Cache3.java, clockStep, lines 360–395.
* Intended: docs/levels.md section 7 and Eviction's BATCH Javadoc,
  lines 589–600: at most 4,096 handles (65,536 under pressure), two
  rounds and 2 ms per batch, independent of database size; 009-01
  section 1, target 1, and 010-01 P1 require bounded eviction work.
* Actual: the limits are checked before clockStep. That call traverses
  the whole map under its monitor; it accepts no remaining handle limit
  or deadline. A map has no maximum size. Processing all its pinned
  objects and their values is outside the checks too.
* Effect: one batch's work grows with a whole map, hence with the resident
  set. A writer waits for that work under writeLock, and a reader resolving
  an id in that map waits on its monitor. The probe verifies the work-count
  violation; it does not claim a measured 20 ms pause.
* Evidence: R4/R4BatchBound.java inserts 5,000 distinct, detachable key-node
  versions in the first map, selects an ordinary, non-pressure budget, and
  calls one sweep under writeLock. It reports
  `one sweep released=5000; maps=1`, beyond BATCH=4096. No production
  changes or timing benchmark. Commands/output: R4/R4BatchBound.txt.
* In 2026.1: yes, unbounded eviction work already existed: sweep walked
  the whole resident set (Eviction, lines 376 onwards at that tag). The
  specific constant handle/time limits are new and do not remove it fully.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no format or Pub signature change; choose a resumable traversal
  within a map rather than treating a whole map as the indivisible step.
* Proposed fix, not made: bound handles and pinned-value work inside the
  step, preserve the hand's position within a map, and recheck the deadline
  and waiting writers within that work. Account for partial rounds.

### R4-F3. Startup leaves large values retained in the writer's admission list

* Where: core/Eviction.java, largeValues/largeValueCreated, lines 735–746,
  recordWritten, lines 756–777; core/Db.java, pointerCreated listener,
  lines 913–923 and startup, lines 704–715; core/DbStarter.java,
  rerunTransaction, lines 362–432.
* Intended: Eviction's admission Javadoc, lines 50–52, and 009-02 section
  4.8: values over 1 MiB are not kept once their record is written.
  The resident roots and accounting in Residents and docs/levels.md
  section 7 must describe the database's retained data.
* Actual: startup's replay uses Db.newPutData and its pointer-created
  listener, adding already-written large values and their holders to
  largeValues. Only a later recordWritten drains that list. Startup's
  afterTransaction batch can unswizzle all their leaf pointers, but the
  admission list still strongly holds their payloads and leaf objects.
* Effect: a database reopened for reads retains the replayed large values
  indefinitely, outside the resident count, even after eviction has removed
  every resident value pointer. There need not ever be another write to
  drain the list. This is an additional strong root, separate from the
  documented delayed accounting of dirty nodes.
* Evidence: R4/R4StartupLargeValues.java writes three 1,200 KiB values,
  closes, reopens under a 1-byte Core budget and waits for eviction. Output:
  `resident bytes=430; resident value pointers=0`, while
  `admission list retains=3 entries; payload bytes=3686400`.
  Reflection only reads the private list. Both databases close in
  try-with-resources. Commands/output: R4/R4StartupLargeValues.txt.
* In 2026.1: no. The supplied diff adds largeValues and recordWritten;
  the previous sweep had no admission-list root and selected large values
  from the resident walk after startup.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: apply large-value admission to replayed values
  and empty the pending list at the startup boundary, before normal
  operations. Merely unswizzling a leaf does not remove the list's root.

### R4-F4. A test-schedule resync overwrites concurrent readers' accounting

* Where: core/Residents.java, resync, lines 229–241; called by the
  non-BUDGET schedules in Eviction.afterTransaction, line 339.
* Intended: Residents' synchronization note (61–63), resync's Javadoc
  (224–228) and 009-02 section 4.7: the byte total matches the per-object
  counts; holding writeLock between transactions is the required precondition.
* Actual: resync locks each node separately and collects a local sum, then
  replaces the global atomic totals. Readers do not take writeLock. A value
  loaded into an already-visited holder updates that holder's count and the
  global total, but the final bytes.set(b) drops its global update.
* Effect: the sum of counts and the total diverge, and releasing everything
  can leave a negative total. In this base the resync call is in the forced
  test schedules (VALUES, EVERY, RANDOM), not in ordinary BUDGET eviction
  or Audit.check. It invalidates their accounting under concurrent reads.
  This is a separate reset/load race, not the already-fixed zero-sentinel
  or excessive value-subtraction issue.
* Evidence: R4/R4ResyncRace.java holds the last node's monitor so the
  resyncing writer blocks after counting the first holder. The reader then
  installs a value under the first holder's monitor with valueIn. Resync
  completes after the last monitor is released. Output:
  `total=414; sum of node counts=570; lost bytes=156`, then
  `after releasing every resident: bytes=-156; objects=0`.
  Commands/output: R4/R4ResyncRace.txt. No database is needed by this
  registry probe. A failing Nano regression is in R4/R4Regression.diff.
* Interleaving and edges: W holds writeLock and holder's monitor while
  capturing the old size, then releases holder. R acquires holder, installs
  the value, increments its count and bytes, and releases holder. W later
  replaces bytes from its local sum without revisiting holder. Both atomic
  operations are ordered; W's final replacement erases R's contribution.
  writeLock provides no exclusion against R. The node monitor orders the
  node count, but does not protect the interval through the global reset.
* In 2026.1: yes; Residents.resync (lines 136–162 there) also overwrote
  totals from a walk while readers could add resident data. The counters
  were split by node kind then; the reset race already existed.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: correct individual counted objects with deltas
  under their monitors instead of resetting totals from a snapshot that
  readers can change; handle objects installed or replaced during the walk.

### R4-F5. A budget decrease can settle above budget although the pins fit

* Where: core/Eviction.java, sweep, lines 633–636 and 670–692;
  EvictorRun.run, lines 538–551; setBudget(Db,long), lines 195–199.
* Intended: 005-52, Outcome; Db.setCacheSizeIndicator's Javadoc,
  lines 386–398; docs/levels.md section 7: a decrease evicts in batches
  until resident bytes are at most the new budget, even without another
  call. The exception is state that must stay pinned above the budget.
* Actual: the batch's target is capped by pinnedOfLastRound. Formerly
  pinned nodes may now be clean. A batch can reach that older target,
  refresh the pin estimate during its round, and raise trigger to the new
  pinned bytes plus the watermark gap. The request ends as soon as bytes
  fall below this trigger, even when they remain above high and the actual
  pinned bytes are below high. No further request comes to finish it.
* Effect: an idle database does not give back all memory promised by the
  decrease; it retains detachable data above budget after its thread sleeps.
* Evidence: R4/R4StalePinned.java uses normal commits and Core cache-size
  calls, with read-only reflection of controller state. After 500 puts it
  lowers the budget, raises it, writes a transaction that writes former
  dirty nodes, then lowers it between the old and current pinned sizes.
  Output: `old pinned=3878; current pinned without values=3016`, then
  `budget=3447; after=3703; detachable bytes left=687; trigger=3878`.
  The remaining pinned count is 3703 - 687 = 3016, which fits the budget.
  The eviction thread reaches WAITING with those 3703 bytes still resident.
  Commands/output: R4/R4StalePinned.txt. The database closes in finally.
  A failing Nano regression is in R4/R4Regression.diff.
* In 2026.1: no. Its sweep took every detachable object if still above
  high (takeAll); it had no remembered pinnedOfLastRound target. The new
  API's idle wake was also absent then.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: keep a budget-decrease request active until the
  new high watermark is reached or a fresh round establishes that the
  remaining state cannot fit. Do not use a normal load trigger or an old
  pin count as the completed decrease's goal.

### R4-F6. The audit reports a valid empty-handle cleanup as a bad table entry

* Where: core/Audit.java, check, lines 198–206; core/Cache3.java,
  handles, lines 156–163, and dropIfEmpty, lines 407–412.
* Intended: 009-02 section 4.10 and Audit's handles invariant: detect a
  dead handle in the node table. Normal reads may finish while an audit
  holds writeLock; reader cleanup does not take that lock.
* Actual: handles() returns a snapshot collected under successive map
  locks. Audit then checks each handle's state without its map lock or
  verifying that it is still in the table. A reader can remove an empty
  handle after its map was copied and before the audit examines it.
* Effect: a correct concurrent cleanup produces a false audit failure.
  Audit is test-only; the database does not fail from this finding, but
  concurrent test runs can report corruption that did not occur.
* Evidence: R4/R4AuditSnapshot.java pauses Audit.check after it copied an
  early map into its handles snapshot and before it finishes a later map.
  The reader calls the real dropIfEmpty, then the audit resumes. Output:
  `reader removed its empty handle: dead=true; still in table=false`, then
  `audit result=[handles: the node table has a dead handle of node 107863]`.
  Commands/output: R4/R4AuditSnapshot.txt. The probe's database closes.
* Forced interleaving and edges:
  1. A holds writeLock. handles() acquires the early map, copies LIVE h
     into its local list, and releases that map. A later blocks on a
     different map; the probe uses only these existing monitors as barriers.
  2. R acquires h's map, CASes LIVE to DEAD and removes h with dropIfEmpty,
     then releases the map. It needs no writeLock. The earlier map release
     orders A's snapshot before R's removal; it does not preserve membership.
  3. A finishes its snapshot and observes h's volatile DEAD state at line
     199. It does not reacquire h's map or test current membership. Thus it
     calls fail even though h is no longer a table entry. The probe's barrier
     orders the cleanup before this check, so this is not stale visibility.
* In 2026.1: no; this handles audit is added by the supplied diff.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: validate table membership and state together
  under the handle's map lock; skip handles removed since the snapshot.
  Apply the same coherent observation to checks of a pointer's handle.
