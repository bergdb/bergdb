## 2. Faults

### S1-F1. Two writes of one key in a transaction: the later one can lose
* Where: `pubimp/RwEnvironmentImp.java`, `MapKey.equals`, lines 615 to 638
  at 0b739f3; with `core/Trans.java`, `Builder.build`, lines 299 to 323.
* Intended: an rw-transaction's action, or a w-transaction's builder,
  writes in the order of its calls; `RwEnvironment.delete`: "Deletes a
  database entry if it exists"; `WBuilder.delete`: "The operation deletes
  the database entry with the given key if it exists".
* Actual: `MapKey.equals(Object)` returns false unless its argument is a
  `long[]`, and it is always a `MapKey`; so `kvOps`, a `HashMap<MapKey,
  byte[]>`, never replaces an entry: each `put` or `delete` of a key with a
  suffix (`/a.txt`, a key for bytes or a String) adds one. `createTrans`
  hands them all to `Trans.Builder`, whose `build()` keeps the last put of a
  key, and keeps a put over a delete ("Non-deletes take precedence over
  deletes"). So (a) a put and then a delete of one key commits the put;
  (b) of many puts of one key, the one that wins is the last in the
  `HashMap`'s iteration order: the order of the calls while the bin is a
  list, but not once it is a tree (more than 8 entries in a bin, table of
  64 or more), as a `TreeNode` is linked after its parent in the tree, by
  `System.identityHashCode` for a class that is not `Comparable`.
* Effect: wrong data, silently: (a) an entry that the action deleted is
  still there, with the value the action put before the delete; (b) an
  earlier value of the key is stored instead of the last one.
* Evidence: tests in `PubTesterS1` (`S1/S1-tests.diff`), each fails on
  0b739f3:
  `java -ea -cp build/bergdb.jar bergdb.dev.Unit -c PubTesterS1 -m '^testRwPutThenDelete$'`:
  "rw: put then delete: expected no entry, got 'new'."; `testWPutThenDelete`,
  the same through `c.w().put(..).delete(..).execute()`: "w: put then delete:
  expected no entry, got 'new'."; `testRwManyPutsOfOneKey`, 40 puts of
  `/c.txt` with `v0` to `v39` in one action: "round 0, expected 'v39', got
  'v34'" (the value that wins differs from run to run, by the identity hash
  codes: 'v11' in another run).
* In 2026.1: yes (`MapKey.equals` and `Trans.Builder.build` are as in
  `git show release-2026.1:...`; since the 2017 code).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no for (a) and (b), but see S1-F2 for the order between `kvOps`
  and `objectOps`.
* A fix: `MapKey.equals` compares with a `MapKey` (`key instanceof MapKey`),
  and its hash code stays as it is; then `kvOps.put` replaces the earlier
  operation of the key, the last call wins and the map holds one operation
  a key. A `HashMap` keeps the first key object on a replace, so the puts
  remove the key first, so that the `MapKey`'s key transformation is the
  last call's too (in `indexOps` a delete has none and a put may have one).
  A test of put then delete, delete then put, and 40 puts.

### S1-F2. A String or bytes and an object, or a delete, of one key: the call order is lost
* Where: `pubimp/RwEnvironmentImp.java`, `put(String, Object)` lines 265 to
  291, `delete` lines 224 to 235, `createTrans` lines 399 to 456 at 0b739f3;
  `core/Trans.java`, `Builder.build`.
* Intended: as in S1-F1, the transaction writes in the order of its calls.
* Actual: a key without a suffix (`/d`, an object key) goes to `kvOps` when
  its value is a String or a `byte[]`, and to `objectOps` when it is an
  object or a delete. `createTrans` adds `kvOps` to the builder first, then
  `objectOps`; `build()` keeps the later put, and a put over a delete. So
  `put("/d", "new")` then `delete("/d")` commits "new", and `put("/e",
  object)` then `put("/e", "text")` commits the object. This holds with
  S1-F1 fixed too: the two maps are separate.
* Effect: wrong data: a deleted entry stays; a value written last is
  replaced by an earlier one.
* Evidence: `PubTesterS1.testRwStringAndObjectOfOneKey`: "String put, then
  delete: expected no entry, got 'new'."; `testRwObjectThenString`:
  "object put, then String put, expected 'text', got 'bergo ... key /e name
  object'" (the object's bytes).
* In 2026.1: yes.
* Design choice: yes, small: whether a key holds one operation in the
  environment whatever its kind (one map, or a put to one map removing the
  key from the other); and S1-F7's question, whether a String or `byte[]`
  belongs at an object key at all.
* A fix: `put` and `delete` remove the key from the other map, so that each
  key has one operation, the last; for the index entries of a String or
  `byte[]` put at an object key, see S1-F7.

### S1-F3. An rw() on a connection changes its frozen lookup time
* Where: `pubimp/ConnectionImp.java`, `getInternal`, lines 270 to 279 at
  0b739f3, called by `RwEnvironmentImp.get` (line 74) and `getInternal`
  (line 89).
* Intended: `Connection.freezeLookupTime()`: "The lookup time of this
  Connection will not change until setLookupTime() is called or this method
  is called again."
* Actual: the rw-transaction's reads go through the connection's
  `getInternal`, with the connection's `GetData`; at the first, with lookup
  time `Long.MAX_VALUE`, `getInternal` sets the frozen connection's lookup
  time to the actual lookup time of that read, the latest. A w-transaction
  of an object in a directory with an index does the same (`indexEntries`'
  read of the previous value).
* Effect: wrong answers for the reader that froze its time: after `rw()`,
  its reads see a later state than the one it froze, so a set of reads meant
  to be consistent mixes two states. The connection's `transactionInfo()`
  then also names the rw's last read (the same `GetData`).
* Evidence: `PubTesterS1.testRwKeepsFrozenLookupTime`: freeze, read "1",
  another connection writes "2", the frozen read gives "1", an `rw()` whose
  action reads another key, then the frozen read: "frozen after rw,
  expected '1', got '2'." `testObjectPutKeepsFrozenLookupTime`, the same
  with `c.put` of an object in a directory with an index in place of the
  `rw()`: "frozen after an object put, expected '1', got '2'.";
  `testRwKeepsTransactionInfo`: `get("/a.txt")`, then an `rw()` that reads
  `/b.txt`, then `transactionInfo()`: "after rw, expected 17937365932110000,
  got 17937365932110001" (the time of `/b.txt`'s put, not `/a.txt`'s).
* In 2026.1: yes.
* Design choice: no.
* A fix: `RwEnvironmentImp` reads through a `GetData` of its own (and a
  method of `ConnectionImp` that does not touch the frozen time), so that an
  rw-transaction leaves the connection's read state as it was.

### S1-F4. Index work reads the indexes before the read time: a new or deleted index is missed
* Where: `pubimp/RwEnvironmentImp.java`, `indexEntries` lines 318 to 336
  (the map read at 320, the virtual hash at 321, the first read of a
  previous value at 336) and `createTrans` line 402 at 0b739f3; `core/Db.java`,
  `stmCheckConflicts`, lines 2311 to 2317.
* Intended: `IndexManager`'s design note (at its end): the directory's
  virtual read hash is added "even when directory has no indexes. We still
  have a readKeyHash for the directory and can get transaction rerun in
  case an index is added while Connection.set(String, Object) is being
  executed." `DatabaseImp.deleteIndexInternal`, after
  `ensureDeletingState`: "After this method returns, there should be no more
  index entries added to the index directory". `Action.run`: the action runs
  again when what it read was modified before its writes were applied.
* Actual: `indexEntries` reads the directory's indexes from
  `IndexManager`'s map and adds the directory's virtual hash to the read
  set, and `stmCheckConflicts` checks the hash against the transaction's
  read time. But that time is not before the map read unless the action read
  something first: (a) when no read is made at all (no index for the
  directory, so no read of the previous value; an action that read nothing,
  or a w-transaction), `readTime` stays -1, `createTrans` gives the core
  transaction the lookup time `Long.MAX_VALUE`, and
  `KeyModSet.modifiedAfter(Long.MAX_VALUE, hash)` is never true; (b) when
  the first read is `indexEntries`' own read of the previous value, after
  the map read, the read time is that read's, later than the map read. So
  an index registered (`createIndex`: the map, then `storeIndex`'s commit
  of the directory's virtual hash) or deleted (`ensureDeletingState`: the
  map, then `storeIndex`) after the map read and before that time, or ever
  in case (a), does not refuse the transaction.
* Effect: wrong answers for good. (a) An index made and built meanwhile
  misses the object: it is in the database and the index's iterators never
  return it. (b) An index deleted meanwhile gets an entry written after its
  deletion job has run; a new index of the same name then holds it, and
  returns the object twice, once by an entry of the old index's
  definition. The window runs from `indexEntries` to the write lock,
  which includes the warm-up and the wait for the lock, when the index's
  registration, its build's steps or its deletion's transactions take it.
* Evidence: tests in `PubTesterS1` that run the steps of
  `RwTransaction.executeRw` for `WTransaction.execute()` one by one
  (`RwEnvironmentImp.put`, `indexEntries`, `createTrans`, `Db.execute`),
  with the other thread's work between two of them, as it can run while
  this thread waits for the write lock or between its two reads:
  `testObjectPutWithoutReadsMissesNewIndex`, (a), an index on the directory
  made and built between `createTrans` and `Db.execute`: no
  `RerunException`, and "the objects in the index 'from', expected 1, got
  0."; `testObjectPutWhileIndexIsDeleted`, (b), the index deleted
  (`deleteIndex("from").join()`) between the map read and the read of the
  previous value (inside a subclass's `getActiveIndexesForDir`), then a new
  index "from" on another field: "the objects in the new index 'from',
  expected 1, got 2." The contrasts pass on 0b739f3:
  `testObjectPutWithReadIsRefused` (a read before the steps: the creation's
  interleaving is refused with a `RerunException`) and
  `testObjectPutAfterIndexIsDeleted` (the same deletion and new index
  without the interleaving: 1).
* In 2026.1: yes.
* Design choice: no.
* A fix: `indexEntries`, when no read has set the read time yet, takes the
  database's lookup time (`Db.lookupTime(Long.MAX_VALUE)`) before its first
  `getActiveIndexesForDir` and makes it the read time (`firstRead` false),
  so that the previous values are read at it too. `createIndex` and
  `ensureDeletingState` change the map before `storeIndex` commits, under
  `IndexManager`'s lock, so a map read that misses the change is followed
  by a commit of the directory's hash after that time, which refuses the
  transaction, and one that sees it needs no refusal.

### S1-F5. DatabaseBuilder.cryptoKey(CryptoKey.NULL) after a key keeps the key
* Where: `pubimp/DatabaseBuilderImp.java`, `cryptoKey`, lines 79 to 85 at
  0b739f3.
* Intended: `DatabaseBuilder.cryptoKey`: "@param cryptoKey The crypto key to
  use or CryptoKey.NULL to not use any encryption."
* Actual: `if (!cryptoKey.isNull()) this.cryptoKey = cryptoKey;`: NULL is
  ignored, and a key given before stays. (`cryptoKey(null)` throws a
  `NullPointerException`; the Javadoc says nothing of null.)
* Effect: a database started with "no encryption" after a key was set on
  the builder (a builder set up from a configuration, then overridden) is
  encrypted with that key; a later start without the key is refused with
  `BadCryptoKey`. No data is lost, and the key is known to the application.
* Evidence: `PubTesterS1.testCryptoKeyNullAfterKey`: a builder with
  `cryptoKey(CryptoKey.generate()).cryptoKey(CryptoKey.NULL)` on a
  `MemoryStream`: "the stream's first bytes, plain text without encryption,
  expected 'berg', got 'q>...'".
* In 2026.1: yes.
* Design choice: no.
* A fix: `this.cryptoKey = cryptoKey.isNull() ? null : cryptoKey;`, and an
  `IllegalArgumentException` for null, as `dir(null)` has.


### S1-F6. CryptoKey has equals() and no hashCode()
* Where: `pub/CryptoKey.java`, `equals`, lines 152 to 160 at 0b739f3.
* Intended: `Object.hashCode()`'s contract, which a public class of the
  Pub API that overrides `equals` keeps: equal objects have equal hash
  codes.
* Actual: `equals` compares `serialize()`; `hashCode` is `Object`'s, by
  identity.
* Effect: an application that keeps keys in a `HashSet` or a `HashMap` (a
  key ring by key) does not find a key equal to one it holds, such as one
  parsed again from its serialized form. Nothing in BergDB itself does.
* Evidence: `PubTesterS1.testCryptoKeyHashCode`: `k.equals(parse(k.serialize()))`
  holds, and "a HashSet finds the equal key, expected true, but was false."
* In 2026.1: yes.
* Design choice: no.
* A fix: `public int hashCode() { return serialize().hashCode(); }`, or
  `Arrays.hashCode(keyData)` with name and algorithm.

### S1-F7. A String or byte[] at an object key in an indexed directory breaks the index
* Where: `pubimp/RwEnvironmentImp.java`, `put(String, Object)` lines 277 to
  281 (a String or `byte[]` goes to `kvOps`, with no index work) and
  `indexEntries` lines 334 to 345 (the previous value parsed as a
  `DbObject`) at 0b739f3.
* Intended: `Connection.put`, `RwEnvironment.put(String, Object)`: "Sets
  the key-value entry with the given key to the provided object", "If an
  entry with the given key already exists, it is overwritten"; `WBuilder.put`:
  "Special handling is provided for object of type byte[] and
  java.lang.String", with no limit to keys with a suffix. An index's build
  skips values at object keys that are not objects (`PubTesterIndex.
  testNonObjects2`), so such values are expected in an indexed directory.
* Actual: (a) a String or `byte[]` put over an indexed object leaves the
  object's index entries: only `objectOps` read the previous value and
  delete its entries; (b) an object put over a String or `byte[]` at an
  object key in an indexed directory parses the previous value as a
  `DbObject` and throws `DataFormatException`, at every rerun.
* Effect: (a) the index names a key whose value is not an object, and its
  iterators throw `ObjectCreationException` when they reach it: queries by
  the index fail until the key holds an object again; (b) the object can
  never be put at that key while the index exists, unless the key is
  deleted first.
* Evidence: `PubTesterS1.testStringOverIndexedObject`: an index on
  `/payments/`, an object put at `/payments/1`, then a String put there; the
  index's iteration: "bergdb.pub.ObjectCreationException: bytes too short, 4
  ukey=/payments/1". `testObjectOverStringInIndexedDir`: a String put at
  `/payments/2`, then an object put: "bergdb.pub.DataFormatException: bytes
  too short, 4 For ikey: '/dpayments/-2'."
* In 2026.1: yes.
* Design choice: yes, small: whether a String or `byte[]` at an object key
  is allowed at all (refused, as an object at a key with a suffix is), or
  allowed and kept out of the indexes.
* A fix, if allowed: a String or `byte[]` put at an object key goes through
  `objectOps` as a value that is not an object, so that `indexEntries`
  deletes the previous object's entries and writes none; and `indexEntries`
  treats a previous value that is not a `DbObject`
  (`Entries.isProbablyDbObject`, as the build does) as no previous object.

### S1-F8. A byte[] value is shared with the caller: a change of the array changes the value in memory
* Where: `pubimp/RwEnvironmentImp.java`, `put(String, Object)` line 279
  (`setBytes(ikey, (byte[]) object)`, no copy) and `createTrans` (the array
  to `Trans.Builder.put`, which keeps it in the `Kv`, and the value node
  keeps it); `pubimp/KvToObjectImp.java`, `createObject`, line 68
  (`byte[].class`: `result = (TYPE) value`, the value node's own array) at
  0b739f3. The same path serves `Connection.put`, `WBuilder.put` and
  `Connection.get`.
* Intended: a value is what was put at the commit, at every read of its time
  (levels.md, section 1, Level 0: a multiversion map; section 7: "the
  records, D and the answers are those without eviction"); `Connection.get`:
  "Use byte[].class to get the raw bytes as stored in the database". No
  Javadoc tells the caller to leave the array alone after a put or a get.
* Actual: the database keeps the caller's array as the value in memory,
  and hands its own array to every `get(key, byte[].class)`. The record in
  the stream is serialized at the commit, with the bytes then.
* Effect: wrong answers that depend on the cache: after the caller changes
  the array it put (a reused buffer), or one a get returned, reads return
  the changed bytes while the value is in memory, and the committed bytes
  after its eviction or a restart; a value over 1 MiB, which leaves memory
  when its record is written, is not affected. Reads at a fixed lookup time
  give two answers.
* Evidence: `PubTesterS1.testByteArrayAliasing`: an rw-transaction puts
  `{1, 2, 3}`, the caller sets its array's first byte to 9; and a get's array
  set to 9: "expected '1 1', got '9 9'." `testByteArrayPutAliasedAgainstStream`:
  the same put and change, a read, then a restart on a copy of the stream:
  "the value's first byte before and after a restart, expected '1 1', got
  '9 1'."
* In 2026.1: yes (`KvToObjectImp`, `Trans.Builder.put` and
  `RwEnvironmentImp.put` as at 0b739f3, but `checkHash`).
* Design choice: yes, small: copy at the API's edge (a copy at each put and
  at each `get(.., byte[].class)`: allocation and time on every byte[] put
  and get), or document that the arrays are the database's (and the C
  clone's API, if it has the same).
* A fix: `setBytes` stores `value.clone()`, and `createObject` returns
  `value.clone()` for `byte[].class` (and the `Object.class` path for
  values that are bytes); the core API keeps its arrays as they are, with a
  line in `Trans.Builder.put`'s and `Db.getOne`'s Javadoc.

### S1-F9. freezeLookupTime(), then exists(): the frozen time is the read before, or -1
Outside this review's files (the connection and its time, H2a's), met
while checking S1-F3; reported here as it is verified.
* Where: `pubimp/ConnectionImp.java`, `getBytesAtLookupTime`, lines 173 to
  179 at 0b739f3, which `exists` (line 202), `IndexManager` (line 517) and
  `UseIndexBuilderImp` (line 638) call.
* Intended: `Connection.freezeLookupTime()`: "After this method has been
  called, the actual lookup time of subsequent read operations will be
  constant." `setLookupTime()`'s default: Time.MAX, the latest state.
* Actual: `getBytesAtLookupTime` sets the frozen time from
  `getData.actualLookupTime` before its read, so from the read before it,
  where `getInternal` does so after its own read. After
  `freezeLookupTime()`, an `exists()` as the first read freezes the time of
  the connection's previous read, or -1 if there was none, and reads itself
  at the time asked for.
* Effect: (a) with no read before, every later read of the connection
  throws `LookupTimeNotAvailableException` ("Cannot lookup at time -1")
  until `setLookupTime()`; (b) with a read before, the frozen reads are at
  that older time, while the `exists()` that began them saw the latest: the
  set of reads that the freeze was to make consistent is not.
* Evidence: `PubTesterS1.testFreezeThenExists`: a put by another
  connection, `freezeLookupTime()`, `exists("/a.txt")`, `get("/a.txt")`:
  "expected 'true 1', got 'true bergdb.pub.util.LookupTimeNotAvailableException:
  Cannot lookup at time -1 ...".
* In 2026.1: yes.
* Design choice: no.
* A fix: in `getBytesAtLookupTime`, update the frozen time after the read,
  as `getInternal` does.

## 3. Doubts

* **D1. `rw()` can throw `LookupTimeNotAvailableException`.** An action
  reads every key after its first at the first read's actual lookup time
  (`RwEnvironmentImp.readTime`). With a retain duration, an action that runs
  longer than it, while reclaim cuts, gets the exception from a later read;
  it leaves `rw()`, which does not run the action again, and `Connection.rw`'s
  Javadoc names only `DbFailedException` (the exception is an
  `IllegalArgumentException`, not a `DbException`). Not verified: a cut during an
  action needs reclaim's iterations (stream growth of twice the startup
  distance, 5 MB at least through the Pub API) and a clock moved past the
  retain duration; a test with a `TestClock` and about 20 MB of puts would
  show it. Whether the STM should run the action again then (the read set is
  too old in any case) is the fix's question.
* **D2. A refused transaction stays referenced.** `Db.executeInner` calls
  `x.begin(t)` before `stmCheckConflicts(t)`, so after a `RerunException`
  `x.trans` holds the refused `Trans`, with its values, until the next
  transaction begins; `x.end()` is not called. Seen by reading; no effect
  found but memory held between transactions (`x.transNodes` is empty, and
  `x.nextVpos` is what the next `begin` sets again). A heap check after a
  refused large transaction would show it; harmless as far as read.
* **D3. `RwEnvironment.exists` throws where `Connection.exists` returns
  false.** For a key of a bad format, `RwEnvironmentImp.exists` calls `get`,
  whose `PubKeys.u2i` throws `IllegalArgumentException`; `Connection.exists`
  catches it and returns false. `ReadInterface` is meant to make the two
  interchangeable ("composable methods for reading data that can be used
  both for read-only operations and for read-write transactions"). Not run;
  a test of the two calls would show it. Neither Javadoc promises the bad
  format's case. (A null class: `KvToObjectImp.createObject` throws
  `IllegalArgumentException` for both, as `Connection.get` says.)
* **D4. Five JMX operations wait as long as a stalled writer.**
  `getStreamSize`, `getStartupDistance`, `getTransactionCount`,
  `getKvCount` and `setStartupDistance` take `Db.writeLock`; while the
  storage does not return (a disk that stalls: the write buffer full, a
  writer waiting in `store()` with the lock), they wait too, so the monitor
  cannot show a database that hangs on its disk. Probe `S1/JmxProbe.java`,
  "stalled storage" (a `FaultStream` that holds its appends): "writer state:
  WAITING", and those five "HANGS" (2 s limit each); the others answer.
  Not registered as a fault: `DbMonitor`'s Javadoc says that "Many get
  methods acquires DB.writeLock", and nothing promises an answer during a
  stall. A fix, if wanted: the getters read volatile copies (the stream
  length, the counters, the setting) without the lock.
* **D5. The keystream depends on the key and the position only.** The
  nonce is the key data's first 8 bytes, fixed for the database's life, and
  byte p is encrypted with keystream byte p. Bytes that a crash loses from
  the tail are written again at the same positions with other plain text,
  under the same keystream; a copy of the lost bytes (a disk image taken
  before, blocks the file system freed) then gives the XOR of two plain
  texts. Bytes that survive are never rewritten (recovery appends). Not a
  fault by any promise: no Javadoc states what the encryption protects
  against. A per-start nonce in the meta block would need a format change.
  Reasoned from the code, not probed.

## 4. Checked and right

* The STM's check: `stmCheckConflicts` and `stmRecordKeys` run under
  `writeLock`, the check before the go point and the record after
  `dbClock.transactionEnd()`; a reader's actual lookup time is set before its
  Dag read (`getOneInternal`) and is below any running transaction's time,
  so a write after the read time is in `KeyModSet` when the reader commits.
  Key transformations update `writeKeyHashes` before they are recorded.
* `KeyModSet`: the four bins and their rotation keep every write after the
  oldest bin's first time (a dropped bin holds only times at or before it);
  a read time before it is "modified"; `setFirstTime` (005-70) makes a read
  time before the last recovered commit "modified" and one at it covered,
  and is called after `DbStarter` has validated the times. Hash indexes are
  never negative (005-21).
* The retries, against 005-81, section 2.5: sleeps of 10 ms doubling to
  10,240 ms and staying there, no limit of attempts or time, the backoff per
  call; the RW reset (everything, outputs cleared) and the W reset (index
  information only); an interrupt in the sleep sets the flag again and
  throws `DbException` with the transaction not run (levels.md, section 3).
  A refused transaction changes nothing in the Dag (D2 aside).
* An exception from the action leaves `rw()` at once; nothing is committed;
  the environment is closed in a `finally` (005-12), so later calls throw
  `IllegalStateException`; the outputs are those of the committed run only,
  cleared before each rerun. An action that never ends holds no lock and no
  pin: `close()` does not wait for it, and its later reads or its commit
  throw as the database stops.
* The read set: every `RwEnvironment.get` and `exists` adds the key's hash
  before it reads; the first read is at the latest time and fixes the read
  time for the rest, so the action reads one snapshot. An action that reads
  nothing has no read set (S1-F4's directory hash aside). Index work after a
  read of the action's is refused when the directory's indexes change after
  that read (`testObjectPutWithReadIsRefused`).
* The cipher (`SalsaStream`, `Salsa`): byte p of the stream is the plain
  byte XOR keystream byte p of (key, nonce), for appends of any size, across
  new `SalsaStream`s after a cut at any byte of the tail (the constructor
  reads the partial last block and moves the keystream to the length), and
  for reads at any position and length; a wrong key reads other bytes;
  `getLength` is the underlying length after every append. Probe
  `S1/SalsaCutProbe.java` (bergdb.stream, before the jar on the class path;
  3,000 rounds of random keys, sizes and cuts): "rounds 3000, faults 0". A
  cut at the front is a file start (multiples of 200,000 in `FileStream`,
  of 1,000,000 in `MemoryStream`), so a read's 64-byte block never starts
  below the first position. Only the storage thread appends (the
  `BufferedStream` consumer), so `encrypt` and `appendBuffer` need no lock;
  readers share `decrypt` under `readLock`.
* A start of an encrypted database through the Pub API whose stream is cut
  at every byte of the last 300 and of 200 on each side of the meta block at
  200,000 (702 cuts): a wrong key throws `BadCryptoKey` and leaves the stream
  as it was; then the right key starts, has every transaction that ends at
  or before the cut and none after it, takes a put, and starts again with
  it. Probe `S1/CryptoCutProbe.java` (bergdb.pubimp): "cuts 702, faults 0".
* The key's path: `checkCryptoKey` before any directory is opened (015-06);
  the nonce is the key data's first 8 bytes, the key the next 32; a wrong
  key, none, or a key on a stream that is not encrypted is refused with
  `BadCryptoKey` by `recover()` before anything is written (005-40;
  `refuseIncompleteCreation` reads only and sees no meta block's magic);
  `created.txt` is written only after a start succeeds or for a new
  database; a failed start closes the streams.
* JMX: every operation of `Jmx.DbMonitor` on a running, a failed (a
  storage error, then a sync) and a closed or stopped database (probe
  `S1/JmxProbe.java`, bergdb.core): none hangs; on a database that is not
  active `setStartupDistance` throws `DbFailedException` or
  `DbStoppingException` and changes nothing, the other setters only set
  their values, the getters answer. `setRetainDurationInDays` computes in
  long (005-20). The descriptions match the code. (`Jmx.Speed.stop()` before
  `registerAndStart()` throws a `NullPointerException`; a tool's method,
  with no promise.) A storage that stalls: D4.
* `DbStarter`: no part of the key's path; a wrong key never reaches it
  (`recover()` refuses first), and its refusal of an empty transaction list
  means `KeyModSet.setFirstTime`'s last transaction always exists.
* 005-45: `SalsaStream.getLength()` counts the appends;
  `WTransaction.sync(SyncLevel)` waits for its own position.

## 6. Shared fields (R1, R2, R4 and R5; 016-07, section 3)

* `KeyModSet.bins` and each `Bin`'s arrays (KeyModSet): written by the
  committing thread under `Db.writeLock` (`stmRecordKeys`), by the start
  under `writeLock` and `readSync` (`setFirstTime`); read by the committing
  thread under `writeLock` (`stmCheckConflicts`). The monitor orders them.
  Test: none of its own (the STM tests in `PubTesterOutput` and `DbTester`).
* `SalsaStream.decrypt` (a `Salsa`, its `input`, `output`, `x` and
  `appendPos`): read and written by every reader under `readLock`. Test:
  none concurrent.
* `SalsaStream.encrypt` and `appendBuffer`: written by the start thread in
  the constructor, then only by the `BufferedStream` consumer thread
  (`flushToStream`); the thread's start orders the constructor's writes
  before its use. Test: none.
* `SalsaStream.stream`, the key and the nonce: final, or copied into the
  final `Salsa` objects before publication.
* `Reclaim.retainDuration`: written by any thread (the Pub API, JMX),
  volatile; read by the writer. A stale value for one transaction is
  harmless: each cut keeps the duration in force when it was decided.
* `Jmx.Speed.stop` and the four speeds: volatile, written by the Speed
  thread (the speeds) and by `stop()` (`stop`), read by JMX threads;
  `thread` under `synchronized`. Harmless if stale for one round.
* `RwEnvironmentImp`, `RwTransaction`, `ConnectionImp` and its `GetData`:
  one thread each by the API's rule (`Connection`'s class Javadoc); not
  shared. The `output` map is handed to the caller's thread by return.
