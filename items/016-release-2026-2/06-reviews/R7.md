### R7-F1. A reclaim step that rewrites old values beyond the value limit fails the database, at every restart
* Where: `core/Reclaim.java`, `step`, lines 435 to 560 at f7974d3 (the scan's
  stop condition, about 460 to 468, and `db.execute(t)` at 558, which catches
  only `RerunException`); `core/Db.java`, `executeInner` (`checkSize(t)` at
  1975, `checkSize` at 2146).
* Intended: docs/levels.md, section 3: after the go point "nothing refuses
  the transaction", and the database fails only when "the environment or a
  bug" throws; a transaction that `checkSize` (005-17) would refuse is refused
  before its go point and "the database goes on". Section 6: a step scans
  "at most about 16 KB of KVs" and rewrites each live value stored before
  pCut. Every value that the user committed was within
  `StoredTrans.valueLimit()`.
* Actual: a step adds KVs to its scan until their size passes the step's
  write size (10 to 16 KB), so the last KV can be a value of any size, and the
  step rewrites it together with the old values before it and the iteration's
  row (`CURRENT_KEY_NAME`), in one internal transaction. When the value nodes
  together pass `valueLimit()`, `checkSize` throws a `DbException`. The step
  runs inside the go point of the user transaction that allowed it
  (`Reclaim.transactionCompleted`), `step` does not catch it, and
  `executeInner`'s `catch (Throwable)` fails the database (`fail()`).
  The iteration's row is in the stream, so after a restart the iteration
  resumes at the same key and the first user commit fails the database again.
  A retain duration of forever does not stop it: an iteration in progress
  goes on (`if (current != null)` in `transactionCompleted`).
* Effect: a database that fails when it should not, and fails again at the
  first commit after every restart: with reclaim on, a database that holds a
  value whose node is within about 16 KB (one step's scan) plus the row's
  size of `valueLimit()` cannot take commits again. The failing commit itself
  is in the stream (its record was appended before the step), although the
  call threw. With the real limit, `valueLimit()` is 7/8 of
  `Integer.MAX_VALUE - 8`, about 1.88 GB, so the value must be within about
  16 KB of 1.88 GB: rare, but the Core accepts it. The same path can also
  pass the record limit in `store()` (the step's touch makes index nodes dirty
  besides the values), which throws after the go point as well (not probed).
* Evidence: probe `R7/R7StepSizeProbe.java` (package `bergdb.core`; lowers
  `StoredTrans.recordLimit` to 100 kB as `StoredTrans`'s own test does, so
  `valueLimit()` is 87,500). Ten values of 4,000 bytes under `/a/`, then
  `/b` alone with a node of 86,500 bytes (accepted), then small puts 50 ms
  apart with a retention of 1 s and a startup distance of 2,000. Command (in
  `java/`, the probe compiled to `../../probe-classes`):
  `java -ea -Dslack=1000 -cp ../../probe-classes:build/bergdb.jar
  bergdb.core.R7StepSizeProbe`. Output (`R7/R7-F1-output.txt`): "FAULT at put
  399: The transaction at time 215500000 failed after it began", cause
  "DbException: The transaction is too large: its values and keys take 90596
  bytes in the stream, more than 87500." Then a restart on a copy of the
  stream with the builder's default retention (forever): "AFTER RESTART
  (retain forever), put 0 fails again", the same cause. With `/b` at 77,500
  bytes (`-Dslack=10000`) no failure: 12 iterations, cuts made.
* In 2026.1: yes. The same probe on `release-2026.1` (built in a second
  clone): "FAULT at put 509", the same cause, and the same failure after the
  restart.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: a design choice, small: how a step bounds its values. No format or
  API change.
* A fix, proposed: the step's scan stops before a KV whose value would make
  the step's value nodes, with the row's, pass `valueLimit()` (and a margin
  for the touch's index nodes, as `checkDirtyNodes` reserves for a user
  transaction), unless it is the first KV of the step; a value that alone
  with the row passes it is rewritten in a step of its own, which needs the
  row's own share kept out of `valueLimit()` (for example a user value limit
  a few kB below the record's, so that reclaim's step always fits). A test in
  `Reclaim.Tester` from the probe.

### R7-F2. A value transformation's result is not size-checked: one above the value limit fails the database
* Where: `core/Db.java`, `executeInner` (`checkSize(t)` at 1975, before the
  go point, sees the input value) and `putKvs` (`kv.transformValue` at
  2391, after it); `StoredTrans`'s record check (line 673) then throws in
  `store()`. `core/ValueTransformation.java`, its Javadoc (a key transformation's
  result is likewise unchecked; not probed).
* Intended: docs/levels.md, section 3: "Before [the go point], everything
  that may refuse the transaction is checked ...: ... the size of the
  transaction (005-17) ... A refused transaction leaves the database as it
  was, and it goes on." `ValueTransformation`'s Javadoc asks only that the
  transformation "must not throw any exception"; it says nothing of the
  size of its result.
* Actual: `checkSize` adds up `kv.getValue()`, the input of the
  transformation. The transformation runs after the go point; its result
  is not checked, and a result that does not fit the record makes
  `store()` throw "The record of the transaction would take ... bytes, more
  than the limit", which `fail()` turns into a failed database. The same
  value given directly is refused before the go point and the database goes
  on.
* Effect: a database that fails when it should not: a Core API transaction
  whose transformation returns a value above `StoredTrans.valueLimit()`
  (about 1.88 GB with the real limit) fails the database instead of being
  refused. The Pub API does not use value transformations (only
  `Reclaim.step`'s row does, with a small value), so only Core API users
  meet it.
* Evidence: probe `R7/R7TransformSizeProbe.java` (record limit lowered to
  100 kB as in F1): a put with `new byte[0]` and a transformation that
  returns 120,000 bytes. `java -ea -cp ../../probe-classes:build/bergdb.jar
  bergdb.core.R7TransformSizeProbe`. Output (`R7/R7-F2-output.txt`): "FAULT:
  The transaction at time 2 failed after it began", cause "DbException: The
  record of the transaction would take 120112 bytes, more than the limit,
  100000 (bergdb 005-17)."; the next put is refused with
  `DbFailedException`.
* In 2026.1: yes; the same output on `release-2026.1`.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: a design choice between two small ones; no format or Pub API
  change.
* A fix, proposed: either `ValueTransformation`'s Javadoc says that the
  result must fit `valueLimit()` with the transaction's other values, or
  the database fails (as for an exception), which keeps the code; or
  `putKvs` refuses before the go point by running the transformations
  first (they read the state before the transaction, which is available
  then), which changes when they run. The first is enough for 2026.2.

### R7-F3. `execute()` can be refused with `LookupTimeNotAvailableException`, which neither its Javadoc nor docs/levels.md lists
* Where: `core/Db.java`, `executeInner`, `warmup(t)` at line 1977, before
  the write lock; `warmup` (2338 to 2345) reads at
  `dbClock.lookupTime(Long.MAX_VALUE)` through `getOneInternal`, whose
  `readFailed` turns a read that a cut overtook into a
  `LookupTimeNotAvailableException` (`expiredIfReadBelowCut`).
* Intended: `execute`'s Javadoc lists what refuses a transaction
  (`IllegalDbStateException`, `DbFailedException`, `RerunException`, the
  stream exceptions while stopping, `InternalDataException`, `DbException`
  for the top node ordinals); docs/levels.md, section 3, lists the checks
  before the go point (the STM, the ordinals, the size, the index nodes, the
  clock), and section 6 says that a *read* that a cut overtakes expires.
  Neither says that a transaction can be refused because its warmup read
  expired.
* Actual: the warmup runs before the lock and reads at the latest time when
  it starts. Since 009 (handles, no pointer locks) other writers commit
  while a warmup read waits on the storage; if the wait lasts longer than
  the retain duration and a cut overtakes the warmup's time, the read meets
  the cut bytes and `execute()` throws `LookupTimeNotAvailableException`
  ("The lookup at time ... expired while it ran ... Retry with a later
  time."), an `IllegalArgumentException`. Nothing is changed and the
  database goes on, so a retry succeeds.
* Effect: a wrong, undocumented exception from a write: the transaction is
  refused (not run) with an exception that speaks of a lookup time; a
  caller that handles only the listed ones sees an unexpected
  `IllegalArgumentException`. No data is lost and the database goes on. It
  needs a storage read stalled for longer than the retain duration (at
  least 1 s) while other writers commit and a cut is made: a slow disk or a
  long pause with a short retention.
* Evidence: probe `R7/R7WarmupExpiryProbe.java`, which forces the
  interleaving: a stream wrapper makes one thread's reads wait (outside the
  `MemoryStream`'s monitor). A database with `/old/x` behind its startup
  pos is restarted on the wrapper, so `/old/x`'s nodes are not resident;
  thread W runs `execute(put /old/x)`, and its warmup's read at stream pos
  296 is held. The main thread commits puts, 50 ms of test clock apart,
  retention 1 s, until the stream's first position is past 296 and the first
  available lookup time past W's read time (1,484 puts); then W's read goes
  on. `java -ea -cp ../../probe-classes:build/bergdb.jar
  bergdb.core.R7WarmupExpiryProbe`. Output (`R7/R7-F3-output.txt`): "the
  held transaction: bergdb.pub.util.LookupTimeNotAvailableException: The
  lookup at time 160000000 ... expired while it ran", "database active:
  true".
* In 2026.1: unknown. The warmup code is the same, but the probe compiled
  for `release-2026.1` (its `SyncLevel` import removed: the class was in
  `bergdb.core` then) does not get past the held read within 60 s: the
  writer there appears to wait behind the held reader (2026.1 still had
  `PointerLocks`, gone with 009), so the interleaving does not arise in the
  same way; not analysed further. So likely new in 2026.2 in practice.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no format or API signature change; a small choice of which side.
* A fix, proposed: in `warmup`, catch `LookupTimeNotAvailableException` and
  ignore it (the warmup only loads nodes; the transaction reads again under
  the lock at the latest time), or read the warmup at the time read again
  just before each key; or list the exception in `execute`'s Javadoc and
  in docs/levels.md, section 3. The first is a two-line change with the
  probe as its test.

### R7-F4. A transaction that runs when `stop()` comes is committed, but `execute()` throws `DbStoppingException` from reclaim's step
* Where: `core/Db.java`, `executeInner`: `reclaimTransactionListener.
  transactionCompleted(t)` at 2050, after `store()`, inside the `try` whose
  `catch (Throwable)` calls `fail()`, which throws the exception as it is
  while stopping (2080); `core/Reclaim.java`, `step`: `db.getMany(g)` at
  474 (and `db.execute` of the step and of `storeTable`), each of which
  checks the state (`assertDbStateIsActive`, `Db.java` 1674).
* Intended: `execute`'s Javadoc: "@throws IllegalDbStateException If
  start() has not been called or database is stopping", that is, the call
  was refused; `stop()`'s Javadoc and 005-35: the close waits for a running
  transaction, which "completes and is written"; `fail()`'s Javadoc: while
  stopping, "a failure is the stop's" (a storage that the stop closed). After
  the go point nothing refuses a transaction (docs/levels.md, section 3).
* Actual: when `stop()` (or `close()`) sets STOPPING while a user
  transaction holds the write lock, after its record is appended, the
  transaction's `transactionCompleted` runs a reclaim step or stores the
  table; their reads and internal transactions see STOPPING and throw
  `DbStoppingException` ("Cannot call getMany() while DB is stopping."),
  and `fail()` passes it to the caller as it is. The transaction's record
  is in the stream, and the close writes it.
* Effect: a wrong answer: the caller is told that the database refused the
  call while it was stopping, but the transaction is committed and is there
  after the restart. A caller that retries it after the restart applies it
  twice (extra data, for example an increment counted twice). Only with a
  finite retain duration, when the transaction allows a step or a table
  write; with forever nothing in reclaim checks the state. The same holds
  for `setStartupDistance`'s 200 kB transaction (not probed): it would put
  back the old setting in memory and throw, while the stream's meta block in
  its committed record keeps the new one, which the next start reads.
* Evidence: probe `R7/R7StopDuringStepProbe.java`. `Db.testHooks`'
  `transExecuted` (called after `store()`, before reclaim's work) calls
  `stop()` for the first user transaction whose `transactionCompleted` will
  make a step, as another thread's `stop()` would at that moment (it sets
  the volatile state under `readSync`, which the writer does not hold there,
  and returns; its closer waits for the write lock). `java -ea -cp
  ../../probe-classes:build/bergdb.jar bergdb.core.R7StopDuringStepProbe`.
  Output (`R7/R7-F4-output.txt`): "put 297 of /k/7 threw
  bergdb.core.DbStoppingException: Cannot call getMany() while DB is
  stopping.", then, after `close()` and a start on a copy of the stream:
  "the value of /k/7 is the put's; the transaction at 133280 has time
  159000000 (the put's 159000000)".
* In 2026.1: yes; the same probe (`fractionOf` written as `/ 4`) on
  `release-2026.1`: "put 156 of /k/29 threw DbStoppingException ..." and
  the put's value after the restart.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no format or API change; a small design choice.
* A fix, proposed: in `executeInner`, a `DbStoppingException` from
  `reclaimTransactionListener.transactionCompleted(t)` while the state is
  STOPPING ends reclaim's work and the call returns normally: the
  transaction is committed. A check of the state before the call is not
  enough, as `stop()` takes only `readSync` and can come during the step.
  An internal transaction that the stop refuses is refused at its entry,
  before its go point, so nothing is half done; an iteration whose last
  table write is refused resumes from its row at the next start, as after a
  crash (`testCrashBeforeIterationEnd`). The probe as a test in
  `Reclaim.Tester`.

### R7-F5. pSafe is not "the stream length now", as `markSafePositions`'s Javadoc says (no harm shown)
* Where: `core/Reclaim.java`, `transactionCompleted`: `streamSize =
  t.nextPos` at 357, passed to `markSafePositions` at 380, after the same
  call's iteration start (`storeTable`) and step; `markSafePositions`'s
  Javadoc at 603.
* Intended: the Javadoc: "Sets pSafe of done iterations whose last step the
  startup pos has passed: the stream length now"; the class comment: "then
  passed pSafe, the stream length at that moment (nodes written before their
  children and kept dirty by the still-dirty test written once more, now
  naming the children's new positions)"; docs/levels.md, section 6.
* Actual: `streamSize` is the user record's end, read before the call's
  internal records. When the call starts an iteration (its table) and makes
  a step, and their takes move the startup pos past pEnd, pSafe is set to
  the user record's end, below the stream's length at the marking, and the
  startup pos is already at it.
* Effect: none shown. The probe found no cut of such a row decided before
  the startup pos had passed the true length, as the internal records are
  taken soon after. The risk is the one pSafe is there for: a cut decided
  while nodes that the call's records keep dirty for the done iteration are
  not yet written again; after a crash before their next take, a start or a
  read could meet a pointer below the cut.
* Evidence: probe `R7/R7SafePosProbe.java` (reads the table's rows by
  reflection after each put; retention 1 s, startup distance 2,000):
  `java -ea -Drate=20 -cp ../../probe-classes:build/bergdb.jar
  bergdb.core.R7SafePosProbe`. Output (`R7/R7-F5-output.txt`): "put 1677:
  pSafe 1077656 = the user record's end; the same call then started an
  iteration at pStart 1077656 (its table and step before the marking);
  stream now 1081704; startup pos 1077656", in 2 or 3 of about 57 markings
  a run; "such rows cut later: 2, of them at a startup pos before the length
  at the marking: 0", at three write rates and startup distances.
* In 2026.1: yes, the same code (`release-2026.1`, Reclaim.java 325 and 348).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no format or API change; the stream's bytes change where a cut
  would come later.
* A fix, proposed: pass `db.getStreamLength()` (the write lock is held) to
  `markSafePositions`, so pSafe is the length at the marking, as the Javadoc
  says; or correct the Javadoc and argue the safety of the earlier
  value in 001-07's register. The first changes the stream only where a
  cut comes a little later; run `level3.sh`.

### R7-F6. A user transaction at the last database time is taken, and reclaim's next internal transaction then fails the database
* Where: `core/DbClock.java`, `transactionBegin` (the check `time >
  Klong.MAX_TIME`); `core/Db.java`, `executeInner`: `t.tt =
  dbClock.transactionBegin()` before the go point, for reclaim's internal
  transactions inside the user transaction's go point
  (`transactionCompleted`, 2050).
* Intended: docs/levels.md, section 3: the clock (005-18) is checked before
  the go point, and a refused transaction leaves the database going on.
  The top node ordinals keep a margin for exactly this case:
  `TOP_ORDINAL_MARGIN` (Db.java), "room for the internal transactions that
  run after a user transaction, reclaim's", so that "no transaction reaches
  the bound" (005-02).
* Actual: the times have no such margin. A user transaction may take the
  last time, `Klong.MAX_TIME`; a reclaim step or table write that it allows
  then needs a later time, `transactionBegin` throws "No database time is

  point, and `fail()` fails the database. The user transaction is committed
  (its record was appended first), although the call throws.
* Effect: a database that fails when it should not: reads are refused too
  until a restart (after which writes are refused cleanly, as there is no
  time left). It needs a clock at the end of the range, about the year
  2198, so only a wrong or a test clock; low weight, but the ordinals'
  margin shows the intent.
* Evidence: probe `R7/R7ClockEndProbe.java`: puts with retention 1 s until
  the next put will make a step, then that put with the test clock at
  `Klong.MAX_TIME`. `java -ea -cp ../../probe-classes:build/bergdb.jar
  bergdb.core.R7ClockEndProbe`. Output (`R7/R7-F6-output.txt`): "put 297
  (clock at Klong.MAX_TIME: true) FAILED THE DATABASE:
  bergdb.pub.util.DbException: No database time is left after
  72057594037927935; the largest is 72057594037927935."
* In 2026.1: yes; the same on `release-2026.1` ("put 156 ...").
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no; a margin's size.
* A fix, proposed: refuse a user transaction whose time would be above
  `Klong.MAX_TIME - margin` (a margin of, say, 1,024 units, as the ordinals'),
  in `transactionBegin` for user transactions only, so that reclaim's
  internal transactions after it always have a time. A test from the probe.

## 3. Doubts
* **D1. A read concurrent with `start()` may fail the database (new in
  2026.2, if at all).** Since 009 step 1c reads no longer wait on
  `readSync`, which `start()` holds; `startInner` sets `state = ACTIVE`
  before `reclaim.initFromDb()` sets the first available lookup time (0
  until then). A read admitted in that window at a time below the stream's
  cut reads cut bytes; if `initFromDb` has not yet set the time when
  `expiredIfReadBelowCut` reads it, the read fails the database instead of
  expiring. `start()`'s Javadoc asks for the get methods after it ("Call
  once per Db object after constructor and before the get/set methods"), so
  this is outside the contract; not written out as an interleaving for a
  verifier. A fix would set ACTIVE after `initFromDb` (its reads through
  `getOneInternal`).
* **D2. A Core API transaction with `keyRead` and no `lookupTime` is never
  refused by the STM.** `Trans.Builder`'s read time defaults to
  `Long.MAX_VALUE` (line 162), and `KeyModSet.modifiedAfter(Long.MAX_VALUE,
  h)` is never true, so the check passes whatever was written after the
  read, also across a start (005-70's boundary does not apply). It agrees
  with `execute`'s Javadoc ("changed after the read time of the
  transaction") but not with what a caller of `keyRead` expects; `keyRead`
  and `lookupTime` have no Javadoc. Whether this is a fault is the Core API
  contract's question; the Pub API sets the read time. A probe would show a
  stale read set committed.
* **D3. F1's other path, not probed:** a step whose values pass
  `checkSize` but whose record, with the index nodes that its touch makes
  dirty, passes `StoredTrans.recordLimit` in `store()` (the take's room,
  `recordLimit - fixedBytes`, can be negative), which also throws after the
  go point. A probe as F1's with the value just under `valueLimit()` minus
  the row and a range of many keys would show it.

## 4. Checked and right
* 005-61: `Reclaim.transactionCompleted` reads `db.getStartupDistance()`
  under the write lock (reentrant); no copy is left; the dummy transaction
  of `setStartupDistance` already uses the new distance, and so does a
  restart (the meta block), so the spacing does not depend on restarts.
* 005-79: `fractionOf` is floor(g f / 2^16) without overflow (checked the
  algebra; `testFractionOfExact`); `retainDuration / ITERATION_DIVISOR`;
  `Db.setReclaimInternalFraction` maps the whole range 0.001 to 0.90 into
  66 to 58,982 (`Math.round` of 65.536 and 58,982.4), so no accepted double
  is refused by Reclaim; NaN, infinities and values outside are refused
  before anything changes; the getter is exact.
* 005-70: `setFirstTime` after DbStarter's validation, under both locks;
  `Bin.add` keeps the boundary at its first add; the "too old" path refuses
  an older read time; the boundary bin ages out by the normal turnover. A
  reclaim step reads at the latest time under the write lock, so the
  boundary never refuses it and its `RerunException` path cannot loop.
* 005-73: F1 (`StartInfo.startupDistance`), F4 (NaN), F5 (`closeFailure`
  kept under `closeLock`, reported by a waiting or a repeated `close()`, and
  by a `close()` within a transaction).
* 005-82: the parse inside the `try`; a `StreamFormatException` or another
  `RuntimeException` of the parse fails the database; the end of the stream
  stays an `IllegalArgumentException`; a read below the cut expires.
* 005-53's `setStartupDistance`: the state is checked under the write lock
  before anything changes; the value in force returns at once; a refusal or
  a failure puts back the field and the meta block's value.
* The go point in `executeInner`: every refusal (`checkSize`, the top node
  ordinals, `checkDirtyNodes`, the state again under the lock, the STM, the
  clock) comes before `putKvs`; `x.begin`'s writes are overwritten by the
  next `begin`, so a refusal leaves nothing; after it every `Throwable` goes
  to `fail()`, an `Error` is thrown as it is, and a nested reclaim
  transaction's `DbFailedException` passes as it is.
* The reads: `getOne` and `getMany` check the first available time before
  they read the clock, and the actual lookup time is never below it (the
  last transaction time is at least tEnd, written before); the expiry
  rereads the time; `setFailed` keeps the first failure under `readSync`.
* Reclaim's cut: its conditions are docs/levels.md, section 6's; the first
  available time is set at the decision, before the physical cut, which
  waits for durability; `initFromDb` redoes a cut that a crash lost; the
  first available time never moves back. With forever no new iteration
  starts, an iteration in progress ends, and no cut is made
  (`timeNow - Long.MAX_VALUE` does not overflow; `lastTStart()`'s
  `Long.MIN_VALUE / 2` does not either).
* `setRetainDuration`, `setStepReserve`, the fraction: volatile, thread-safe.

  harmless, as `Cache3.getSizeIndicator` is read only by a test
  (`PubTester`).
* `close()`, `stop()`, `closeStorage()`: no lock held while waiting; the
  eviction thread ended without an interrupt ending the wait; a start that
  throws closes its storage.
* Run at f7974d3: `ReclaimReaderTester`, `ReclaimRetentionTester`,

## 6. Shared fields (R1, R2, R4 and R5; 016-07, section 3)
Db (`core/Db.java`):
* `state` (Db): volatile; written under `readSync` by `setFailed`, `stop`,
  `close`, and by `start` under `writeLock` and `readSync`; read plain
  (acquire) by every call in `assertDbStateIsActive`. Edge: the volatile
  write and read. A stale ACTIVE read lets one call in after a failure or a
  stop; it then meets the closed storage or a refused transaction (under
  `writeLock`, `executeInner` checks the state again). Test: `DbTesterFailure`
  (`assertRefused`); no jcstress.
* `failure` (Db): volatile; written under `readSync` before `state` is set to
  FAILED (`setFailed`), never again; read in `assertDbStateIsActive` after
  `state`. Edge: program order before the volatile write of `state`, and
  the volatile read of `state` before it; a reader that sees FAILED sees the
  first failure. Test: `DbTesterFailure`.
* `dag` (Db): plain; written once in `start` (DbStarter), before `state`
  becomes ACTIVE; read by readers after `assertDbStateIsActive`. Edge: the
  volatile write and read of `state`. A call before `start` returns is
  refused (state ZERO) or sees the Dag; the Javadoc asks for calls after
  `start`. Test: none.
* `startupDistance` (Db): plain; written under `writeLock` (`start`,
  `setStartupDistance`, its restore); read under `writeLock`
  (`getStartupDistance`, `store`, `Reclaim.transactionCompleted` through
  `getStartupDistance`). Edge: the monitor. Test: `Reclaim.Tester`
  (`testIterationsFollow...`), `DbTester.testSetStartupDistanceInForceOrRefused`.
* `keyModSet` (Db) and its bins: plain; written under `writeLock`
  (`setFirstTime` in `start`, `stmRecordKeys`); read under `writeLock`
  (`stmCheckConflicts`). Edge: the monitor. Test: `KeyModSet.testStartupBoundary`,
  `DbTesterRestart.testStmAfterRestart`.
* `writersWaiting` (Db): an AtomicInteger, incremented before and
  decremented inside `synchronized (writeLock)` in `executeInner`; read by
  the eviction thread (`Internal.writersWaiting`). Only a hint for giving way;
  a stale value delays or hastens a batch. Test: `EvictionReaderTester`
  (009 step 3d).
* `closeBegun`, `closeDone`, `closeFailure` (Db): plain, under `closeLock`
  for every write and read (`stop`, `close`, `closeStorage`,
  `closeAfterFailedStart`, `waitUntilClosed`). Edge: the monitor, and its
  wait/notifyAll for `closeDone`. Test: `DbTester` (005-73, F5's
  regressions, `testCloseAfterStopAndTwice`).
* `x` (ExecuteData), `aux.transactionCount`, `aux.kvCount`,
  `newestWrittenTop`, `transSeq`, `opMarks` and the other put state: the
  writer's, under `writeLock`; `getTransactionCount` and `getKvCount` read
  under it. Edge: the monitor.
* `x.endOfLastTrans` (ExecuteData): plain; written by the writer in
  `x.end()` under `writeLock`; read by `sync(0)` under `writeLock`. Edge: the
  monitor.
* `x.startupPos` (StartupPos): its `evictPos` volatile, set by
  `releaseForEvict` after `store`; read by eviction and by Reclaim (under
  `writeLock`). Edge: the volatile, or the monitor for Reclaim.
* `aux.getOpCount` (Db.Aux): a LongAdder, added by readers; read by
  `getGetOpCount`. A statistic; a sum that misses a running read is
  harmless.
* `dbClock.lastTransactionTime` (DbClock): volatile; written by the writer
  in `transactionEnd`, under `writeLock` and the clock's monitor; read
  plain (acquire) by every read in `lookupTime`. Edge: the writer's Dag
  writes before `transactionEnd` happen before the volatile write; a reader
  that reads the time sees them (Db's concurrency note, 009 step 1c). A
  stale time gives an older snapshot, which is complete.

Reclaim (`core/Reclaim.java`):
* `firstAvailableLookupTime`, `firstAvailablePos` (Reclaim): volatile;
  written by the writer under `writeLock` and `readSync`
  (`pretruncateIfPossible`, `initFromDb`); read plain by readers in
  `getOneInternal`, `getMany` and `expiredIfReadBelowCut`, and by
  `Db.getFirstAvailable...` after an empty `readSync` block. Edge: the
  volatile; the time is written at the decision, before the physical cut
  (`cutIfDurable`), so a reader that reaches the cut bytes reads the new time
  in `expiredIfReadBelowCut`. The two are separate volatiles: a caller that
  reads both may see the time of one cut and the position of the one before;
  only statistics and tests read the position. Test: `ReclaimReaderTester`,
  `java/stress/ReclaimReaders.java`.
* `retainDuration`, `internalFraction`, `stepReserve` (Reclaim): volatile;
  written by any thread (the setters, JMX); read by the writer under
  `writeLock`. `transactionCompleted` reads `retainDuration` twice; a
  setter between the two reads is the same as a setter just after the
  check. Test: `ReclaimRetentionTester`, `DbTester.testReclaimInternalFractionValidation`.
* `iterationCount` (Reclaim): volatile; incremented by the writer only,
  under `writeLock`; read by any thread (statistics). One writer, so the
  `++` loses nothing.
* `table` and its rows, `pendingCut`, `pendingCutDurableAt`, `stats`
  (Reclaim): plain; written and read by the writer under `writeLock`
  (`transactionCompleted`, `step`, `initFromDb` in `start`); `lastPStart()`
  and `lastDoneRow()` are read by tests from the writer's thread. Edge: the
  monitor.
