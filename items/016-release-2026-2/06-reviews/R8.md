## 2. Faults

### R8-F1. deleteIndex() by an interrupted thread throws, and leaves the index deleting with no job

* Where: `pubimp/DatabaseImp.java`, `deleteIndexInternal`, line 318
  (`sync(SyncLevel.ORDINARY)` in the caller's thread, after `ensureDeletingState`, before the
  job is made and started at line 390).
* Intended: `Database`'s class Javadoc, "Interrupts (bergdb 005-46)": three calls only wait
  and end on an interrupt (`sync()`, a `Job`'s `join()`, the wait of a rerun); "Every other
  call ignores an interrupt until it is done", and the flag is set when it returns.
  `deleteIndex()` is not one of the three.
* Actual: the sync waits for the deleting state's transaction, which `ensureDeletingState`
  has just committed and which is still in the write buffer; the wait ends on the interrupt
  with `InterruptedIOException`, and `Db.sync` throws a `StreamIoException`. The index is
  then in the deleting state, in the stream and in memory, and no deletion job runs.
* Effect: a refused call that is not refused: the caller gets a `DbException` (no `Job`),
  while the index has been taken out of use; its entries stay until a later `deleteIndex()`
  or a restart (`finishOngoingJobs`) starts the job. The same sync runs in
  `DatabaseImp.createAndStart` through `finishOngoingJobs` when a start finds an index
  deleting; there it finds everything durable and does not wait, so a start by an
  interrupted thread works (`R8Tester.testStartWithIndexDeletingByInterruptedThread`
  passes, and its job deletes the 100 entries). Of the other public calls, none breaks the
  rule (`R8Tester.testSweepInterrupted`, on a file database: only `deleteIndex` fails).
* Evidence: `R8Tester.testDeleteIndexByInterruptedThread`:
  ```
  FAILED! bergdb.pubimp.R8Tester.testDeleteIndexByInterruptedThread
  bergdb.storage.StreamIoException: Thread was interrupted while waiting for D1 size 3184.
      at bergdb.core.Db.sync(Db.java:1812)
      at bergdb.pubimp.DatabaseImp.sync(DatabaseImp.java:183)
      at bergdb.pubimp.DatabaseImp.deleteIndexInternal(DatabaseImp.java:318)
  ```
* In 2026.1: the code yes (`release-2026.1:java/src/bergdb/pubimp/DatabaseImp.java`, line
  281); the promise no: 2026.1's `Database` has no "Interrupts" paragraph. So new in 2026.2,
  as a statement the code does not keep.
* A fix touches the stream format, a Pub API signature, or needs a design choice: no.
* A fix: make the sync of `deleteIndexInternal` not interruptible (clear the flag with
  `Thread.interrupted()`, sync, set it again in a `finally`), or move it into the job's
  thread before `deleteIndexEntries`, where nothing interrupts.

### R8-F2. Time.resolve(TimeZone, String) ignores its time zone

* Where: `pub/Time.java`, `resolve(TimeZone timeZone, String timeString)`, line 95:
  `TimeResolver.resolveAbsolute(UTC, timeString)`.
* Intended: its Javadoc, "Resolves the time string using the given time zone."
* Actual: it resolves in UTC, whatever zone is given.
* Effect: a wrong answer: `Time.resolve(Europe/Stockholm, "2013-08-19 14:29")` is
  14:29 UTC, not 12:29 UTC; a lookup time made this way is off by the zone's offset.
* Evidence: `R8Tester.testTimeResolveUsesTheTimeZone`:
  ```
  FAILED! bergdb.pubimp.R8Tester.testTimeResolveUsesTheTimeZone
  java.lang.AssertionError: Expected 2013-08-19 12:29:00.0000000, got 2013-08-19 14:29:00.0000000.
  ```
* In 2026.1: yes (`release-2026.1:java/src/bergdb/pub/Time.java`, line 95, the same call).
* Design choice: no.
* A fix: `TimeResolver.resolveAbsolute(timeZone, timeString)`; `Time.utc()` keeps UTC.

### R8-F3. TestClock.setTime() refuses the clock's current time, which its Javadoc allows

* Where: `pub/TestClock.java`, `setTimeInUnits`, line 47: `if (time <= this.time) throw`.
* Intended: `setTime()`'s Javadoc, "The time must be larger than or equal to the current
  time of the clock."
* Actual: an equal time throws `IllegalArgumentException("Bad time, must be larger than
  current time, ...")`; so does `setTime(Time.units(0))` on a new clock.
* Effect: a refusal the Javadoc does not state; a test that sets the same time twice fails.
* Evidence: `R8Tester.testTestClockSetTimeEqual`:
  ```
  FAILED! bergdb.pubimp.R8Tester.testTestClockSetTimeEqual
  java.lang.IllegalArgumentException: Bad time, must be larger than current time, 1000.
  ```
* In 2026.1: yes (line 42 there, the same check and Javadoc).
* Design choice: which side to change (the Javadoc to "larger than", or the check to
  `time < this.time`); no format or signature change.
* A fix: `if (time < this.time)`, as the Javadoc says; the database's clock gives each
  transaction a later time itself (`DbClock.transactionBegin`), so equal clock times are
  safe.

### R8-F4. Connection.getLookupTime() of a new connection throws IllegalArgumentException

* Where: `pubimp/ConnectionImp.java`, the constructor, line 47 (`this.lookupTime =
  Long.MAX_VALUE`), and `getLookupTime`, line 70 (`Time.units(lookupTime)`);
  `pubimp/DatabaseImp.java`, `newConnection`, line 169 (no `connectionInitializer`, unlike
  `connection()`).
* Intended: `Connection.setLookupTime()`'s Javadoc: "By default, the requested lookup time
  is Time.MAX"; `getLookupTime()`: "Returns the requested lookup time". `Database.connection()`
  says its connection's lookup time "is always Long.MAX_VALUE", which is not a `Time`.
* Actual: `newConnection()` (also the connections that `deleteIndexInternal` and
  `createAndStart` make) has `Long.MAX_VALUE`, above `Time`'s range (2^56 - 1), and
  `getLookupTime()` throws `IllegalArgumentException("Time ouf of range, units:
  9223372036854775807.")`. A connection from `connection()` has `Time.MAX` (2^56 - 1), as
  its initializer sets it, so the two kinds differ, and neither is what `connection()`'s
  Javadoc says.
* Effect: an exception from a getter on a connection in its default state; code that saves
  and restores a connection's lookup time fails.
* Evidence: `R8Tester.testNewConnectionLookupTime`:
  ```
  FAILED! bergdb.pubimp.R8Tester.testNewConnectionLookupTime
  java.lang.IllegalArgumentException: Time ouf of range, units: 9223372036854775807.
      at bergdb.pub.Time.units(Time.java:59)
      at bergdb.pubimp.ConnectionImp.getLookupTime(ConnectionImp.java:70)
  ```
* In 2026.1: yes (`ConnectionImp.java` lines 47 and 70 there).
* Design choice: no. The reads are the same for both values (`DbClock.lookupTime` takes the
  last transaction's time for any larger value).
* A fix: the constructor sets `Time.MAX.units()`; `Database.connection()`'s Javadoc says
  "Time.MAX".

### R8-F5. Database.connection() keeps a connection for every thread that ever called it

* Where: `pubimp/DatabaseImp.java`, `connection()`, lines 150 to 166: a
  `HashMap<Thread, Connection>`, cleared only by `stop()` and `close()`.
* Intended: `connection()`'s Javadoc: one connection per thread; nothing says that the
  connections of ended threads are kept. `Transaction`'s Javadoc asks the user not to keep
  objects long, "To allow Connection and Database objects to be garbage collected".
* Actual: an ended thread and its `ConnectionImp` (with its `GetData`) stay in the map
  until the database stops.
* Effect: memory that grows without bound in a program whose threads come and go (a
  cached thread pool, a thread per request) and that calls `connection()`; at the end an
  `OutOfMemoryError`, which, in a transaction, fails the database.
* Evidence: `R8Tester.testConnectionOfEndedThreadsKept` (200 threads, each calls
  `connection()` and ends; the map, read by reflection, holds 200):
  ```
  FAILED! bergdb.pubimp.R8Tester.testConnectionOfEndedThreadsKept
  java.lang.AssertionError: connections of ended threads kept: 200, expected true, but was false.
  ```
* In 2026.1: yes (`DatabaseImp.java` lines 51 to 57 and 153 there).
* Design choice: no.
* A fix: a `ThreadLocal<Connection>` per `DatabaseImp` (dropped with the thread), or a
  `WeakHashMap<Thread, Connection>`; `stop()` then needs no clear, or clears what it can.

### R8-F6. A deletion job that stop() or close() ends early reports "Done! Deleted"

* Where: `pubimp/DatabaseImp.java`, `deleteIndexInternal`: the job's thread catches
  `DbStoppingException`, `DbFailedException` and `StreamIoException` and ends (lines 339 to
  347); `getStatus()` (lines 356 to 372) says progress 100 and "Done! Deleted 'NAME', N
  index entries were deleted." whenever the thread has ended.
* Intended: `JobStatus.progress()`: "100 means finished"; the comment at line 340: the job
  "will continue when database is started again", so it has not finished. The index builds
  report such an end as "Stopped" (`PubTesterIndexJobs.checkStopped`, bergdb 015-21).
* Actual: a deletion that a stop, a close or a failure ended before it deleted anything says
  it is done and has deleted the index.
* Effect: a wrong answer: `join()` returns 100 and "Done! Deleted 'by-amount', 0 index
  entries were deleted." while the index is deleting and its entries are in the stream.
* Evidence: `R8Tester.testDeletionJobStoppedSaysDone` (the test hook `testHookDelete`
  closes the database when the job's thread starts):
  ```
  R8 deletion job after close: 100, Done! Deleted 'by-amount', 0 index entries were deleted.
  FAILED! bergdb.pubimp.R8Tester.testDeletionJobStoppedSaysDone
  ```
* In 2026.1: yes (the same catch clauses and note; line 321 there).
* Design choice: no.
* A fix: a `volatile boolean done`, set after the final sync in the thread; `getStatus()`
  says "Stopped: ..." (progress 100, as a build) when the thread has ended without it.

### R8-F7. transactionInfo() after a get() that found no entry throws IllegalArgumentException

* Where: `pubimp/ConnectionImp.java`, `transactionInfo`, lines 105 to 118: only
  `actualLookupTime == -1` and `tpos == Spos.NULL` are checked; a get of a missing key
  leaves `tpos` 0, and `Db.getTrans(0)` throws.
* Intended: `Connection.transactionInfo()`'s Javadoc: information about the transaction that
  wrote "the last value retrieved with the get() method"; `IllegalStateException` "If no get()
  has been made, or if the transaction that wrote the value was still being stored".
* Actual: `IllegalArgumentException: Not a position of a transaction, 0.`, a message about
  an internal stream position, an exception the Javadoc does not name.
* Effect: an undocumented exception; a caller that catches `IllegalStateException` for "no
  value" does not catch it.
* Evidence: `R8Tester.testTransactionInfoAfterGetOfMissingKey` (passes; it prints what
  `transactionInfo()` throws):
  ```
  R8 transactionInfo after a missing key: IllegalArgumentException: Not a position of a transaction, 0.
  ```
* In 2026.1: yes for the code path; 2026.1's `getTrans` may have read position 0 instead of
  refusing it (005-34 added the refusal); not checked.
* Design choice: no (which exception to give: `IllegalStateException`, as for "no get()").
* A fix: in `transactionInfo()`, when the last get gave no value (`tpos` 0 or the value
  null), throw `IllegalStateException("No available transaction info: the last get() found
  no entry.")`, and say so in the Javadoc.

### R8-F8. Time.toString() from several threads gives wrong strings and throws

* Where: `pub/Time.java`, `toUtcString`, line 225: one static `SimpleDateFormat`,
  `UTC_DATE_FORMAT`, which is not thread-safe, for every `Time`.
* Intended: `Time` is an immutable value (its one field is final), returned by
  `Transaction.getTime()`, `Database.currentTime()` and `TransactionInfo.time()` to any
  thread; `toUtcString()`: "Returns the time in UTC formatted like this". The sentence "This
  class is not thread-safe" in `resolve()`'s Javadoc is copied from `TimeResolver`'s, about
  the resolver.
* Actual: two threads that format at once share the formatter's `Calendar`.
* Effect: a wrong answer (the string of another thread's time) or an
  `ArrayIndexOutOfBoundsException` from `toString()`; in a log or a message, a wrong time.
* Evidence: `R8Tester.testTimeToStringFromThreads` (8 threads, 20,000 calls each, 0.1 s):
  ```
  Exception in thread "Thread-7" java.lang.ArrayIndexOutOfBoundsException: Index 510 out of bounds for length 13
      at bergdb.pub.Time.toUtcString(Time.java:225)
  FAILED! bergdb.pubimp.R8Tester.testTimeToStringFromThreads
  java.lang.AssertionError: wrong strings, e.g. expected 2035-02-15 15:25:35.1234567, got 2021-06-14 18:28:38.1234567, expected 0, got 2287.
  ```
* In 2026.1: yes (`Time.java` line 212 there, the same static formatter).
* Design choice: no.
* A fix: `java.time.format.DateTimeFormatter` (immutable, thread-safe) with
  `ZoneOffset.UTC`, or a new `SimpleDateFormat` per call.

### R8-F10. A refused second start() of one builder closes the running database's stream, and the database fails

* Where: `pubimp/DatabaseBuilderImp.java`, `start`, lines 201 to 211: `openDirs()` throws
  (the directory is in use, by the database this builder started), and the catch calls
  `dbBuilder.closeStreams(e)`, which closes every stream in the `DbBuilder`
  (`core/DbBuilder.java`, `closeStreams`, lines 91 to 99): at that point the streams of the
  first start, which `build()` left there, the running database's main stream among them.
* Intended: `DatabaseBuilder.dir()`'s Javadoc (bergdb 005-63): while another database has
  the directory open, `start()` throws a `StreamIoException` whose cause is a
  `DirectoryInUseException`, and "Nothing in the directory has been read or changed then";
  `start()`'s: "A start that throws has closed what it opened" (bergdb 005-32), not what
  another start opened. 005-66 made the builder hold nothing until it starts.
* Actual: the second start is refused as stated, and the first database's `FileStream`
  is closed under it: its storage manager's next flush fails, the next sync fails the
  database, and its lock is released while it is still open.
* Effect: a database that fails when it should not, and loses what it had not yet
  flushed: after the refused start, `put("/b")` returns, and `sync()` throws
  `DbFailedException` ("StorageManager has error: Main storage not active ... The flush
  failed"); every later call is refused until a restart, and `/b` is gone. The lock file's
  lock is released while the first `Database` object is not closed, so a third start on
  the directory is not refused (not tested).
* Evidence: `R8Tester.testSecondStartOfOneBuilder` (one builder with `dir()`, start, put,
  sync, start again, then put and sync on the first):
  ```
  R8 second start: bergdb.storage.StreamIoException: Directory ... is in use by another BergDB database in this JVM (bergdb.lock is locked)., cause bergdb.stream.DirectoryInUseException: ...
  R8 first database after it: bergdb.pub.util.DbFailedException: A sync failed on the storage (the cause). The database takes no more transactions or reads and must be restarted., cause bergdb.storage.StreamIoException: StorageManager has error: Main storage not active. java.io.IOException: The flush failed (the cause).
  FAILED! bergdb.pubimp.R8Tester.testSecondStartOfOneBuilder
  ```
* In 2026.1: no, not this way: there `dir()` opened the `FileStream` and a second `start()`
  of the builder gave the same stream object to a second `Db` (not checked further); the
  refusal and its close path are 005-63 and 005-66, new in 2026.2.
* Design choice: no, unless the builder is to refuse a second `start()` (one start per
  builder, said in the Javadoc), which is a choice of the API.
* A fix: `start()` closes only what this start opened: `openDirs()` adds its streams to a
  local list and the catch closes those; and the streams of an earlier start are dropped
  from the `DbBuilder` before `openDirs()` (or `build()` hands them to the `Db` and clears
  them), so that a later failure cannot reach them.

## 3. Doubts

* D1. `TestClock.time` is a plain field: a test thread's `setTime()` and a transaction in
  another thread (`DbClock.transactionBegin` reads `clock.getTime()` under DbClock's
  monitor, not the test's) have no happens-before edge, so the transaction may see the old
  time. Not verified: no failing run; a jcstress test of `setTime` in one thread and
  `getTime` in another would show it. A fix: `volatile`.
* D2. `currentTime()` with a clock that returns a time above 2^56 - 1 once sets
  `DbClock.lastReadTime` there, and every later transaction is then refused ("No database
  time is left"), until a restart. `Clock.getTime()`'s Javadoc forbids such a value, so this
  is a misuse; not tested.
* D3. The builder's default cache size (a fifth of the heap, at least 2 MB) is not clamped
  as `cacheSizeInMb()` and `Database.setCacheSizeInMb()` clamp it (4 to 100,000 MB): a heap
  below 20 MB gives a budget below 4 MB, a heap above 500 GB one above 100,000 MB. Not a
  stated promise; not tested.

## 4. Checked and right

The statements of the Javadoc, with the code that keeps them and a test where one is known.

Database:
* Class: a refused transaction changes nothing; a failure fails the database, later calls
  throw `DbFailedException` with the first failure as the cause (`Db.assertDbStateIsActive`,
  under `writeLock` again in `executeInner`); `sync()` still works after a failure (`Db.sync`
  checks no state).
* Interrupts: `sync()` throws a `StreamIoException` whose cause is an
  `InterruptedIOException`, the flag set (`StorageManager.sync`, `syncStrong`); `join()`
  returns the status with the flag set (`DatabaseImp`, `IndexBuilderImp`, `IndexManager`
  jobs; `PubInterruptTester`); the rerun's wait throws a `DbException`
  (`RwTransaction.executeRw`). Every other call, by an interrupted thread on a file
  database, returns with the flag set: `put`, a `w()` with an index entry, `get`,
  `transactionInfo` (a stream read), `exists`, `rw`, `usePrimary` and `useIndex`
  iterations, `setStartupDistanceInMb` (a 200 kB transaction), `setCacheSizeInMb`,
  `setRetainDuration`, `currentTime`, `close`; a start with an index deleting
  (`R8Tester.testSweepInterrupted`, `testStartWithIndexDeletingByInterruptedThread`).
  `deleteIndex()` does not (R8-F1).
* After `close()`, each public method of `Database` and `Connection`
  (`R8Tester.testSweepAfterClose`, no assertion, its output read): the reads,
  transactions, `indexBuilder().createFast()` and `deleteIndex()` throw
  `DbStoppingException`; `sync()`, `sync(STRONG)`, `Connection.sync()`, `currentTime()`,
  the getters, `stop()` and `close()` return; none hangs. `setCacheSizeInMb()` after
  `close()` sets the value that `getCacheSizeInMb()` then returns, and nothing else, where
  the Javadoc says "After stop() the method has no effect" (`Db`'s: "only sets the value");
  harmless.
* `stop()`: STOPPING under `readSync`, then one closer thread (`closeBegun` under
  `closeLock`), not a daemon; `closeStorage` takes `writeLock` first, so a running
  transaction completes and is written; idempotent.
* `close()`: waits (`waitUntilClosed`, not interruptible, flag set again); in a transaction
  closes at once; a failed close is kept in `closeFailure` and thrown by every later
  `close()`. Test: `R8Tester.testSyncAfterClose` (sync after close returns).
* `connection()`: one per thread, others different; lookup time reset on each call
  (`connectionInitializer`) to `Time.MAX`, not `Long.MAX_VALUE` (R8-F4); kept for ended
  threads (R8-F5). `newConnection()`: always new.
* `currentTime()`: at least the last completed transaction's time, below a running or a
  later one (`DbClock.currentTime` and `transactionBegin`, under DbClock's monitor, with
  `lastReadTime`). Test: `R8Tester.testCurrentTime` (1,000 rounds, one thread).
* `setRetainDuration()`: below one second refused (`DatabaseImp`, `Reclaim`); volatile
  field, so in force for the next step.
* `setStartupDistanceInMb()`: clamped 5 to 1,000 MB; under `writeLock`, the state checked
  first; a refused or failed call restores the setting and the meta block; equal value
  writes nothing. Test: `R8Tester.testSetStartupDistanceAfterClose` (refused with
  `IllegalDbStateException`, 50 kept).
* `setCacheSizeInMb()`: clamped 4 to 100,000 MB, in long; after close no exception. Test:
  `R8Tester.testSetCacheSizeAfterClose`; `DatabaseBuilderImp.testCacheSizeAbove2GB`.
* `getStartupInfo()`: `StartInfoImp` clones its job array (immutable as stated).
* `indexBuilder()`, `deleteIndex()`: the name checks; a second `deleteIndex()` returns the
  running job (`IndexManager.startDeletionJob`, `PubTesterIndexJobs`, 015-21).

DatabaseBuilder:
* `dir()`, `replica()` only record (005-66); `start()` checks the crypto key and a missing
  stream (015-01) before it opens anything; a failure in `openDirs` or the crypto setup
  closes the streams opened (`closeStreams`); a failure in `Db.start` closes the storage
  (`closeAfterFailedStart`); one after it, in `createAndStart`, closes the Db (005-32).
* The second start on a directory: refused by the FileStream lock (005-63; R3's area).
* `startupDistanceInMb()` and `cacheSizeInMb()` clamp; `DatabaseBuilderImp`'s own tests.

Connection:
* `setLookupTime()`: null refused; ends a freeze. `get()`: the null and format checks.
  `exists()`: null refused, an invalid key false. `put()`, `delete()`: through `w()`.
  `rw()`: sets `lastSposOfLastTrans` as `w()` does, so `Connection.sync()` waits for it.
  `Transaction.sync()`: this transaction's `lastPos` (005-45).
* `transactionInfo()`: the user's KVs only, a delete as a null value. Test:
  `R8Tester.testTransactionInfoHasTheDelete` (passes). The case of no value: R8-F7.

Time, Duration, Job: `Time.millis()` checks the product; `Time`'s range 0 to 2^56 - 1;
`Duration` non-negative; `Job.join()` and `join(millis)` as stated; `JobStatus` immutable
(each status captures its values).

## 5. Met outside the scope

* `DatabaseBuilderImp.openDirs` gives each replica `DEFAULT_BUFFER_TIME`, where
  `DatabaseImp.addReplica` gives `DEFAULT_REPLICA_BUFFER_TIME` (replication).
* `IndexBuilderImp.sleepFiftyPercentOfDuration` caps `ms` and `nanos`, not `msToSleep` and
  `nanosToSleep`, so the sleep between build steps is not "never longer than 1 second" as
  its Javadoc says: half of any step (speed; the index area).

## 6. Shared fields

* `DatabaseImp.threadLocalConnections`: written and read under its own monitor by every
  caller of `connection()`, `stop()`, `close()`; the monitor orders them. Growth: R8-F5.
* `DatabaseImp.startupInfo`: written in `createAndStart` before the `DatabaseImp` is
  returned; read by the user's threads after that; the publication is the user's (no
  final, no volatile), as for any object handed over. Harmless in practice; no test.
* `TestClock.time`: written by the test's thread, read by the transaction's; plain (D1).
* `Time.UTC_DATE_FORMAT`: shared, mutable, no lock: R8-F8.
* The deletion job's `deletedCounter[0]`: written by the job's thread, read by
  `getStatus()` in any thread, plain; a stale count in a note only; after `join()` the
  thread's end orders it.
* `Db.state`, `closeBegun`, `closeDone`, `closeFailure`: volatile, and under `readSync` and
  `closeLock`, as their comments say; checked in `stop`, `close`, `closeStorage`,
  `waitUntilClosed`.
