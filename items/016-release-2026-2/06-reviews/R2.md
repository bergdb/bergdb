## 2. Faults

### R2-F1. A rejected open through another class loader releases the active directory lock

* Where: `java/src/bergdb/stream/FileStream.java`, `LOCKED_DIRS`,
  `lockDir()`, lines 139-140 and 585-647; especially the close in the
  `OverlappingFileLockException` handler, lines 614-618, at BASE.
* Intended: 005-63, "The lock file", points 5-6, and FileStream's class
  Javadoc promise one stream per directory, in the JVM and across
  processes, until close finishes. Refusing another open must preserve
  the first stream's operating-system lock.
* Actual: `LOCKED_DIRS` belongs to the defining class loader. A second
  copy of BergDB in another class loader has an empty set, opens the
  lock file, gets `OverlappingFileLockException`, and closes that handle.
  On the tested macOS/POSIX filesystem this releases the process's lock
  held through the first stream's handle. The first stream remains open
  and accepts appends; another process can now take its lock.
* Effect: an application with isolated copies of BergDB (for example,
  separate plugin or application loaders) can lose directory exclusion
  merely by refusing a second open. Another process can then open the
  same live stream, risking conflicting writes and corruption. This
  needs no modification or deletion of bergdb.lock.
* Evidence: `R2/LockLoaderProbe.java`, one JVM, with an isolated
  `URLClassLoader` for the second copy and a short Python POSIX-lock
  check in another process. From the review root:

  ```sh
  javac --release 17 -cp repo/java/build/bergdb.jar -d out/R2/classes out/R2/LockLoaderProbe.java
  java -ea -cp out/R2/classes:repo/java/build/bergdb.jar bergdb.core.LockLoaderProbe out/R2 repo/java/build/bergdb.jar
  ```

  Output (`R2/LockLoaderProbe.output.txt`): `Before second loader:
  REFUSED`; the second loader throws `DirectoryInUseException`; `After
  rejected open, first still open: ACQUIRED`; `First still accepts
  appends: length=4`. Both Java streams are closed or refused; the
  native checker exits before the next step. No second JVM is used.
* In 2026.1: no, this rejected-open path and lock registry did not exist
  (`git show release-2026.1:java/src/bergdb/stream/FileStream.java`).
  That release also did not enforce directory exclusion.
* A fix touches the stream format, a Pub API signature, or needs a
  design choice: yes, how to share the lock registry across isolated
  class loaders, or explicitly constrain supported deployment. No
  stream-format or Pub API signature change is inherently required.
* Proposed fix, not made: put directory ownership in a registry or lock
  service shared across the JVM's class loaders and all library copies,
  and refuse before opening the lock file. Do not rely on closing an
  overlapping handle to be harmless. Add this cross-loader/native-lock
  regression alongside the ordinary same-loader check.

### R2-F2. A cut at the current length throws an internal Bug, including on an empty stream

* Where: `java/src/bergdb/stream/FileStream.java`, `pretruncate()`,
  lines 425-439 at BASE.
* Intended: `AppendOnlyStream.pretruncate()` accepts a discard frontier
  within the stream; only a frontier greater than its length is refused.
  How much storage to reclaim is the implementation's choice. Keeping
  the last backing file is compatible with that contract.
* Actual: at `pos == getLength()`, every file satisfies
  `spos + fileLength - 1 < pos`. This includes the initial empty file
  at position zero. `newSize` becomes zero and the method throws `Bug`.
* Effect: a legal cut request fails as an internal error. Through
  BufferedStream's pending-cut path it can fail the storage instead of
  accepting the frontier. The ordinary database reclaim policy normally
  cuts behind its current tail, so that policy does not establish a
  trigger for this boundary by itself. No data is removed by this
  exception at BASE, and subsequent direct stream operations still work.
* Evidence: `R2/CutEndProbe.java`. From the review root:

  ```sh
  javac --release 17 -cp repo/java/build/bergdb.jar -d out/R2/classes out/R2/CutEndProbe.java
  java -ea -cp out/R2/classes:repo/java/build/bergdb.jar bergdb.core.CutEndProbe out/R2
  ```

  Both cuts fail: `Unexpected newSize: 0. pos=0, kfiles.length=1` and
  `Unexpected newSize: 0. pos=3, kfiles.length=1`; read/append afterward
  succeeds (`R2/CutEndProbe.output.txt`). The probe closes the stream.
* In 2026.1: yes. Its pretruncate has the same selection and `newSize`
  check, and deletes the selected files before throwing; BASE at least
  checks before deleting (`git show release-2026.1:java/src/bergdb/stream/FileStream.java`).
* A fix touches the stream format, a Pub API signature, or needs a
  design choice: no.
* Proposed fix, not made: exclude the last file from the removal loop.
  A cut at length can keep that file, including when empty, as it keeps
  partial files already. Test empty and nonempty streams and a cut
  deferred by BufferedStream to exactly its next flushed length.

### R2-F3. Unchecked failures during open leak handles; an Error also strands the directory lock

* Where: `java/src/bergdb/stream/FileStream.java`, constructor,
  lines 205-213; `openForRw()`, lines 1032-1049 at BASE.
* Intended: 005-63, "The lock file", point 5, explicitly requires a
  failed open to release the directory lock. 011-07, "Production
  changes", requires failed construction to release opened files.
* Actual: `openForRw()` only closes its unpublished writer handle on
  `IOException`. An unchecked exception escapes with that handle still
  open, and `closeAfterFailedOpen()` cannot find it in `dbFiles` because
  publication has not happened. For `Error`, even the outer constructor
  cleanup is skipped: the lock handle stays open and the directory key
  stays in `LOCKED_DIRS`. No FileStream is returned to the caller to close.
* Effect: repeated unchecked failed opens leak descriptors. After an
  Error during construction, an immediate valid open is refused as busy
  although no database started. Even if a cleaner eventually closes the
  unreachable lock handle, nothing removes the static registry entry.
  There is no public cleanup handle. The outer Pub builder cannot fix
  this: `openDirs()` registers a stream only after its constructor returns.
* Evidence: `R2/FailedOpenProbe.java` injects a checked exception, a
  runtime exception and an Error at the first new file's force through
  FileStreamIo, the production fault-injection boundary. From the review
  root:

  ```sh
  javac --release 17 -cp repo/java/build/bergdb.jar -d out/R2/classes out/R2/FailedOpenProbe.java
  java -ea -cp out/R2/classes:repo/java/build/bergdb.jar bergdb.core.FailedOpenProbe out/R2
  ```

  `R2/FailedOpenProbe.output.txt`: checked failure leaves its data handle
  invalid and allows reopen; runtime failure leaves the handle valid;
  Error leaves the handle valid and reopen throws `DirectoryInUseException`.
  The probe closes captured data handles. No Db is started; the
  unreachable directory lock from the failed constructor ends at JVM exit.
  This verifies cleanup control flow, not the frequency of such failures
  on a particular device.
* In 2026.1: yes for the unpublished-handle leak: its constructor and
  `openForRw()` have the same catch coverage. No for the stranded
  directory registry, introduced with 005-63; 2026.1 had no registry.
  Checked with `git show release-2026.1:java/src/bergdb/stream/FileStream.java`.
* A fix touches the stream format, a Pub API signature, or needs a
  design choice: no.
* Proposed fix, not made: clean up the local DbFile on every unsuccessful
  `openForRw()` exit, and run constructor cleanup for `Error` as well as
  checked and runtime exceptions. Preserve and rethrow the original
  failure, adding cleanup exceptions as suppressed exceptions. Release
  the directory lock even if closing a data handle fails.

### R2-F4. setMax2G(true) can still create a backing file larger than two billion bytes

* Where: `java/src/bergdb/stream/FileStream.java`,
  `determineFileSizeIndex()`, lines 970-987 at BASE, and
  `determineFileSizeIndexFromFiles()`, lines 738-758.
* Intended: `setMax2G()` Javadoc, lines 366-374: never use stream files
  larger than 2e9 bytes, for filesystems with a file-size limit.
* Actual: after reopen, the capacity is chosen from the actual lengths
  of the last two files. Repeated short writes followed by reopen can
  leave that capacity at 100 MB while the retained stream grows to
  40 GB. At its next aligned rotation the size rule jumps directly to
  the 10 GB target. The cap checks the old index, not the chosen result,
  so it does not clamp that jump. Appends keep growing the new file
  toward 10 GB despite max2G being true.
* Effect: the promised cap is exceeded. A filesystem with a per-file
  size limit can refuse a write and fail the database even though smaller
  backing files would work.
* Evidence: `R2/Max2GProbe.java`. Its entire prefix is generated through
  public FileStream methods: 400 rounds of 100 MB and close/reopen, with
  max2G set on every opened stream, followed by 2,001 MB of appends.
  Its FileStreamIo extends zero-filled files sparsely and skips forces
  to avoid writing 42 GB to the device; file creation, selection,
  accounting, rotation, channels and close use production code. This is
  a file-size test, not a durability test. From the review root:

  ```sh
  javac --release 17 -cp repo/java/build/bergdb.jar -d out/R2/classes out/R2/Max2GProbe.java
  java -ea -cp out/R2/classes:repo/java/build/bergdb.jar bergdb.core.Max2GProbe out/R2
  ```

  `R2/Max2GProbe.output.txt`: before the last appends, 460 files, largest
  100,000,000 bytes, length 40,000,000,000; afterward 461 files, largest
  2,001,000,000 bytes, `Cap respected: false`. No giant byte array is
  allocated. Every stream is closed and sparse files are removed.
* In 2026.1: yes; the size-selection and cap logic is identical
  (`git show release-2026.1:java/src/bergdb/stream/FileStream.java`).
* A fix touches the stream format, a Pub API signature, or needs a
  design choice: no.
* Proposed fix, not made: clamp the selected `result` to `INDEX_2G`
  when max2G is true, rather than testing `currentFileSizeIndex`.
  Add a regression where a reopen-selected small capacity jumps over
  the cap at an aligned large retained length.

### R2-F5. A negative append length corrupts the stream's length bookkeeping

* Where: `java/src/bergdb/stream/FileStream.java`, `append()`, lines
  268-291; `DbFile.append()`, lines 1329-1372 at BASE.
* Intended: `AppendOnlyStream.append()` promises
  IllegalArgumentException for a negative length. Its getLength()
  contract says the length always increases; existing appended bytes
  remain readable unless cut.
* Actual: no entry check rejects negative `len`. DbFile chooses it as
  `toAppend`, skips the write and force because it is not positive, then
  adds it to `fileLength`. With assertions enabled the consistency assert
  throws after that mutation. Without assertions it returns the negative
  count, FileStream also decreases its total length, and append returns
  normally. Neither path produces the promised argument refusal.
* Effect: a caller's bad argument hides previously appended bytes and
  leaves the stream unusable for its next valid append. With assertions
  enabled getLength still reports three bytes while the third byte is
  unreadable; without assertions the length actually decreases to two.
  Physical bytes remain on disk, so this is corruption of the live
  bookkeeping, not a demonstrated loss after reopen. No normal Db API
  trigger for a negative storage length is established here.
* Evidence: `R2/NegativeAppendProbe.java`, run both with and without
  assertions. From the review root:

  ```sh
  javac --release 17 -cp repo/java/build/bergdb.jar -d out/R2/classes out/R2/NegativeAppendProbe.java
  java -ea -cp out/R2/classes:repo/java/build/bergdb.jar bergdb.core.NegativeAppendProbe out/R2
  java -cp out/R2/classes:repo/java/build/bergdb.jar bergdb.core.NegativeAppendProbe out/R2
  ```

  `R2/NegativeAppendProbe.output.txt`: with assertions, `Negative append:
  AssertionError`, reported length 3; without assertions, `Negative
  append: returned normally`, reported length 2. Both report
  `Previously committed last byte: EOFException` and `Next append:
  IOException`. The probe closes the failed stream and removes its files.
* In 2026.1: yes; the append argument handling, negative update and
  post-update assert are the same
  (`git show release-2026.1:java/src/bergdb/stream/FileStream.java`).
* A fix touches the stream format, a Pub API signature, or needs a
  design choice: no.
* Proposed fix, not made: reject invalid lengths before finding or
  mutating any DbFile, with IllegalArgumentException as documented.
  Validate the complete source range before the first chunk, too.
  Verify that rejection leaves length, readable bytes and the ability
  to append unchanged, with assertions both enabled and disabled.

## 3. Doubts

### R2-D1. Failure to start the cut thread may strand close()

`pretruncate()`, lines 452-460, stores `cutThread` before `Thread.start()`.
If starting the native thread throws (for example, thread-resource
exhaustion), no code resets the field or starts a replacement. The files
are already off the published list, and `awaitCutThread()` then has a
non-null thread for which no worker will run or notify. This could hang
`close()`. Not verified: exhausting native threads would disturb the
shared machine, and there is no thread-factory injection point. A hook
that makes thread start throw, followed by a bounded close check, would
verify it. This is a doubt, not a registered fault.

## 6. Shared fields

This inventory covers the five assigned implementation files, including
FileStream's embedded test classes. The separately named Core/stress
testers are supporting test code read for coverage, not additional
production ownership. `FileStreamIo` is stateless; AppendOnlyStream has
no fields. The two assigned exception classes add only immutable
serialization constants.

Thread names below: O = opening/configuring thread; W = append writer
(normally BufferedStream's consumer); P = cut caller; D = FileStream-cut;
R = reader; C = close caller. The AppendOnlyStream contract serializes
non-read callers; construction/configuration must be safely handed to
the consumer and readers. In the database, Thread.start and the buffer's
publication/monitor handoffs supply that initialization edge. Every
DbFile is fully initialized before its array is published, except the
constructor's private array, filled before FileStream itself escapes.
The assertions about stale values below assume this required initial
publication. No jcstress test was added or run.

* `SUFFIX` (FileStream): class initializer writes the final immutable
  string; O/W/static-query threads read it plainly. Class initialization
  happens-before use; no stale mutable content. Tests: restart/name tests.
* `BYTES_PER_INDEX_UNIT` (FileStream): final long from class initialization;
  O/W/P read plainly, initialization edge, no later writer or tearing.
  Test: `testReopenPast214TB`.
* `M` (FileStream): immutable constant used to initialize sizes; class
  initialization/constant-value semantics; no later writer. Test: none
  specifically for sharing.
* `G` (FileStream): as M, immutable size constant; no later writer.
  Test: none specifically for sharing.
* `SMALLEST_FILE_SIZE` (FileStream): class-initialized final long; O/W/P
  read plainly, no subsequent writes. Test: seek/name tests; no race test.
* `FILE_SIZES` and its elements (FileStream): final array, populated by
  class initialization and never mutated; O/W and test callers read
  plainly. Class initialization publishes elements; no stale mutation.
  Tests: size rules and `Max2GProbe` (F4 is logic, not publication).
* `FACTOR_UP` and its elements (FileStream): class-initialized final
  array, only read by tests; immutable after initialization, no race.
  Test: `testConstants` (read, not run in this review).
* `INDEX_2G` (FileStream): immutable constant, read by size selection and
  test callers; constant semantics, no mutable state. Test: `Max2GProbe`.
* `LOCK_NAME` (FileStream): immutable constant read by O; concurrent
  constructors share no mutable string state. Test: `testSecondStreamRefused`.
* `LOCK_POS` (FileStream): immutable long constant used by O; no writer
  after class initialization. Test: native checks in `LockLoaderProbe`.
* `LOCK_TEXT` (FileStream): immutable constant read by concurrent O
  callers; no mutation. Each new file gets its own output stream.
  Test: `testLockFile`.
* `LOCKED_DIRS` and its HashSet (FileStream): final reference initialized
  by the class initializer; O adds before opening the lock file, C/failed
  O removes. Every set operation uses the synchronized-set monitor, so
  add/remove operations are atomic and ordered across those threads.
  There is no unsynchronized iteration. That edge is per defining class
  loader, not JVM-wide (F1); an Error can strand an entry (F3).
  Tests: `testSecondStreamRefused`, `testRestartMissingFile`,
  `LockLoaderProbe`, `FailedOpenProbe`.
* `dir` / FileStream's File object: final reference to an immutable
  pathname, assigned by O, read by O/W/D/C and static query callers.
  Safe construction publication orders the reference and path state.
  The filesystem namespace has separate I/O ordering, not a Java-field
  race. Tests: cut, reopen and lock probes.
* `io` / FileStreamIo object: final reference assigned by O, used by
  O/W/D/C and R on channel reopen. Publication orders the reference;
  production FileStreamIo has no mutable fields. Subclasses must protect
  their own state. Tests: HeldIo, model I/O, attached probes.
* `firstPos` (FileStream): volatile long written by O/seek and P under
  the stream monitor; read by R and W through getFirstPos. Volatile
  ordering prevents tearing. P writes it before volatile `dbFiles`;
  a reader finding no file reads firstPos afterward. A reader holding
  an older array is protected by each file's volatile isDeleted flag.
  Tests: below-first/deleted-file tests and cut test.
* `length` (FileStream): volatile long initialized by O/seek, incremented
  by the single W after each valid forced file chunk; P reads it for its bound.
  Volatile ordering prevents tearing; += relies on the single-writer
  contract. No reader must use a length beyond its published append.
  Tests: append/reopen tests; force ordering checked in source. F5 is
  the unchecked negative-length exception to monotonicity.
* `fileSizeIndex` (FileStream): plain int written by O and then W.
  Initial handoff and serialized non-read calls order it; no R reads it.
  There is no claim of concurrent append writers. Test: `Max2GProbe`.
* `renameAsDelete` (FileStream): plain boolean initialized false by O,
  read by D in delete; no setter or later write exists. Thread.start
  publishes the initial value. No stale change is possible in current
  code. Test: none for the unused rename branch.
* `max2G` (FileStream): O/configuration writes under the FileStream
  monitor; W reads plainly in size selection. Initial Thread.start or
  externally serialized non-read handoff is required; the setter's
  monitor alone does not order a simultaneous unsynchronized reader.
  Concurrent configuration during append is not promised by the
  AppendOnlyStream concurrency contract. Test: `Max2GProbe`, not jcstress.
* `dbFiles` / its arrays (FileStream): volatile reference; W publishes
  after forcing a new file/name, P publishes after marking removed files
  deleted; both replacements are under the stream monitor. R takes one
  volatile snapshot in findFile and reads its immutable elements/positions.
  Volatile publication supplies initialization visibility. Old snapshots
  remain valid objects and detect removal through isDeleted. Constructor
  array filling happens before external publication. Tests:
  `testReadDuringNewFile`, below-first/deleted-file and cut tests.
* `cutFiles` / ArrayDeque (FileStream): final reference; P adds, D
  peeks/removes, C copies after awaiting D, all under the stream monitor.
  Monitor release/acquire and Thread.start order its mutable contents.
  No stale deque access is used. Tests: cut/deletion-failure tests.
* `cutThread` / Thread (FileStream): O initializes null; P creates,
  stores and starts, D clears and notifies, C/awaitDeletes loops and
  waits; every field access is under the stream monitor. Wait releases
  the monitor and reacquires it before checking. No stale value in the
  ordinary path. Failed start is D1. Test: `testCutOnItsOwnThread`.
* `ioException` / failure object (FileStream): volatile reference written
  by O/W/R/D/C failure paths, read at operation entry and close. Each
  exception is constructed before its volatile store; reads see a
  published exception. It never goes back to null. Competing failures
  may replace its cause, but do not make the stream usable again.
  Tests: `testFailedDeleteOfACut`, power-loss failure tests. No test
  establishes which of simultaneous failures wins.
* `lockFile` / its RandomAccessFile, channel and OS FileLock
  (FileStream): O opens and stores under the stream monitor; C releases
  under the same monitor after file close/deletion work. The monitor
  orders its Java reference. The kernel lock protects other processes;
  the static set protects overlapping opens within one loader. The local
  FileLock is not subsequently used; the open handle retains the kernel
  lock. F1/F3 are exclusions to correct lifetime. Tests: lock probes.
* `lockKey` (FileStream): O stores and C clears under the stream monitor;
  only the owning instance uses its key to remove the static-set entry.
  Same monitor orders reads/writes; no stale-key removal in the normal
  path. Tests: same-loader/refused-open and failed-open probes.
* `this$0` / enclosing FileStream reference (DbFile): implicit final
  reference installed by O/W before DbFile publication; R/W/D/C use it
  for I/O, failure state and directory. Array publication / Thread.start
  orders it; no mutation. Tests: all concurrent FileStream tests.
* `file` / File object (DbFile): final immutable pathname set before
  publication; R/W/D/C read it plainly. Final-field and publication edges;
  mutable namespace state is governed by delete/reopen ordering.
  Tests: deleted-file/cut/reopen tests.
* `rfile` / writer RandomAccessFile (DbFile): O creates before publication;
  W seeks/writes/forces/replaces on interrupt and closes on rotation;
  C/D close it. After publication, access uses the DbFile monitor.
  `force()` without that monitor is only used before publication.
  R never touches it. Monitor edges prevent racing seek/write/close.
  Tests: read-during-force, interrupt tests, `FailedOpenProbe`.
* `channel` / FileChannel (DbFile): volatile reference installed before
  publication; R snapshots it, and an R reopens under channelLock after
  a closed-channel exception. C/D close under channelLock. Volatile
  publication and channelLock order replacement with close; channel's
  own API orders in-flight reads against close. A stale channel reference
  throws and retries, or sees closed/deleted state. Tests:
  `testReadsAndInterrupts`, `testReadOfClosedFileFailsAlone`.
* `channelLock` / monitor object (DbFile): final object, created before
  publication; R reopen and C/D close acquire it. Monitor release/acquire
  serializes channel replacement and permanent close; ordinary reads
  take no such lock. Tests: closed-file and interrupt tests.
* `fileLength` (DbFile): volatile long initialized by O/W before
  publication and increased by W after a valid force; R and P read it. Volatile
  store publishes the permitted physical read extent. A concurrent read
  of older data remains within the old extent; the buffer publishes
  newly flushed ranges only after append completes. Tests: read-during-
  force/new-file and durable-prefix tests; F5 covers the negative update.
* `isRw` (DbFile): plain boolean initialized before publication, W/C/D
  change under the DbFile monitor; append reads it under that monitor.
  Monitor/initial-publication edges order operative reads. toString's
  plain debug read could be stale but makes no storage decision.
  Tests: rotation/reopen tests, no dedicated race test.
* `spos` (DbFile): final long, initialized before publication, read by
  R/W/P/D/C. Final-field/volatile-array publication prevents tearing or
  stale initialization. Never changes. Tests: cross-file/cut/reopen tests.
* `maxSize` (DbFile): initialized and finalized in value before
  publication; W reads it under the file monitor, no later writes.
  Initial publication supplies visibility. Plain toString read is debug
  only. Test: `Max2GProbe`.
* `isClosed` (DbFile): volatile boolean set by C/D before closing the
  channel; R checks before reading and while reopening under channelLock.
  False read before a concurrent close is safe: the read completes or
  its closed channel leads to a second state check. Tests:
  `testReadOfClosedFileFailsAlone`.
* `isDeleted` (DbFile): volatile boolean set by P before removing the
  file from the list, and by D before close/unlink; R checks initially
  and while reopening. Volatile ordering and the close/reopen monitor
  prevent an interrupted reader reopening after deletion. A read already
  in progress may finish or expire as the contract permits. Tests:
  below-first/deleted-file tests and cut test.

Embedded test-only fields and shared objects:

* `holdForce` (HeldIo): main test thread writes the volatile latch
  reference; writer reads it. Volatile/Thread.start publishes the latch,
  and countDown/await orders release. Test: read-during-force.
* `holdDirectoryForce` (HeldIo): main writes volatile, writer/D reads;
  latch and volatile edges as above. Tests: new-file and cut tests.
* `holdDelete` (HeldIo): main writes volatile, D reads; latch/volatile
  edges as above. No selected test sets this branch.
* `held` (HeldIo): final CountDownLatch; I/O worker counts down, main
  awaits. The latch publishes worker progress before main proceeds.
  Tests: held-force/new-file/cut/closed-read tests.
* `readOpens` (HeldIo): final AtomicInteger; O/R increment and test main
  reads; atomic operations order the count. Test: reads/interrupts.
* `lastRead` (HeldIo): volatile channel reference written by O/R and
  read/closed by main; volatile publication orders it. JDK channel close
  is safe against read. Test: reads/interrupts.
* `failDeleteAt` (HeldIo): main writes volatile before D starts; D
  reads volatile; no stale failure index. Test: failed-delete.
* `deletes` (HeldIo): plain int incremented only by D; main reads after
  awaitDeletes acquires the stream monitor following D's completion and
  notify. That edge orders the count. Test: failed-delete.
* `holdRead` (HeldReadIo): main writes volatile, one test reader reads
  and clears it. Latch/volatile edges stop that reader before close;
  this helper is not used with competing held readers. Test:
  `testReadOfClosedFileFailsAlone`.
* `ch` / delegate channel (HeldReadIo.HeldChannel): final reference
  published through DbFile.channel; R reads and C closes it. JDK channel
  lifecycle supplies operation ordering. Test: closed-file.
* Enclosing HeldReadIo/HeldIo references of HeldChannel: implicit final
  references, safely published with the channel; reader accesses the
  shared volatile holdRead and the latch. Test: closed-file.
* `r` / Callable (Run): final reference set by main before start;
  Thread.start publishes its captured FileStream, byte arrays and
  latches to the worker. They use the protocols listed here. Tests:
  held I/O and closed-file tests.
* `failure` (Run): worker writes volatile Throwable; main reads after
  join. Volatile and join both publish the result; no stale success.
  Tests: all Run.finish users.
* Captured source/expected byte arrays in the embedded concurrent tests:
  main fills them before Thread.start, then worker and main only read
  them. That start edge publishes contents; there is no later mutation.
  Each read's destination array/ByteBuffer is reader-private. Tests:
  read-during-force/new-file/cut and reader/writer tests (latter read only).
* Local `hold` CountDownLatch in the closed-file test: main and reader
  share via Thread.start; countDown/await orders release, and join orders
  the final failure check. Test: closed-file.
* Local `published` AtomicLong in the reader/writer f-test: main writes
  after append; R reads atomically before choosing ranges. Release/
  acquire publishes completed append state. Test read, not run here.
* Local `stop` AtomicBoolean in that f-test: main writes; R loops on
  atomic reads; release/acquire orders termination, then join orders
  results. Test read, not run here.
* FileStreamIo has no instance or static fields; caller-supplied source
  and destination storage is not retained. Production BufferedStream's
  shared ring source is protected by reservation until append returns;
  its monitor orders reuse. Read destinations are owned by their caller.
* `serialVersionUID` (DirectoryInUseException): immutable static final
  constant; serialization/class initialization semantics, no writer.
  Test: none for sharing.
* `serialVersionUID` (ReadBelowFirstPosException): immutable static final
  constant, no writer. Test: none for sharing.
