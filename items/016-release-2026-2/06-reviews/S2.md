### S2-F1. An ICU collator is used by several threads at once, and gives wrong sort bytes
* Where: `src-icu/bergdb/pubimpicu/IcuKCollator.java`, `getSortBytes`, line
  19 (`collator.getCollationKey(s)`), on the one `IcuKCollator` of the
  `FieldIndexFunction` of the index manager's `Index`. Its callers run
  without a lock: `RwEnvironmentImp.indexEntries` (line 304) in the thread
  of every writer, before `Db.execute`, through
  `FieldIndexFunction.createIndexEntry` (line 80), and the build's thread
  (`IndexBuilderImp.createStep`, line 451, on the same `Index`). (A
  reader's `eq`, `startAt` and `prefix` use the collator of a new `Index`
  that `getActiveIndex` makes for each `useIndex`, not shared.)
* Intended: `Connection`'s class Javadoc: one connection per thread for
  multi-threaded access; an index holds an entry for each object, by the
  collation of its type (`IndexBuilder.type`). ICU4J's `Collator` is not
  thread-safe unless frozen; this one is not frozen.
* Actual: in `S2IcuThreads`, four threads that call `getSortBytes` of one
  `string/sv` collator for 3 s get other sort bytes than the same string
  alone in 5,509,844 of 5,755,790 calls, and an exception in 125,285.
* Effect: wrong index entries: lost and invented data in the index. In
  `S2IcuIndexProbe`, four threads, each with its own connection, put 1,500
  objects each to a directory with a `string/sv` index (`createFast`):
  "objects stored 6000, put errors 0, objects that eq() on their own name
  does not find 15". With `string/unicode` (no ICU) the count is 0. An
  entry with wrong sort bytes stays: a later put or delete of the object
  computes the old entry's key again, and deletes another key. A put or a
  read can also throw the collator's exception (none in this run).
* Evidence: probes `S2/S2IcuThreads.java` (run as `bergdb.pubimp.S2IcuThreads
  string/sv`) and `S2/S2IcuIndexProbe.java` (`S2IcuIndexProbe string/sv`,
  and `string/unicode` for the control), outputs above.
* In 2026.1: yes (`IcuKCollator` unchanged; `FieldIndexFunction` and
  `RwEnvironmentImp.indexEntries` the same).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no. Indexes built with wrong entries stay wrong until rebuilt.
* A fix: `IcuCollatorFactory.createCollator` freezes the collator
  (`collator.freeze()`, ICU4J's thread-safe form) or `getSortBytes` is
  `synchronized`; a test with threads, as `S2IcuThreads`.

### S2-F3. A String or byte[] put over an object leaves its index entry; the key can then not be deleted
* Where: `pubimp/RwEnvironmentImp.java`, `put(String, Object)`, lines 279
  and 281 (`setBytes`, no index work), and `indexEntries`, lines 336 to
  345 (the previous value must be a `DbObject`).
* Intended: `Connection.put`: "If an entry with the given key already
  exists, it is overwritten"; `Connection.delete`: deletes the entry; an
  index holds the entries of the objects in its directories.
* Actual: a `String` or a `byte[]` value is a plain KV put (`kvOps`):
  the index entries of the object it replaces stay. A later put of an
  object, or a delete, of an object key (no suffix) in an indexed
  directory parses the previous value as a `DbObject` and throws
  `DataFormatException` when it is a String or other bytes.
* Effect: wrong answers, a scan that fails, and a key that cannot be
  deleted. `S2BytesOverObject`: the bytes of an object of v = 7 put over
  an object of v = 1: "eq(1) [7], eq(7) []"; "hello" put over an object:
  "scan throws bergdb.pub.ObjectCreationException: bytes too short, 5
  ukey=/p/2", "delete /p/2 throws bergdb.pub.DataFormatException: bytes
  too short, 5 For ikey: '/dp/-2'.; exists true", and the put of an object
  to it throws the same. Every later scan of the index over that entry
  throws; the key can be deleted only after a put of an object's bytes
  (a `byte[]`) over it, and the old entry stays. The delete is refused
  before the go point, so the database goes on.
* Evidence: probe `S2/S2BytesOverObject.java`.
* Test: `PubTesterIndex.testS2StringOverObject`: "bergdb.pub.DataFormatException:
  bytes too short, 5 For ikey: '/dpayments/-1'." (the delete).
* In 2026.1: yes.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: a design choice: whether a String or byte[] may replace an
  object at an object key in an indexed directory (then it deletes the
  object's entries, and a previous value that is not an object has none),
  or is refused.
* A fix: `put` of a String or byte[] to an object key goes through
  `objectOps` as a value with no index entries; `indexEntries` takes a
  previous value that is not a `DbObject` as one with no entries (as
  `IndexBuilderImp`'s stop condition does with `isProbablyDbObject`).

## 3. Doubts

* D1. A build's thread that meets an exception it does not catch (only
  `StreamIoException`, `DbStoppingException`, `DbFailedException` are):
  for example a stored object whose top level parses and whose nested
  field does not (`BadFormatException` from `FieldIndexFunction` through
  `setIndexEntry`), or an `IllegalDbStateException`. The thread ends, the
  job of `start()` says "Working" (-1) for ever, and the index stays
  creating until the next start, where the same object stops it again.
  Seen for a null string (S2-F26); for the other causes not verified: it
  needs such an object made by hand.
* D2. For S2-F13's fix with ICU: whether the primary weights of a prefix
  are a byte prefix of those of the longer strings at L1 for every
  supported locale (contractions, as Czech "ch"; ICU's compression of
  primary lead bytes). A probe over a word list per locale would tell.
* D3. For S2-F1's fix: whether ICU4J 50's `freeze()` makes
  `getCollationKey` safe for threads (ICU's documentation says a frozen
  collator is); `S2IcuThreads` on a frozen collator would tell.
* D4. `IndexCreateState.isDone` is set without the monitor in
  `createStep`'s catch of `DbStoppingException` (line 468) and read by
  `getJobStatus` under it: another thread may not see it. Harmless beside
  S2-F11; no test.

## 6. Shared fields (R1, R2, R4 and R5; 016-07, section 3)

S2 is none of these reviews; the fields of this area that more than one
thread uses:

* `IcuKCollator.collator` (not final): written at construction, published
  with its `Index` under `IndexManager.lock`; the one of the manager's
  `Index` is used by every writer and the build's thread without a lock. ICU's unfrozen collator has
  mutable state: S2-F1. Test: `S2IcuThreads`.
* `IndexManager.nameToIndex`, `dirToActiveIndexes`: written and read under
  `lock`; the arrays of `dirToActiveIndexes` are replaced, never changed,
  so a reader's array is stable after the lock.
* `Index.state`: written under `lock` (`setIndexStateToActive`,
  `ensureDeletingState`; `Data.createIndex` before publication); read by
  `getState()` under it; `getStateString()` reads it plain, for messages.
* `Index.deletionJob`: under `lock` (015-21).
* The writer's index set (`getActiveIndexesForDir`, under `lock`) and its
  read time (set later, at the first read): no order between them and a
  deletion's commit: S2-F12. Test: `S2DeleteRaceProbe`.
* `IndexCreateState`: `update`, `stop` and `getJobStatus` synchronized;
  `startKey`, `dirId` used by the build's thread only; `isDone = true`
  plain in `createStep` (D4).
* `IndexBuilderImp.testHook`, `DatabaseImp.testHookDelete`: volatile.
  `createInThread_waitEvent`: plain, set and read on the caller's thread
  before `Thread.start`.
* `IcuInfo.hasIcu`: plain, written before the volatile `isSet`, read after
  it: ordered.
* `KvToObjectImp.factories`: synchronized; a `BlankConstructorFactory`'s
  constructor is published through it.
* `DbObject.PATH`: a `ThreadLocal`.
