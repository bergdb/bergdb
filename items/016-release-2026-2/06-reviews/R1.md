## 2. Faults

### R1-F1. After a growth, a reader can see a key node's arrays without their contents

* Where: `dag/KeyNode.java`, `growCapacity` (lines 914 to 947 at BASE),
  called by `ensureCapacity` (903) from `addKlong`, `addToEnd` and
  `addToSorted`; `setContentFrom` (1004, the same pattern); the readers:
  the searches (`searchEq` 361, `searchLte`, `searchLt`, `searchGt`,
  `searchGte`, `searchFirst`: `sz = this.size; klongs = this.klongs;`),
  `getPointerNode`, `getPointerPos`, `getPointee` and
  `NodeCollection.pointsToIndexNode` (763), which read the array fields
  plainly.
* Intended: KeyNode's class comment: the used part of the arrays "only
  grows. Existing data in them does not change. ... Once KeyNode.size is
  increased by the writer, all writes are visible for the readers as they
  read the KeyNode.size field." 009-02, 3.3, row "node arrays": written by
  the writer plainly before `size`, read after `size`, "published by
  `size`".
* Actual: a growth makes three new arrays, copies the used part into them
  with `System.arraycopy` (plain stores) and stores the three fields
  (plain stores, under the node's monitor, which readers do not take). A
  reader that read `size` before the growth, and then reads `this.klongs`
  (or `pointers`, `pos`) after it, sees the new array through a data race:
  no happens-before edge orders the copy before its reads, and on AArch64
  the field's store can become visible before the copy's stores. The
  reader then reads default elements below `size`: a klong 0, a null
  pointer, a reference 0.
* Effect: a wrong answer, rarely (see Evidence). A klong 0 is a time
  klong of time 0: a search
  takes it for a time at or before its lookup time and goes on, so the key
  klong that was there is not seen. `searchEq` misses a key that the node
  has had since long before the reader's lookup time (a get returns no
  value for a key that has one); `searchLte` and the others can choose
  another key, so a get or a scan descends into the wrong child. If the
  klong not seen is a time klong after the reader's lookup time (that of
  a later transaction, or of the transaction in progress, where every
  reader stops: KeyNode's class comment), the search goes on past it and
  returns a value of that later transaction: a read of a value that was
  not committed at the lookup time, or not committed at all (a
  transaction that fails afterwards). `setContentFrom` can give the same
  for a node split in place that readers reach (one that was empty before
  the transaction): a reader that read its size before may see its first
  klong, the time klong of the transaction, as 0 and read that
  transaction's klongs (the same mechanism; not probed apart). A
  reference 0 or a null pointer only sends the follow to the slow path
  (the pair under the monitor, which orders the growth before it); for a
  get that throws instead, see D1. Seen on AArch64 (F53; any ARM server
  would do the same). x86 (s1) does not reorder stores in the hardware;
  there only the JIT could, as nothing forbids it to move the field's
  store before the copy's.
* Evidence: three probes, in `R1/`, run on F53 at BASE (load average
  about 30 from other sessions):
  * `GrowRace.java` (a writer fills fresh key nodes to 62 klongs, growths
    at 2, 6, 14 and 30; a reader reads `size`, then the arrays):
    `java -cp build/bergdb.jar:. GrowRace 20` printed `reads 1873956118,
    klong 0 below size: 154, null pointer below size: 133, reference 0
    below size: 29`.
  * `GrowSearch.java` (the same writer; the reader calls `searchEq` at time
    10 for key 1, which every node of size 2 or more has, with reference
    1008): `java -cp build/bergdb.jar:. GrowSearch 20` printed `searches
    476809405, key 1 not found: 8, found with a wrong reference: 1350`.
  * `GrowFuture.java` (leaves with key 1 at time 10, reference 1008, then
    time 20 and key 1 again, reference 2008, then 56 more keys at time 20;
    the reader searches key 1 at time 15 in each leaf of size 4 or more):
    `java -cp build/bergdb.jar:. GrowFuture 20` printed `searches
    1132092859, the value of time 20 at time 15: 3, key 1 not found: 8,
    another reference: 13`.
  The probes are of KeyNode alone, as the get path uses it (`Dag` calls
  the searches on the canonical nodes that the writer appends to). On a
  database the race is rarer: `R1/DbGrowProbe.java` (package bergdb.core;
  maxNodeSize8, no eviction, one put a transaction, two readers getting
  the last two committed keys) ran `java -Xmx6g -cp probes:build/bergdb.jar
  bergdb.core.DbGrowProbe 40` and printed `transactions 4000000, gets
  101226606, missing 0, wrong value 0, thrown 0`: no wrong answer in 40 s.
  So the fault is shown on the code a get runs, not yet as a get's answer.
* In 2026.1: yes (`growCapacity` is the same, with `Node[] pointers`).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no; a choice between the ways below (cost per search).
* A fix: publish the copies before the arrays. In `growCapacity`, a
  `VarHandle.releaseFence()` (or `storeStoreFence()`) after the three
  copies and before the three field stores orders them on every machine;
  by the JMM the readers also need an acquire read of the field (a
  `getAcquire` of `klongs`, `pointers` and `pos`, once per search and
  follow), or the three arrays in one holder object with final fields,
  whose freeze covers the copied contents for any reader that sees the
  holder (one more indirection per read). A jcstress test of the growth
  (the probe's two actors) checks it.

### R1-F2. The resident bytes count no handle, where 009-02, 4.7 counts them

* Where: `core/Residents.java`, `bytesOf` (the bytes an object is counted
  with: `getMemSize()` and the values its pointers hold) and `added`;
  `core/Cache3.java`, `liveOrNewHandle`, `register`, `install` (a live
  handle and its table entry are counted nowhere).
* Intended: 009-02, 4.7, "Handles are counted too. A live handle with its
  table entry counts as the table's (79 bytes, T1a). A dead handle stays in
  the pointers that hold it ... so each pointer of a resident object that
  holds a handle adds the handle's 32 bytes to that object's bytes"; the
  item's log of 2026-10-25, 19:10 records it ("the counting of handles'
  memory, dead handles included (4.7, open point 8)"). 009-02, section 9
  lists no change to it.
* Actual: no handle's bytes are counted: `bytesOf` of a key node with 30
  pointers that hold handles is its `getMemSize()`, and the table's
  entries (the handle, the `HashMap$Node`, the `Long`) are outside the
  estimate. `docs/levels.md`, section 7 describes the code ("each object
  with its values"), not 4.7.
* Effect: the capacity controller keeps the counted bytes at the budget
  while the heap holds the handles on top: in the probe below the rule of
  4.7 gives 49 percent more than the counted bytes (small key nodes; for
  large ones less). A database uses more memory than `cacheSizeInMb` says
  by that much; with small budgets and small nodes, about half again.
* Evidence: `R1/HandleBytesProbe.java` (package bergdb.core; 200
  transactions of 100 puts, the random schedule, reads, one random
  eviction): `java -ea -cp probes:build/bergdb.jar bergdb.core.HandleBytesProbe`
  printed `resident bytes (Residents): 2312775, resident objects 9775, live
  handles 9775`; `pointers of resident objects that hold a handle: 11842
  (dead 488, distinct handles 9869)`; `not counted, by 009-02 4.7's rule:
  1151169 bytes (49 percent of the resident bytes)`; `a key node with 30
  handle pointers: Residents.bytesOf 800, getMemSize 800`. (The rule of
  4.7 is an upper bound: it counts a live handle that a pointer holds
  twice. Without that, about 9,775 times 79 plus 488 times 32 bytes, 34
  percent, are held and not counted.)
* In 2026.1: no (no handles; 2026.1's Residents counted the objects
  only, not the table's entries).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: a design choice: count the handles as 4.7 says, or record in
  009-02, section 9 and levels.md, section 7 that the budget is for the
  objects and their values only, without the table and the handles.
* A fix: for 4.7's rule, `bytesOf` adds 32 for each pointer that holds a
  handle, and `added` and `released` 79 for the object's live handle
  (the table's entry), at the same places; `valueIn` and `valueOut` keep
  their meaning. Or the documents changed, if Frans prefers the
  estimate as it is.


### R1-F3. The fast path is not safe by the JMM, as 009-02, 3.4 says it is

* Where: `core/NodeCollection.java`, `followPointer` (188 to 199: the
  pointer read plainly by `getPointee`, the reference plainly by
  `getPointerPos`, the handle's object by its volatile read in
  `memoryObject`, 232), with `Handle.usable` (`dag/Handle.java`, 77);
  `dag/KeyNode.java` and `dag/TopNode.java`, `getPointee` and
  `getPointerPos`.
* Intended: 009-02, 3.4: a plain read of a pointer to a handle is safe
  under C1 to C4, "The argument is the JMM's, not the hardware's: it holds
  on x86 and on AArch64 alike"; point 4: the fast path "reads nothing of h
  that needs" an edge to whoever published h; 3.3, row `pos[i]`: "a stale
  value only sends the reader to the slow path, or names an older version
  that lemma M covers". KeyNode's class comment and levels.md, section 7
  repeat it.
* Actual: the argument covers the contents of the object that the read of
  `h.obj` returns, not which of the handle's objects it is. A live handle
  can hold an older version before a newer one is installed (an old
  reader's load into a new handle, then a newer reader's load into the
  same handle, which replaces it: `Cache3.install`, "a newer version").
  The newer reader raises the reference, installs, and then swizzles the
  handle into the pointer; a third reader that sees the swizzle through
  its plain read of the pointer has no edge to the raise or to the install,
  so by the JMM it may read the old reference and the old object, which
  `usable` accepts.
* Effect: by the JMM, a wrong answer: a version without a change that was
  committed before the reader's lookup time. Not on HotSpot today: the
  read of `h.obj` depends on the address the read of the pointer gave, and
  the installer's stores are ordered by its release (the volatile store
  and the release store of the swizzle), so x86 and AArch64 give the new
  object. The code relies on that dependency (as RCU's
  `rcu_dereference` does), which the argument does not name and the JLS
  does not promise.
* Evidence: the interleaving. Node y has versions at P1 and, later, W;
  x is resident, its pointer i holds nothing, its reference P1.
  1. Reader R_old (lookup time before T): fast path, nothing in the
     pointer; slow path, pair (null, P1) under x's monitor; id from the
     header; ref P1; `liveOrNewHandle` gives h_a (new, empty). It stops
     before `synchronized (live)` (450).
  2. The writer, under the write lock: follows x to y (pair (null, P1)),
     loads P1 into h_a, `setPointee(i, h_a)`, `makeCanonical`; transaction
     T changes y and commits (the volatile write of the clock). A record
     writes y at W; an eviction kills h_a (DEAD, writtenPos W, obj null,
     out of the table).
  3. R_old goes on: h_a dead, `liveOrNewHandle` gives h_b (new); under
     h_b's monitor it loads P1 and installs it (w0, a volatile write of
     h_b.obj); its swizzle of h_b expects null and fails (x's pointer holds
     h_a). h_b, in the table, holds the P1 version.
  4. Reader R1 (lookup time after T): pair (h_a, P1) under x's monitor;
     ref = newerPos(P1, W) = W; `raiseRef(i, W)` under x's monitor (w_r);
     live h_b; under h_b's monitor the P1 version is not usable for W, so it
     loads W and installs it (w1); `swizzle(i, h_a, h_b)` under x's monitor
     succeeds (w2, a release store).
  5. Reader R3 (lookup time after T, from a read of the clock after T's
     commit), on the fast path, without a lock: (a) the plain read of
     `pointers[i]` sees w2 (h_b); (b) the plain read of `pos[i]` sees P1
     (not w_r); (c) the volatile read of `h_b.obj` sees w0 (the P1
     version), ordered before w1 in the synchronization order.
     Happens-before: none from R1's w_r, w1 or w2 to R3 (R3 takes no
     lock, and a plain read of a release store makes no edge); T's commit
     happens before R3's reads, but w0, w_r, w1 and w2 come after it in
     their threads. So (b) and (c) are allowed by 17.4.5, and (a) seeing a
     write that no edge orders is the data race the JMM allows.
  6. `usable(P1 version, P1)` is true: R3 returns y's version at P1,
     without T's change, at a lookup time after T.
* In 2026.1: no (no handles; the pointer locks ordered every follow).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: a design choice: T6a (an acquire read of a pointer to a handle,
  one load-acquire per hop on AArch64) or T6b kept with the argument
  rewritten to rely on dependency ordering, as the code does now.
* A fix: for T6a, `getPointee` on the fast path as `getPointeeAcquire`
  for handles too (and TopNode's pointers by a VarHandle), and `pos[i]`
  read after it; the acquire then orders the raise (before the swizzle
  under x's monitor) and the install before both reads. A jcstress test of
  steps 3 to 5 (an old object installed, a raise, a newer install, a
  swizzle, against a fast-path reader) would show the forbidden outcome
  only on a JVM that breaks the dependency, so it documents rather than
  tests.


### R1-F4. A batch subtracts uncounted values, and a count driven to 0 stays 0

* Where: `core/Residents.java`, `valueOut` (155) and `grown` (114: "if
  (old == 0) return"); `core/Eviction.java`, `unswizzleValues` (666) and
  `unswizzleValue` (331), which the capacity controller's batches run on
  every pinned key node the hand meets; `core/Cache3.java`,
  `pointerCreated` (217) and `Db`'s `valueNodeCreated`, which call
  `Residents.added` for a value, which returns at once for a value.
* Intended: Residents' class comment: "a value a reader puts into, or
  eviction takes from, a pointer of a counted object moves that object's
  count (valueIn, valueOut) ... it does not drift, as every byte added is
  taken away with the object or the pointer it was added for"; a canonical
  object changed by the writer "is counted with its size at the last
  count" until its write, when `grown` counts it again. Cache3's
  `pointerCreated`: "a value counts as resident from here". levels.md,
  section 7: "Residents counts their bytes exactly, without walks: each
  object with its values, from when it enters a handle until it leaves it."
* Actual: a value the writer puts into a key node is not counted (the
  node's count is its size at its creation or last write). A batch's
  `unswizzleValues` takes every written value of a pinned (dirty) key node
  and `valueOut` subtracts each from the node's count, the values never
  counted included, down to 0. `grown`, at the node's next write, does
  nothing for a count of 0 (the sign of "not counted"), so the node stays
  counted 0 for as long as it is resident: its bytes, and those of the
  values that reads put into it later (`valueIn` also skips a count of 0),
  are missing from the resident bytes. A leaf that a split makes is
  registered empty (80 bytes) and then filled, so one batch while it is in
  D is enough.
* Effect: the capacity controller sees fewer resident bytes than there
  are, for good while such nodes stay resident, and the database uses
  more memory than its budget. Not a wrong answer. (The undercount of D's
  dirty nodes between their writes is by Residents' design, but levels.md
  calls the count exact; with the default startup distance, D's leaves
  can hold many values uncounted.)
* Evidence: `R1/ValueOutProbe.java` (package bergdb.core; the default
  schedule, BUDGET; 20 transactions of 1,000-byte values; one batch,
  `Eviction.sweep`, with the budget set to 1,000 bytes and then put back;
  400 more transactions; the leaves' counts against `Residents.bytesOf`,
  and the resident bytes against an exact count over a walk):
  `java -ea -cp probes:build/bergdb.jar bergdb.core.ValueOutProbe 100000 400`
  printed, after the batch, `[leaf 15531 dirty: counted 0, bytes 800]`,
  and at the end `leaf 15531 counted 0 after the batch: now clean, written
  at 54392, in its handle true, counted 0, bytes 2916`, with `resident
  bytes 1033517, exact 1299038` (the rest of the gap is the dirty leaves,
  `counted 80, bytes 21980` and the like). With a startup distance of
  50 MB (`... ValueOutProbe 50000000 30`): `resident bytes 968, exact
  72726` after 50 transactions.
* In 2026.1: no (2026.1's sweep made the count exact by walks, resync,
  after each sweep).
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no for the drift; whether D's dirty nodes are counted between
  their writes is a choice (levels.md says exact).
* A fix: keep "counted" apart from the size (a flag, or -1 for not
  counted), so that `grown` and `valueIn` count an object whose count
  reached 0; and count a value when the writer puts it into a counted
  object (`pointerCreated` calling `valueIn` under the holder's monitor),
  or let `valueOut` subtract only down to the holder's own `getMemSize()`.
  A unit test: the probe's steps, asserting the leaf's count equals
  `bytesOf` after its write. (The object counter drifts too: `released`
  of an object counted 0 does not decrement `objects`, and `added`, from
  `makeCanonical`, counts it once more.)


## 3. Doubts

* **D1. R1-F1's race in the slow path: a get that throws.** The slow path
  reads the pointer's pair under the predecessor's monitor, then calls
  `followStreamPointer`, whose `pointsToIndexNode` reads `klongs[i]`
  again, after the monitor (NodeCollection, 205, 389 and 763). A growth
  between the two (the writer appends to the node) can give it a new array whose
  copy it does not see (R1-F1): klong 0 is not a key, so the pointer to a
  key node is followed as a pointer to a value: `followValuePointer` reads
  the key node and, if the pointer holds nothing, casts it to `ValueNode`
  in `setPointee` (586 to 588): a `ClassCastException`, the get fails. Not
  verified: `R1/GrowFollowProbe.java` (package bergdb.core; a reader
  follows pointer 1 of each fresh inner node while the writer appends to
  it) printed `follows 18115206, not a key node: 0, thrown: 0` in 40 s:
  the window, between the monitor's exit and the second read, is too
  narrow to hit so. A probe that pauses the reader there (a hook) would
  verify it. R1-F1's fix covers it.
* **D2. A reader's `dropIfEmpty` against the writer's install.**
  `dropIfEmpty` (Cache3) tests `h.obj == null` and then kills h by a
  compareAndSet, without h's monitor. If the writer installs its version
  into h between the test and the compareAndSet (its load ends with
  LOADING to LIVE), the kill takes the writer's object, and the writer's
  `makeCanonical(live, result)` (NodeCollection, step 6) then puts the
  canonical object into the dead handle: a node whose canonical object is
  in no live handle, which eviction never sees and a resolve by id does
  not find (it makes a second object). Not verified, and not reachable as
  far as I found: a reader drops a handle only after a follow that kept
  nothing, which for an index node needs a cache policy that refuses it
  (`Dag.CACHE_NOTHING`, used by no caller; the readers' policy caches every
  index node) or a version cut back during the reconstruction, when no
  reader runs. A test with a `CACHE_NOTHING` reader paused in
  `firstTouchListener` and the writer's follow of the same node would show
  it. If it is reachable, `dropIfEmpty` should take h's monitor, or
  `makeCanonical` test the state.


## 4. Checked and right

* The slow path's order: the pair under the predecessor's monitor; the
  id (handle, vpos, header); Rule R; the dead handle's written position,
  which is visible because the reader saw the eviction's `obj = null`,
  a volatile write after the write of `writtenPos` in `kill`, and the state
  DEAD, written before it; `raiseRef` only raises (Spos.newer); the live
  handle under its map's lock; the load under the handle's monitor with
  LIVE to LOADING to LIVE in a `finally`; a dead handle re-resolved inside
  the loop; the swizzle a compare-and-set on what the reader read.
* The re-resolve inside the loop does not raise the reference by the
  newly dead handle's written position. Harmless: a reader's `live` is
  the pointer's handle only if it saw that handle live with an object not
  usable for the reference, and a live handle that a pointer holds always
  holds an object usable for the pointer's reference: it is swizzled in
  after an install usable for the raised reference, its object only gets
  newer (`install`, `register`, `makeCanonical` replace by "canonical or
  newer"), and the reference rises only while the pointer holds a dead
  handle or by Rule R, which every load applies. So the swizzle that could
  hide the written position never meets a pointer holding that handle.
* Eviction against a load: `evict`, `clockStep` and `dropIfEmpty` kill
  only by LIVE to DEAD, so never a handle being loaded, and read the
  object after the compareAndSet; an install happens only while LOADING.
  Two loads of one node serialize on its one live handle's monitor
  (`liveOrNewHandle` under the map's lock). No lock cycle: the orders are
  node monitor, then map lock (resolvePointers); handle monitor, then map
  lock (the re-resolve) or object monitor (Residents); map lock, then
  object monitor (kill). None takes a handle's monitor under a map lock.
* The node table: every access to a map is under that map's monitor
  (`liveHandle`, `liveOrNewHandle`, `register`, `evict`, `clockStep` with
  its iterator's remove, `dropIfEmpty`, `getNode`, `handles`, `entries`,
  `nodes`); growth is HashMap's, inside the lock; `mapIndex` is
  non-negative (testLargeIds) and spreads the writer's ids (testBinsStaySmall).
* `register` writes `h.obj` under the map's lock but not h's monitor;
  it races with no loader, as it is called for the writer's new nodes
  (new ids, `Db.registerNewNode`) and at startup, before readers.
* 005-09's kind of fault (a check of the canonical flag and an act on
  the table in different locks): the checks and acts on a handle's object
  are now `install` (handle monitor, LOADING), `makeCanonical` (handle
  monitor, the writer) and `kill` (map lock, after DEAD; the write lock
  but for `dropIfEmpty`); a reader's install and a kill exclude each other
  by the state, and the writer's and the evictor's by the write lock. A
  snapshot in a live handle is allowed with handles (one object per node,
  canonical or a version). D2 is the one pair I found that the state does
  not order, and it is not reached at run time.
* 005-08's fault: `mapIndex` takes 12 bits of the Fibonacci hash, the map
  and HashMap's bin depend on different bits (testBinsStaySmall passes);
  the CLOCK hand goes by maps, and a test schedule's order follows
  `handles()`, by maps and bins.
* `Handle.of` makes a handle outside the table for an object that has
  none; at run time every caller passes an object registered before
  (`keyNodeCreated` and `topNodeCreated` register before the node is
  pointed to; `DbStarter.createMemoryPointers`' targets are registered by
  `registerSectionNodes` with that handle).
* The record rule (`Handle.serializedRef`, `getSerializedRef` of both
  node types under the monitor) matches 009-02, 4.6 and section 9, the
  vpos as older than any position; `Spos.newer` and `newerPos` agree.
* `resolvePointers` and `linkToCanonical` change pairs under the node's
  monitor; `unswizzleValue` and `followValuePointer` count values in and
  out under the holder's monitor, as Residents' synch note says.
* The writer's follower: `makeCanonical` keeps one canonical object per
  handle (the handle's canonical object, else the newer of the two), and
  the swizzle replaces always, its handle holding the canonical object.
* The test schedules and the capacity controller kill only detachable
  objects (not pinned, written), read under the write lock; a loader's
  install between the evictor's test and its compareAndSet is a stream
  version, detachable too.
* 005-65's change: `wake` returns on a pending request without the
  monitor; `wanted` is written only under `evictorLock` and read under it
  before each `wait`; `batches` is the thread's only write.
* `CacheStats`: immutable; its figures come from `Residents.bytes()`
  (atomic; what it counts: R1-F2 and R1-F4), `NodeCollection.loads()`
  (atomic, every follower, values included) and `Eviction.figures()`
  (under Eviction's monitor: the batches, the objects released, values
  included, and their time), as its Javadoc says. `evictionSteps` and the

* TopDs: the new super root is filled before the volatile write of
  `superRoot`; inherited skip pointers keep their handle and reference, so
  a dead handle's written position goes on into the record rule.
* The jcstress tests match the code they model (EvictionRace is `kill`'s
  order; InstallPublication's loader is step 4's), but none covers

  code does not have (an eviction kills the handle).
* The unit tests of the classes read pass at BASE (section 1).
* Comments out of date, with no effect on what the code does:

## 5. Met outside the scope

* `resolvePointers` reads a node header from the stream (`idOf`) while it
  holds the node's monitor, which every reader's slow path on that node
  takes: a reader can wait for the writer's disk read (speed; in 2026.1 a
  pointer lock was held the same way).
* `StoredTopNode.parse` lost the check of the ordinal against
  `MAX_TOP_NODE_ID_VALUE` (005-75); it was dead, as the ordinal is read as
  48 bits.


## 6. Shared fields

* `Handle.id`: final; set by the constructor, which assigns only.
  Seen through a race by any reader. Enough (17.5). Tested: jcstress
  HandlePublication.
* `Handle.obj`: volatile; written by `install` and `makeCanonical` under
  the handle's monitor, by `register` under the map's lock (new nodes and
  startup only), by `kill` (`obj = null`) under the map's lock and, but
  for `dropIfEmpty`, the write lock; read by the fast path (volatile),
  the slow path, the writer, the audit. The volatile write orders a loaded
  object's contents before its reads. Enough for the contents; not for the
  version (R1-F3, by the JMM only). Tested: HandlePublication,
  InstallPublication, EvictionRace, EvictionReaderTester.
* `Handle.state`: volatile, changed only by compareAndSet (LIVE 0 is the
  default, no write in the constructor); read by the slow path under the
  handle's monitor and by the evictor. Enough. Tested: EvictionRace,
  EvictionReaderTester.
* `Handle.writtenPos`: plain; written only by `kill`, before `obj = null`;
  read by the record rule (the writer, under the write lock: ordered by
  the lock) and by a reader's slow path (ordered by its read of the
  eviction's `obj = null`). Enough. Its Javadoc says "under the map's lock
  and the write lock": `dropIfEmpty`, a reader's, calls `kill` too (it
  sets the position only for a canonical object, D2's case).
* `Handle.ref` (CLOCK bit): plain byte; set by followers when clear,
  cleared by `clockStep` under the map's lock; a separate byte from
  `state` (no word tearing, 17.6). A stale or lost bit only changes which
  object goes. Enough. Tested: none (CapacityTester's runs).
* `KeyNode.size`: volatile; the writer's release after appending, the
  readers' acquire before the arrays. Enough for appends.
* `KeyNode.klongs`, `pointers`, `pos` (the fields): plain; replaced by
  `growCapacity` and `setContentFrom` under the node's monitor, read
  plainly by searches and the fast path. Not enough: R1-F1. Tested: none
  (the probes of R1-F1).
* `KeyNode.klongs[i]`: plain, written before `size`; never changed below
  `size` but by the copies of R1-F1. Enough for appends; not for copies.
* `KeyNode.pointers[i]`: written by the writer before `size`, and in place
  under the node's monitor with a release store (`setPointee`,
  `setPointer`, `swizzle`); read plainly for a handle, with an acquire for
  a value, and under the monitor on the slow path. Enough on HotSpot; by
  the JMM the plain read of a handle is R1-F3. Tested: HandlePublication,
  ValuePublication.
* `KeyNode.pos[i]`: plain long; written before `size`, and in place under
  the node's monitor (`setRef`, `raiseRef`, `setPointer`); read plainly by
  the fast path and under the monitor by the slow path and the writer. A
  64-bit JVM does not tear it (relied on, 009-02, section 9); a stale value
  is harmless but in R1-F3's case; 0 from R1-F1's race is harmless on the
  fast path (a live handle's object is usable for any reference the
  pointer had). Tested: none of its own.
* `KeyNode.spos`: plain; `setSpos` writes it and then `size` again,
  `getSpos` reads `size` first. Enough for readers that read `size` after
  the write; a stale spos on a canonical object is not used (canonical
  serves).
* `KeyNode.isCanonical`, `TopNode.isCanonical`: plain; written by the
  writer (`registerNewNode`, `makeCanonical` under the handle's monitor,
  startup) and by `kill` (cleared); read plainly by the fast path's
  `usable`, and by the writer and the evictor under the write lock. A
  stale false sends the reader to the slow path (whose monitor orders
  it); a stale true is on an object a reader reached before the eviction
  nulled `obj`, which is the version at its position (009-02, 3.3). Enough.
  TopNode's comment says "access from threads holding Db.writeLock only":
  readers read it. Tested: EvictionRace.
* `KeyNode.countedMemSize`, `TopNode.countedMemSize`: under the object's
  monitor (Residents). Enough.
* `KeyNode.handle`, `TopNode.handle`: plain; written by `register` (map
  lock), `install` (a reader, under the handle's monitor, on the object it
  just read) and `makeCanonical` (the writer, the same monitor),
  `Handle.of` (the writer, startup); read by the writer and startup only
  (`Handle.of`, `register`), on objects that a follow under those
  monitors or `register` gave it. Enough.
* `KeyNode.id`, `TopNode.id` (volatile), `ValueNode.id`: set before the
  object is published (by `size`, a handle's `obj`, or `superRoot`).
  Enough.
* `KeyNode.isDirty`, `isInTransNodes`, `lastTimeIndex`, and TopNode's and
  ValueNode's: the writer's, read by eviction under the write lock.
  Enough.
* `TopNode.pointers[i]`, `pointersPos[i]`, `rootPointer`,
  `rootPointerPos`: plain, written under the node's monitor (no release
  store, as all hold handles) or before the top node is published; read
  plainly by the fast path and `TopDs`'s searches. As KeyNode's handle
  pointers (R1-F3 by the JMM). Tested: none for top nodes.
* `TopNode.pointersTime`, `topNodeId`, `pointersLength`, `rootTime`,
  `spos` (volatile): final, or set before publication. Enough.
* `ValueNode.value` (final), `spos` (volatile), `offsetFromTrans` (set
  before `spos`): enough with the acquire read of the pointer (C5).
  Tested: ValuePublication.
* `TopDs.superRoot`: volatile; the writer's write after filling the new
  top node, each search's read first. Enough. `secondOrdinal`: set before
  the first transaction.
* `NodeCollection.section`, `reconstructing`, `loadListener`,
  `firstTouchListener`: volatile; `StartupSection` immutable with final
  fields (its map copied in the constructor). `idByPos`: under its own
  monitor (an access-ordered LinkedHashMap, whose get writes). `loads`:
  atomic. `nodeStream`, `cache`: plain, set in the constructor before
  the database starts its readers (could be final). `MaintenanceFollower`:
  one thread. Enough.
* `Cache3.maps`: a final array of HashMaps, each under its own monitor;
  `sizeIndicator`, `totalSize` under `bigLock`; `accessClock` atomic;
  `residents` final. Enough.
* `Residents.bytes`, `objects`: atomic; each object's part
  (`countedMemSize`) under the object's monitor. Enough for the threads;
  what is counted is R1-F2 and R1-F4. `CacheStats`: final fields. Enough.
