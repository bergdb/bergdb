## 2. Faults

### R5-F1. The consumer discards the first storage-close IOException

* Where: `java/src/bergdb/storage/BufferedStream.java`, `runConsumer`,
  lines 205-209, and `close`, lines 655-678 at BASE.
* Intended: `BufferedStream.close()` Javadoc promises to throw if the
  underlying stream's close fails. `Db.close()` Javadoc and levels.md,
  section 8, promise `StreamIoException` for a failed storage close,
  including a later close after stop (005-35's completion contract).
* Actual: the consumer closes the stream and discards its IOException.
  The joining closer calls the underlying close a second time and only
  reports that second call or a flush failure. An underlying close that
  releases its resources and throws once, then is idempotent, loses the
  only failure. No contract requires an AppendOnlyStream to repeat its
  close exception.
* Effect: `Db.close()` returns success after a storage-close failure;
  later closes also report success. This is reproduced through the Core
  API with a supplied stream. FileStream remembers many of its own I/O
  failures, but that does not make BufferedStream's promise hold for all
  supplied streams.
* Evidence: [R5-F1.diff](R5/R5-F1.diff), test
  `bergdb.core.DbTesterStream.testR5FirstCloseFailureIsReported`.
  The single-test command and excerpt are in [R5-F1.txt](R5/R5-F1.txt):
  `close() returned successfully after its storage close failed;
  underlying closes=2`. The database is closed in finally.
* In 2026.1: yes. `git show release-2026.1:java/src/bergdb/storage/BufferedStream.java`
  has the same discarded exception and second close.
* Stream format, Pub API signature, or design choice: no.
* Proposed fix, not made: keep the first close IOException under the
  buffer monitor, alongside the flush failure; finish cleanup and throw
  the saved failure from every close. Preserve the earlier failure if
  cleanup throws too.

### R5-F2. Interrupting a stopping consumer can skip the underlying close

* Where: `java/src/bergdb/storage/BufferedStream.java`, `runConsumer`,
  lines 155-175 and 205-209 at BASE.
* Intended: `BufferedStream.stop()` eventually stops the thread and
  closes the underlying stream (its Javadoc, lines 682-685). Interrupts
  must not prevent completion (levels.md, section 3).
* Actual: an InterruptedException with `stop == true` returns directly
  from `runConsumer`, bypassing its stream-close block.
* Effect: the consumer ends but storage resources remain open. A direct
  BufferedStream.stop or StorageManager.stop can leak file handles and
  a FileStream directory lock. Db.stop's separate closer uses close and
  supplies a second close, so this finding does not claim that Db.stop
  has the same leak.
* Evidence: [R5-F2.diff](R5/R5-F2.diff), test
  `bergdb.storage.BufferedStream.testR5StopWhileConsumerInterruptedClosesStream`;
  command and excerpt in [R5-F2.txt](R5/R5-F2.txt):
  `stop ended the consumer without closing its stream`. The consumer is
  joined before the assertion and the test closes it in finally.
  Forced ordering (all line numbers at BASE):
  1. Consumer C is in the idle `wait()` at line 157, releasing monitor B
     (the BufferedStream object).
  2. Controller T locks B, interrupts C, then calls stop reentrantly:
     line 692 sets stop true. C has left the wait set on the interrupt
     and cannot reacquire B yet.
  3. T unlocks B; that unlock happens-before C reacquires B and throws
     InterruptedException. C must see stop true in the catch.
  4. C executes the return at line 170. Thread termination happens-before
     T's join returns; the close counter remains zero. There is no
     missing visibility edge: the branch skips cleanup with fully
     published stop state.
* In 2026.1: yes. The old InterruptedException catch also returns when
  stop is true, before the same cleanup block.
* Stream format, Pub API signature, or design choice: no.
* Proposed fix, not made: put the underlying close in a finally block
  covering the whole consumer lifecycle, or break the outer loop from
  this catch so it reaches the common close path.


### R5-F3. A background main-storage failure leaves cached reads running

* Where: `java/src/bergdb/storage/StorageManager.java`,
  `handleStreamException`, lines 765-799, and `MyStorage.appendFailed`,
  lines 1053-1055; `core/Db.java`, getOne's state check at 1515 and
  failOnStorage at 2127-2135, at BASE.
* Intended: 010-01, P7: a database whose environment has failed does
  not run on; every later transaction and read must throw until restart.
  Levels.md, section 3, specifies that a storage append error fails the
  database and later reads throw DbFailedException.
* Actual: the consumer's failed flush stops and closes the buffer and
  publishes an error only inside StorageManager. It never changes Db's
  ACTIVE state. A get served entirely by cached nodes never calls
  StorageManager.read, so it never detects the error. Only a subsequent
  operation that encounters the error, such as a sync or append, fails Db.
* Effect: after a known failed main-storage write, an application that
  only reads can keep receiving the unwritten values indefinitely. This
  is the missing failure transition, not a claim that an unsynced commit
  was promised durable. No concurrent transaction or in-flight read is
  needed: the test joins the failed consumer before starting the read.
* Evidence: [R5-F3.diff](R5/R5-F3.diff),
  `bergdb.core.DbTesterFailure.testR5CachedReadAfterBackgroundFlushFailure`;
  command and excerpt in [R5-F3.txt](R5/R5-F3.txt):
  `cached read succeeded after the storage consumer failed: unwritten`.
  It first syncs the prior value, makes the next underlying append throw,
  waits for the consumer to end, then reads. The database closes in finally.
* In 2026.1: yes. Its StorageManager's failure callback likewise only
  updates the storage state, and getOne only checks Db's state before a
  cached read (`git show release-2026.1:...` for both files).
* Stream format, Pub API signature, or design choice: no. The policy is
  already P7; its implementation needs an internal notification or a
  storage-health check at read admission.
* Proposed fix, not made: notify Db when the main storage first fails,
  retaining the original cause and using Db's existing atomic first-failure
  transition. Keep callback execution outside the buffer and durability
  locks and account for initialization and shutdown. Alternatively, have
  read admission observe StorageManager's published failure state.


### R5-F4. A negative append is accepted and decreases StorageManager's length

* Where: `java/src/bergdb/storage/BufferedStream.java`, append,
  lines 462-473; `StorageManager.java`, append, lines 805-816 and 845,
  at BASE.
* Intended: AppendOnlyStream.append's Javadoc requires
  IllegalArgumentException for a negative length; getLength's Javadoc
  says the total appended length always increases.
* Actual: BufferedStream performs no negative-length check, so its loop
  is skipped and append returns successfully. StorageManager then adds
  the negative length to its own logical length, while the buffer's
  totalLength remains unchanged.
* Effect: invalid input that is explicitly required to be refused
  silently desynchronizes the two length counters. The verified call
  leaves StorageManager at 99 bytes and its main buffer at 100. Normal
  Db.store constructs nonnegative lengths; this is a lower-layer API
  contract fault, not a demonstrated path from a valid Pub transaction.
* Evidence: [R5-F4.diff](R5/R5-F4.diff),
  `bergdb.storage.StorageManagerTester.testR5NegativeAppendDoesNotDecreaseLength`;
  command and excerpt in [R5-F4.txt](R5/R5-F4.txt):
  `negative append returned normally; manager length=99, buffer length=100`.
  The test closes the manager in finally.
* In 2026.1: yes. Its BufferedStream has the same unchecked loop and
  StorageManager has the same unconditional length addition.
* Stream format, Pub API signature, or design choice: no.
* Proposed fix, not made: check length and the source interval before
  changing buffer state; reject negative lengths with
  IllegalArgumentException. StorageManager can also defend its counter
  before forwarding the append.


### R5-F5. The buffer issues concurrent writes to a single-writer underlying stream

* Where: `java/src/bergdb/storage/BufferedStream.java`, flushToStream,
  lines 253-259, and pretruncate, lines 570-577, at BASE.
* Intended: AppendOnlyStream's CONCURRENCY contract permits concurrent
  reads, but requires all other method calls to hold one common write
  lock. Implementations may rely on that. BufferedStream is specified
  as a buffer for an AppendOnlyStream, with no stronger requirement on
  its underlying stream.
* Actual: the consumer calls stream.append outside the buffer monitor.
  A cut within streamLength is sent directly from the producer to
  stream.pretruncate, also outside that monitor. The two non-read
  operations can overlap, despite all external buffer calls following
  the single-writer rule. The pendingCut machinery only delays cuts
  beyond streamLength; it does not serialize already-flushed cuts.
* Effect: a conforming underlying implementation that relies on one
  writer can fail or race during a valid buffered cut. The test's legal
  single-writer implementation detects the overlap and throws, so a
  valid cut fails. This does not claim that the current FileStream
  loses bytes in this interleaving; its extra internal synchronization
  is additional to the interface's single-writer guarantee.
* Evidence: [R5-F5.diff](R5/R5-F5.diff), including the new Nano tester
  and its Pack registration;
  `bergdb.storage.BufferedStreamReviewTester.testR5UnderlyingWritesAreSerialized`.
  Command and excerpt in [R5-F5.txt](R5/R5-F5.txt):
  `pretruncate overlaps append on a single-writer stream`.
  Forced ordering, also implemented by the test:
  1. Controller T holds external write lock L and appends 300 bytes to B,
     whose already-flushed prefix is 100 bytes. appendToBuffer at line
     497 holds B; T then releases B and L.
  2. Consumer C reserves the 300 bytes under B (line 189), releases B,
     and calls the underlying append at line 255 without L. The test
     stream sets volatile appending true, counts down entered, then
     waits for release while remaining inside append.
  3. T successfully awaits entered: its acquire is HB-ordered after C's
     active-append publication. T holds L and calls pretruncate(50).
     Lines 571-576 hold B, see streamLength 100, and release B. Line 577
     invokes the underlying pretruncate without any lock shared with
     C.append; the stream sees appending true and throws. The two
     operations have no mutual exclusion despite the published state.
  4. Finally, T releases the latch (HB C's successful await), closes B
     under L and joins C through close. The assertion reports the failed
     valid cut after all storage resources are closed.
* In 2026.1: yes. The same direct pretruncate and out-of-monitor
  append calls are present there.
* Stream format or Pub API signature: no. Design choice: physical-cut
  ownership. Queue cuts to preserve the existing single-writer contract
  and quick producer cut, or explicitly require a stronger underlying
  implementation. The latter changes the documented storage contract.
* Proposed fix, not made: queue every physical cut to the consumer, with
  suitable failure publication, or serialize all underlying non-read
  operations with a separate lock. Queuing preserves a quick producer
  cut when an append/force is slow; do not hold the buffer monitor
  during storage I/O.


### R5-F6. An unchecked close error can kill the consumer before publishing a failed append

* Where: `java/src/bergdb/storage/StorageManager.java`,
  handleStreamException, lines 779-799; BufferedStream.java,
  stopAfterFailure, lines 326-333, and runConsumer, lines 202-209, at BASE.
* Intended: levels.md, section 3, and 010-01 P7 require storage failures
  and bugs to fail the database, with later calls throwing. A failed
  flush must not strand a durability waiter; the code explicitly wraps
  RuntimeException and Error from the underlying append for that reason
  (BufferedStream's flushFailure Javadoc, lines 317-320).
* Actual: the failure callback closes the buffered stream before
  publishing ErrorStorage and recomputing the error rule. It catches
  IOException from that close only. An unchecked close exception escapes
  through appendFailed, outside flushToStream's protected append block,
  and terminates C before either publication occurs. B is stopped, but
  StorageManager still reports no error internally.
* Effect: a sync of the failed buffered transaction waits indefinitely:
  its durable frontier cannot advance, its 500 ms poll sees no error,
  and the only consumer has ended. The database also remains ACTIVE.
  This is distinct from R5-F1's discarded checked close exception and
  R5-F3's cached-read behavior after a normally published storage error.
* Evidence: [R5CloseErrorProbe.java](R5/R5CloseErrorProbe.java), commands
  and output in [R5-F6.txt](R5/R5-F6.txt):
  `consumerAlive=false; uncaught=java.lang.IllegalStateException: R5: unchecked close failure`
  and `dbActive=true; durableUnchanged=true; syncAlive=true; syncFailure=null`.
  It injects an IOException from append and an IllegalStateException
  from its cleanup close, joins the failed consumer, then observes sync
  still waiting past the 500 ms poll. Cleanup interrupts and joins the
  sync waiter, removes the close injection and closes Db.
  The ordering is deterministic:
  1. W commits and syncs the initial prefix, then buffers another
     transaction; its record extends beyond D1.
  2. C's underlying append throws; stopAfterFailure takes B, records the
     IOException, sets stop and notifies B waiters, then releases B.
  3. C invokes MyStorage.appendFailed outside B. handleStreamException
     calls b.close, which skips joining its own C and calls the underlying
     close at BufferedStream line 671. The unchecked exception escapes;
     the snapshot CAS at StorageManager line 788 and computeRules at 799
     are never executed. C terminates.
  4. The probe's join establishes HB from C's termination to the probe,
     which starts S. S holds D1, reads the unchanged atomic snapshot,
     requests a flush from the dead consumer, and repeatedly waits on
     D1. No remaining operation can advance or fail this frontier before
     the probe starts cleanup.
* In 2026.1: yes. The same close-before-publication order and IOException-only
  catch are in its handleStreamException, and the consumer callback is
  outside the append's failure catch.
* Stream format, Pub API signature, or design choice: no.
* Proposed fix, not made: publish the failed-storage/error state before
  potentially failing cleanup, and make its completion unconditional.
  Preserve the append failure and attach cleanup failures; an unchecked
  cleanup error must not prevent the failed state reaching sync waiters.


### R5-F7. A pending cut arriving during another cut can be left unapplied after close

* Where: `java/src/bergdb/storage/BufferedStream.java`, pretruncate,
  lines 570-577; applyPendingCut, lines 584-594; flushToStream,
  lines 279-314, at BASE.
* Intended: pretruncate's Javadoc says a position beyond the flushed
  prefix is held and applied after the flush that reaches it. This is a
  supported use of the buffer, also covered by testPretruncateBeyondFlushed.
* Actual: applyPendingCut takes and clears pendingCut under B, then
  applies that cut outside B. streamLength still has the old value until
  after that underlying call returns. Another cut arriving in that
  interval, within the bytes already written by this flush, is queued
  against the old streamLength. This flush never checks the queue again.
  With no more appends, the consumer has no next flush on which to apply
  it; close sees an empty buffer and stops C without applying the cut.
* Effect: a valid requested cut is never delegated while idle, and
  remains unapplied when close returns. Reclamation can retain a larger
  prefix until a later append/restart. This verifies the BufferedStream
  contract gap; it does not demonstrate lost data or a normal Db reclaim
  call entering this window. Db normally requests already-durable cuts.
* Evidence: [R5PendingCutProbe.java](R5/R5PendingCutProbe.java), commands
  and output in [R5-F7.txt](R5/R5-F7.txt):
  `requestedCut=300; delegatedCut=200; flushedLength=400; bufferClosed=true`.
  All public buffer calls hold the same external write lock. The probe
  releases the held operation and closes the buffer in finally.
  Forced ordering:
  1. T constructs B over a 100-byte stream, buffers 300 bytes, queues
     pretruncate(200) under B, then starts C.
  2. C writes the 300 bytes, then applyPendingCut(400) takes B, copies
     pendingCut 200 and clears it. C releases B and enters the underlying
     cut at line 593, where a test latch holds it.
  3. T's successful latch await is HB-ordered after that entry. T calls
     pretruncate(300), takes B, sees streamLength still 100 and queues
     pendingCut 300, then releases B. C has no storage operation on that
     second cut; this is not R5-F5's overlapping-writes case.
  4. T releases C. C finishes cut 200, takes B and publishes streamLength
     and cStart 400 at lines 303-304, then notifies its append listener.
     That listener's latch releases T. No bytes remain buffered.
  5. T closes B and joins C. C terminates without another pending-cut
     check, so the underlying stream has seen cut 200 only.
* In 2026.1: yes. The same clear-before-I/O sequence, old-length test and
  publication after the pending cut occur there.
* Stream format, Pub API signature, or design choice: no.
* Proposed fix, not made: make the eligibility check and flushed-frontier
  publication atomic with respect to pretruncate. Drain every newly
  eligible pending cut before finishing the flush, or let C process an
  eligible cut without requiring another append. Close must also finish
  cuts that the completed flush already made eligible.


### R5-F8. A read past the end throws IOException instead of the documented EOFException

* Where: `java/src/bergdb/storage/BufferedStream.java`, read,
  lines 369-374 at BASE.
* Intended: AppendOnlyStream.read's Javadoc specifies EOFException when
  there is not enough data for the requested read.
* Actual: BufferedStream detects that the last requested byte is at or
  beyond totalLength, but throws a plain IOException rather than its
  documented EOFException subtype.
* Effect: a client that handles the documented end-of-stream exception
  separately receives the generic I/O-failure case instead. This is a
  lower-layer exception-contract fault; the bounds check prevents stale
  bytes, and the probe does not show data loss or a valid Db read failing.
* Evidence: [R5ReadEofProbe.java](R5/R5ReadEofProbe.java), commands and
  output in [R5-F8.txt](R5/R5-F8.txt):
  `read(position=1,length=1), streamLength=1: java.io.IOException; isEOFException=false`.
  It starts a buffer, appends one byte, requests the byte after it and
  closes the buffer in finally.
* In 2026.1: yes. The same check and plain IOException are in its read
  method, and its AppendOnlyStream Javadoc specifies EOFException too.
* Stream format, Pub API signature, or design choice: no.
* Proposed fix, not made: throw EOFException for this bounds condition,
  retaining the diagnostic message. It already extends IOException, so
  the declared method signature need not change.

## 3. Doubts

### R5-D1. Live listener replacement has no publication rule

appendListener is assigned plainly by setAppendListener (line 620 at
BASE) and read plainly by the consumer after leaving the buffer monitor
(lines 314 and 333). The normal StorageManager setup installs it before
any append, and the first append's monitor publication orders that setup
correctly. No failing database path was found there.

If callers may replace the listener while a flush runs, the setter and
callback have no happens-before edge; a later callback may still use the
old listener. The setter documents no lifecycle rule, but neither
does it explicitly promise live replacement. This remains a doubt about
that API use. Verification needs the intended setter lifecycle confirmed
and a controlled replacement test or a checked
interleaving showing a missed required notification. No race-only fault
is registered from this observation.

## 4. Checked and right

- A sync's length includes the commit byte: Db converts lastPos to
  lastPos + 1 and keeps endOfLastTrans as the exclusive end. The existing
  odd-buffer commit-byte regression passes.
- Sync holds its durability monitor while asking for a flush and then
  waits atomically on it. The consumer calls the listener after releasing
  the buffer monitor; the audited main-only path has no B/D1 or B/D2
  lock cycle. Already durable syncs return without a flush. Group commit
  during a held append passes the retained probe.
- A quarter crossing wakes a timed-waiting consumer, and the pre-wait
  check also drains a quarter left after a flush; both targeted tests pass.
- Buffer ranges remain reserved until the underlying append completes.
  Reads choose their buffer/stream split under the monitor and copy the
  buffered suffix before releasing it. The retained probe preserves
  all 10,294 bytes from a nonempty start with capacity 1,001. R5-F8
  identifies the exception-subtype mismatch for an out-of-bounds read.
- A successful underlying append is published before advancing confirmed
  length and notifying sync waiters. A failed append/force is not counted
  as durable; IOException, RuntimeException and Error from that flush
  enter stopAfterFailure. Existing Error-in-flush and full-buffer writer
  failure tests pass. R5-F3 identifies the separate missing Db transition.
- A blocked append rechecks stop on every wait-loop iteration and throws
  after a failed flush; it does not retain the write lock forever. Its
  interrupted wait completes and restores the caller's interrupt flag.
- An interrupted waiting sync throws the interrupted-I/O wrapper and
  preserves the flag, without failing Db. Subsequent reads and commits
  work in the focused tests.
- Db.stop starts a non-daemon closer, the closer waits for a running
  transaction, and Db.close waits for that close and its consumer. Existing
  tests cover all buffered writes, stop with a running large transaction,
  two closers, a final failed flush, and repeated reporting of that flush.
  R5-F1 and R5-F2 isolate the close-error and direct-stop gaps.
- An idle consumer waits without a timeout; an append and close wake it.
  The wait count saturates rather than overflowing. There is no
  zero-byte flush while closing an empty buffer. These paths were read;
  idle and zero-flush regressions pass.
- A cut already queued when applyPendingCut runs is applied before that
  flush is published. R5-F7 shows the missing second check for a later
  cut. ReadBelowFirstPosException is passed through without poisoning
  storage; the selected test passes. R5-F5 concerns the different path
  for a cut already within the published flushed prefix.

## 6. Shared fields

This inventories every declared field in the three primary files that is
shared in the audited path, their nested shared objects, and the relevant
boundary/test objects. W is a startup/transaction writer holding Db's
writeLock; C is the buffer consumer; R is a reader; S is a sync caller;
K is a stopping/closing caller; T is a test controller. B is the
BufferedStream monitor; D1/D2 are StorageManager's durability monitors;
Q is a Waits object's monitor. "HB" means happens-before. Tests cited
here were selected individually as recorded in checks.txt, unless
explicitly marked read-only or none. No jcstress tests were run.

### BufferedStream

- `buffer`: final reference initialized before C.start; W copies bytes
  under B, R copies under B, C reads its reserved interval outside B.
  W's B unlock HB C's reservation lock. C advances cStart only after the
  underlying append returns, under B, so W cannot reuse that range while
  C reads it. Test: R5MainOnlyProbe.ring; testWriteMuch/testWriteLittle.
- `bufferCapacity`: final constructor value read by W, R and C; final
  publication/start HB, no stale changing value. Test: ring probe.
- `tenPercentOfBufferCapacity`: final constructor value read by writers
  under B; startup publication and common writer access order it. Test:
  testAppendWaitIgnoresInterrupt and full-buffer writer failure.
- `twentyFivePercentOfBufferCapacity`: final constructor value read by
  W/C under B; start/final publication HB. Tests: both quarter regressions.
- `fiftyPercentOfBufferCapacity`: final constructor value read by C and
  by constructor/setup contexts; start/final publication HB. Tests: ring
  probe and testWriteMuch; no changing or torn value.
- `streamLength`: initialized before start; C advances it under B; R and
  the cutting W read it under B. C's own out-of-monitor read for a pending
  cut is program-ordered after its previous update. HB is B unlock/lock.
  Plain seekFirstPos writes are confined to the excluded replica setup
  path; that path's publication is not certified here. Test: nonempty
  ring probe and testPretruncateBeyondFlushed (read-only).
- `totalLength`: W increments under B; W/getLength and R/bounds checks
  read under B. B supplies HB and prevents torn longs. Plain seek writes
  have the same excluded qualification. Tests: ring probe and R5-F4.
- `stream`: final underlying reference published before C.start; C
  appends/closes, R reads, W gets first position and issues eligible cuts,
  and K closes after joining C. The implementations supply read
  publication. There is no common exclusion for C.append versus
  W.pretruncate: R5-F5. Close-error lifetime is R5-F1, and an unchecked
  cleanup error can prevent storage failure publication: R5-F6. Tests:
  R5-F1/F5 and the close-error, held-force and ring probes.
- `consumer`: final Thread object; W starts it, K/T join or interrupt it,
  C identifies itself during close. Thread.start publishes initialization;
  successful join orders all completed C actions before the closer.
  Stop plus interrupt can bypass cleanup despite correct visibility:
  R5-F2. Tests: R5-F2 and the consumer/close interrupt tests.
- `pStart`: W advances under B; R/C/K read under B. Reservation and room
  checks use B, so no torn or stale progress. Seek setup is excluded as
  above. Tests: ring probe, testWriteMuch and blocked-append test.
- `cStart`: C advances under B; W/R/K read under B. C's indexing outside
  B uses its own most recent position and the reserved range. B supplies
  publication to other threads. Seek setup excluded. Tests: ring probe,
  quarter-backlog and full-buffer writer tests.
- `cSize`: C reserves/changes it under B, then reads its own value outside

- `stop`: K and a failing C write under B; waiting W/K and C's inner

  stop again before waiting or flushing. No regression to false occurs.
  The missed-cleanup branch is R5-F2, not a missing HB edge. Tests:
  R5-F2, failed-flush close and blocked-writer failure.
- `flushAndClose`: K writes true under B and notifies; C reads under B

- `exception`: K/C assign the first exception under B; W/R check it

  represents deliberate stop/close, not just storage failure. Tests:
  failed-flush close and post-close tests (latter read-only).
- `failure`: C saves the first flush failure under B; W/K read it under

  consumer's close IOException: R5-F1. Tests: R5-F1 and

- `pendingCut`: W raises it under B; C takes/clears it under B, then

  B orders the long and prevents a torn position. Test:
  testPretruncateBeyondFlushed (read-only). R5-F5 covers direct cuts;
  R5-F7 shows the queue/frontier eligibility gap after this field is cleared.
- `waitTime`: final constructor value read by C; start/final publication

- `waitsBeforeFlush`: final constructor value read by C and test code;

- AppendListener object and captured `MyStorage`/buffer references:

- `appendHasBeenCalled`: W writes volatile true before append, seek's W

- `idle`: C sets it under B; W reads under B to decide whether to notify.
  The idle wait releases B atomically with entering the wait set; an
  append cannot miss publication of idle. Tests: idle and quarter wakes.
- `flushTo`: S raises it monotonically under B; C reads under B in

### StorageManager

- `DEFAULT_REPLICA_BUFFER_SIZE`: static final primitive; written by class
  initialization, read in builders. Class initialization HB all uses;
  no changing value. Replica behavior excluded; no dedicated test.
- `DEFAULT_REPLICA_BUFFER_TIME`: static final primitive; same class-init
  edge and excluded use. No dedicated test.
- `DEFAULT_BUFFER_SIZE`: static final primitive; class-init HB readers in
  multiple builders; no changing value. Test: default-builder tests in
  the selected Db/interrupt checks; no standalone constant test.
- `DEFAULT_BUFFER_TIME`: static final 50; class-init HB all builder and
  BufferedStream constructor reads. No timing-dependent mutable value.
  Same coverage; source matches 005-64's decision.
- `internal`: final AtomicReference. W, C, R/error handling and K publish
  replacement snapshots with set/CAS; all readers use get. Atomic release/
  acquire HB publishes the snapshot fields and arrays. Main-only updates
  copy before publishing. K's close path uses set rather than CAS and
  can supersede a concurrent error snapshot during shutdown; each published
  replacement remains closing/failed. Db separately orders completion
  of a previously admitted writer before closing its buffer. R5-F3
  is the missing observation by cached Db reads, not a torn snapshot.
  Tests: R5-F3, error-in-flush, failed writer and close-failure tests.
- `writeLock`: final caller-supplied monitor, initialized during setup;
  transaction/startup callers serialize the default methods on that
  monitor. The consumer does not take it, avoiding a cycle with a writer
  waiting for buffer room. The in-scope methods rely on caller-held
  write access rather than acquiring it themselves. Tests: full-buffer
  writer and stop-with-running-transaction.
- `mainStream`: final BufferedStream reference, assigned during
  construction; W appends, R reads, S flushes, K closes. Its own monitor
  and the publication edges listed above order its mutable state; the
  reference stays valid even after it is removed from an error snapshot.
  Tests: one-force sync, group probe, R5-F3/F4.
- `streamLength`: W sets it during startup and increases it after a
  successful logical append; W getters require the same external write
  lock. Monitor unlock/lock orders changes between writer threads; C/R/S
  do not use it. R5-F4 is an arithmetic/input defect, not a data race.
  Tests: R5-F4 and stop-all-bytes.
- `d1Size`: C/rule computation writes it under D1; S/getDurableLength
  read under D1. D1 unlock/lock HB protects the durable long. computeRules
  also reads it while holding D2, after that same invocation has released
  D1. In the main-only lifecycle there is one confirmation-producing C,
  and startup rule computation precedes appends; its own ordered write/
  read does not need cross-consumer publication. No general claim is made
  for multiple replica consumers or live rule reconfiguration. Tests:
  group probe, one-force sync and byte-boundary sync.
- `d1Lock`: final monitor shared by C/S and durable-length getters;
  condition reads, increments and notifications all hold D1. wait releases
  D1 and reacquires it; successful notification publication is HB. Error
  publication uses internal.get at a 500 ms poll rather than notifying
  this monitor. Test: group probe and Error-in-flush.
- `d2Size`: C/rules write and S/strong-sync read under D2; D2 HB prevents
  stale or torn size checks. Main-only computation is capped at D1.
  Replica rule semantics excluded. Tests: selected strong-sync calls in
  Db failure/stop tests; no replicas used.
- `d2Lock`: final monitor; C/S hold it for strong durability conditions,
  changes and waits. D2 unlock/lock supplies HB; B is not held in the
  consumer callback, so the S D2-to-B acquisition has no callback cycle.
  Tests: interrupted strong sync and Error-in-flush.
- `isSynched`: W writes volatile true after syncStreams; append reads
  volatile before accepting bytes. Release/acquire publishes completed
  startup integration. Test: group probe startup and Db startup tests.
- `Internal.streams`: plain array reference filled/cloned before atomic
  snapshot publication; W/C/R/K/S read the published snapshot. Main-only
  element changes use a copy and CAS; AtomicReference HB publishes both
  reference and elements. A stale snapshot can still identify the same
  final buffer, whose failure/close checks are synchronized. Tests:
  failed writer, error sync and close tests.
- `Internal.storages`: same snapshot publication; elements are immutable
  ErrorStorage or MyStorage with AtomicLong confirmation. A stale main
  confirmation can delay acknowledgment, not invent it. Tests: group
  probe and Error-in-flush.
- `Internal.d1`: plain rule reference assigned before publication; C
  reads via the acquired snapshot. Default MainConfirmedRule has no
  fields. AtomicReference HB; no main-only mutation. Test: group probe.
- `Internal.d2`: plain reference replaced through a copied snapshot/CAS
  by the rule-setting caller; C reads through internal.get. AtomicReference
  HB orders initial rule state. Default replica policy itself is excluded;
  arbitrary rule internals are not covered. No live-rule-change test.
- `Internal.errorRule`: plain reference installed before atomic
  publication; C/R/error handlers read it through snapshots. Default
  MainErrorRule is stateless. AtomicReference HB. Test: error sync.
- `Internal.hasError`: plain flag written in unpublished copies by W/C/R/K;
  all readers acquire the containing snapshot. AtomicReference HB; once
  set, in-scope replacements remain failed/closing. It is not Db.state:
  R5-F3. Tests: R5-F3 and failure/close checks.
- `Internal.errorString`: plain immutable String reference prepared with
  hasError before publication; atomic snapshot edge orders their pair.
  No torn reference. Test: error-in-flush sync; the original exception
  object is not retained in this field.
- `MyStorage.name`: final immutable String reference initialized in
  construction, read by C/rules/error handlers and W. Final publication
  plus atomic snapshot HB; no changing value. No dedicated name test.
- `MyStorage.confirmedLength`: final AtomicLong; initialized from the
  existing prefix, C sets after a successful flush, rules read with get.
  Atomic set/get supplies HB; C publishes increasing lengths, and a
  failed flush never advances it. Tests: group and failed-flush probes.
- `MyStorage` callback object: created and installed before any append;
  first-append B publication orders its reference and captured buffer.
  It updates confirmedLength before computing rules. It has no callback
  into Db on failure, which is R5-F3. Cleanup can abort storage-error
  publication too: R5-F6. Tests: R5-F3 and the group/close-error probes.
- `ErrorStorage.name`: final immutable reference initialized before CAS;
  readers obtain it through an acquired snapshot. Final/CAS publication
  HB. No dedicated test beyond the storage-failure checks.
- `ErrorStorage.errorMessage`: final immutable reference built from the
  exception before CAS; same HB as name. It is read by the error rule and
  sync error construction. R5-F6 reaches an unchecked close error before
  the ErrorStorage object is installed. Tests: Error-in-flush sync and
  the close-error probe.

Builder.writeLock, Builder.streams, Builder.nameSet and each StreamInfo's
name/stream/bufferSize/bufferTime are setup objects, not shared with C:
the constructor copies their values into the published buffer/storage
objects. A builder used by successive writer threads requires the same
external write-lock handoff; no concurrent-builder guarantee is claimed.
Tests: none for cross-thread builder reuse.

Replica-only declared fields `SynchingStorage.myStorage`, `statusString`,
`replicaStream` and `stopSync` are listed for inventory completeness;
their protocols and replica-only array/rule transitions are deliberately
not audited, as required by the scope. They are final, volatile, final
and volatile respectively; those modifiers alone do not establish the
excluded algorithm's correctness.
