## 2. Faults

### R3-F1. A second delete job lets the first delete a replacement index

* Where: `java/src/bergdb/pubimp/DatabaseImp.java`, `deleteIndexInternal`,
  lines 303-337; `pubimp/IndexManager.java`, `ensureDeletingState`, lines
  622-640, `deleteIndexEntries`, lines 399-453, and `deleteIndexInfo`,
  lines 456-464. All source paths below are relative to `java/src/bergdb/`.
* Intended: `Database.deleteIndex` deletes the named index in a background
  job. A later `indexBuilder` may create that name once deletion has
  finished; that new index must survive an older job. 010-01 P1/P6 require
  concurrent index changes without stopping application operations.
* Actual: `ensureDeletingState` returns the existing object even when it
  is already deleting. Each call nevertheless starts another worker.
  Workers scan and delete by name, and remove metadata and the cached map
  entry by name, without checking that the index is still their object.
* Effect: a delayed worker deletes a newly created index and its entries.
  Its primary objects survive. The metadata loss survives restart.
* Evidence: [DuplicateDeleteProbe.java](r3/DuplicateDeleteProbe.java),
  output and commands in [r3-f1.txt](r3/r3-f1.txt). The probe subclasses
  `Db` only to pause the first delete worker just before its real
  `getMany` call. It makes two ordinary public `deleteIndex` calls,
  waits for the second job, creates and populates the replacement, then
  resumes the first. Output: `new index before old job resumes: 1 entry`,
  then `FAULT: old delete job removed newly created index:
  NoSuchIndexException` and `FAULT persists after reopen`.
  The latches and joins make the interleaving deterministic; no production
  code is changed. Both databases are closed.
* In 2026.1: yes; `git show release-2026.1` has the same unconditional
  worker creation and name-based deletion.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no. Preserve one job per index instance, and prevent stale jobs
  from writing/deleting after its generation has been replaced.
* Proposed fix, not made: coordinate deletion workers under the index
  manager lock; return the existing deletion job for an already deleting
  index. Check object/generation identity before deleting metadata, and
  serialize final removal with admission of another index of that name.


### R3-F2. A deleted index's build job writes into its replacement

* Where: `pubimp/IndexBuilderImp.java`, `createInThread`, lines 302-333,
  `createStep`, lines 375-447, `handleStepResult`, lines 450-467;
  `pubimp/IndexManager.java`, `ensureDeletingState`, lines 622-640.
* Intended: deletion stops new entries for the deleted index
  (`DatabaseImp.deleteIndexInternal`, lines 308-310); `Database.deleteIndex`
  deletes that index. Index changes are concurrent with application calls
  (010-01 P1/P6). `JobStatus.progress() == 100` describes a finished build,
  and `IndexBuilder.start` says it has then become active.
* Actual: deletion marks the old index deleting and removes its directory
  mappings, but the existing builder retains its `Index` and keeps calling
  `setIndexEntry` without validating that it still exists or is creating.
  It commits those entries, marks its status done, and only then checks
  the state during activation. That last check throws outside `Db.execute`.
* Effect: after delete has finished, an old builder can populate a
  replacement index of the same name using the old field definition.
  Queries return extra objects, duplicates and the wrong order; the
  database stays active. The old build reports 100 despite its failure.
* Evidence: [BuildDeleteProbe.java](r3/BuildDeleteProbe.java), commands
  and output in [r3-f2.txt](r3/r3-f2.txt). A `Db.getMany` override pauses
  the old build at its first scan. Public calls finish deleting it,
  create the same name on field `other` instead of `amount`, and insert
  one object. Resuming the old builder changes the replacement's result
  from `[100]` to `[200, 100, 100]`; its uncaught exception is
  `State not STATE_CREATING, but 30`, its progress is 100 and the database
  is still active. The latch and join determine the order. The worker is
  joined and the database closed.
* In 2026.1: yes; the build loop, entry-writing transaction and late state
  check are unchanged in the tag.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: serialize each build step's admission with the
  index state/generation, include an index-info read dependency in its
  transaction, and stop a build when that instance is deleting or gone.
  Finish/cancel the old generation before reusing its entry prefix. Publish
  success only after activation succeeds.

### R3-F3. An exception in the evictor strands requests on a dead worker

* Where: `core/Eviction.java`, `EvictorRun.run`, lines 496-544, and
  `wake`, lines 421-430.
* Intended: a failed environment or a bug stops the database (010-01 P7).
  Loads and a cache decrease start eviction that keeps working (005-51,
  005-65's protocol; `Db.setCacheSizeIndicator` Javadoc).
* Actual: the worker has a `finally` for `running`, but no catch that
  fails the database and no outer cleanup that clears `evictor`. A
  throwable during a batch leaves that field naming a terminated thread.
  `wake` subsequently sets `wanted` without starting a replacement; every
  later wake may then return immediately on that permanently set flag.
* Effect: reads continue after an internal error; eviction requested by
  loads or a cache decrease stops permanently. Resident memory can grow
  beyond the configured budget. A later writer might encounter the error
  separately, but a reader-only workload has no recovery path here.
* Evidence: [EvictorFailureProbe.java](r3/EvictorFailureProbe.java),
  output and commands in [r3-f3.txt](r3/r3-f3.txt). It uses the existing
  instance `testBeforeTrigger` hook to inject an `Error` in the worker's
  batch, as the storage failure tests inject backend errors. The hook is
  installed before `Thread.start`; the uncaught-handler latch and worker
  join precede observations. Output: `evictor dead: true`, `database active
  after worker Error: true`, an accepted cached read, and `request kept
  on the same dead worker: true; wanted=true`. The hook is removed and
  the database closed. This verifies failure propagation/cleanup, not
  the likelihood of a particular natural JVM failure.
* In 2026.1: no. The tag's eviction runs in callers; it has no
  `EvictorRun` or eviction thread. The worker was introduced with 009.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no; the existing failed-database policy applies to a batch
  whose partial in-memory work cannot be rolled back.
* Proposed fix, not made: catch worker failures, publish the first failure
  to `Db` and wake its waiters; clear the worker reference under
  `evictorLock` in an outer `finally`. Keep the intentional idle-interrupt
  exit (005-46/005-65) separate from an erroneous batch failure.

### R3-F4. JMX's monitor still terminates on an interrupt and swallows stop's flag

* Where: `core/Jmx.java`, `Speed.run`, lines 323-342, `registerAndStart`,
  lines 293-307, and `stop`, lines 310-320.
* Intended: 005-46, "Interrupts", the adopted rule: own threads go on
  when interrupted; a call that must complete ignores interruptions and
  keeps the caller's flag. Only sync, a Job join and a transaction retry
  wait are interruptible. The evictor's restartable idle exit is the
  explicit exception; JMX has no such restart protocol.
* Actual: the monitor breaks its outer loop on `InterruptedException`,
  leaves `thread` set, and a subsequent `registerAndStart` returns without
  restarting. `Speed.stop` ignores an interrupted `join`, clears the
  reference and unregisters while the old thread may still be running;
  it also clears the caller's interrupt flag.
* Effect: an application-wide interrupt silently stops JMX measurements,
  and asking to start again leaves them stopped. An interrupted stop
  returns before its worker ends and loses the application's interrupt.
* Evidence: [JmxInterruptProbe.java](r3/JmxInterruptProbe.java), commands
  and four output lines in [r3-f4.txt](r3/r3-f4.txt). The first part
  interrupts the worker in its sleep and joins it. The second uses a
  `Db.getTransactionCount` override to pause that worker, pre-interrupts
  the stop caller and observes `stop returned with monitor alive: true`
  and `interrupted stop lost caller flag: true`. Every monitor is
  unregistered and its worker joined; both databases are closed.
* In 2026.1: yes; these interrupt paths are unchanged. 005-46 established
  the stronger contract after that release, without updating JMX.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: let an interrupted monitor continue, retaining
  the information until its exit; make `stop` join through interruptions
  and restore the caller's flag. Clear the worker reference only after
  termination, under the lifecycle monitor.

### R3-F5. An interrupted STM retry kills an index build permanently for this run

* Where: `pubimp/IndexBuilderImp.java`, `createInThread`, lines 311-325,
  and `createStep`, line 438; `pubimp/RwTransaction.java`,
  `executeRw`, its conflict retry and interrupted sleep, lines 118-140.
* Intended: 005-46, "Interrupts", change (g): index jobs' own threads
  go on when interrupted. The interruptible transaction retry is for
  application callers, not permission to abandon internal maintenance.
  `IndexBuilder.start` completes the build and makes it active, unless

* Actual: a build uses `connection.rw`, whose conflict wait throws a
  `DbException` on interruption. Its worker catches stopping, failed
  database and stream exceptions, but not that refusal. It terminates,

* Effect: a normal conflict combined with an application-wide interrupt
  prevents this index becoming usable until the database is restarted.
  `join()` returns, but `progress()` remains -1, with no exposed error.
* Evidence: [BuildInterruptProbe.java](r3/BuildInterruptProbe.java),
  commands/output in [r3-f5.txt](r3/r3-f5.txt). A real scan completes,
  then a latch allows an application writer to update a scanned object.
  The build resumes with its interrupt flag set, as an external interrupt
  could leave it. STM correctly refuses that stale attempt; the worker
  dies with `The transaction was not run: the thread was interrupted ...
  after a conflict`, progress -1 and database active. The latches and
  worker join establish the order. The worker ends and the database
  closes in `finally`.
* In 2026.1: yes, the same interaction terminated the worker with a
  `RuntimeException`; 005-46 changed that to `DbException` while promising
  the worker would continue.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: give internal build steps an uninterruptible
  retry loop that clears/notices interruption while making progress,
  then restores the worker's flag when it ends. Keep the public caller's
  interruptible retry semantics. Cover both interruption in a retry and
  the pause between successful steps.

### R3-F6. A consumer interrupted at stop skips closing its underlying stream

* Where: `storage/BufferedStream.java`, `runConsumer`, lines 168-170 and
  205-209; `stop`, lines 687-694.
* Intended: `BufferedStream.stop` eventually ends its worker and closes
  its stream; 005-46 says interruption must not cut short cleanup.
* Actual: when `wait` throws and `stop` is set, the catch returns from
  the method, bypassing the underlying `stream.close` below the loop.
* Effect: a stopped consumer can terminate while its files and directory
  lock remain open. This is the lower stream's `stop`/`StorageManager.stop`
  path; ordinary `Db.stop` uses the draining `close` path and its extra
  close repairs this omission. It is not a claim that every Db stop leaks.
* Evidence: [ConsumerStopInterruptProbe.java](r3/ConsumerStopInterruptProbe.java),
  commands/output in [r3-f6.txt](r3/r3-f6.txt), plus the failing Nano test
  [r3-f6.patch](r3/r3-f6.patch). With the consumer waiting,
  the probe takes the buffer monitor, interrupts it, waits until it is
  blocked reacquiring that monitor, then calls `stop` before releasing it.
  The consumer must reacquire it before
  catching the interrupt, so it observes `stop=true` and takes the return.
  A join confirms termination; opening the same directory is refused:
  `FAULT: terminated consumer left directory locked`. The probe's
  `finally` calls `close` to release the original stream, then removes
  its temporary directory. No database is left running.
* In 2026.1: yes; the stopped-interrupt catch also returned before the
  trailing stream close in that tag.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: no.
* Proposed fix, not made: break the outer loop instead of returning, and
  put the consumer's stream cleanup in an outer `finally` so every exit

### R3-F8. A failed append's transaction was already visible, contrary to section 3

* Where: `core/Db.java`, executeInner, lines 2016-2026;
  `docs/levels.md`, section 3, second bullet.
* Intended: section 3 says that a failure anywhere after the go point
  fails the database and "the transaction's time never becomes a lookup
  time". The code comment at lines 2018-2021 makes that narrower promise
  only for a putKvs failure.
* Actual: transactionEnd publishes the transaction's time before store.
  A concurrent reader can read its new value while its record append
  waits for room. The append can then fail before writing any of the
  record's bytes, and restart removes that observed value.
* Effect: the documented visibility guarantee is false. This is a
  contract mismatch, not a claim that a transaction acknowledged as
  durable is lost: the writer here has not returned or synced. The
  database correctly fails once the append throws.
* Evidence: [PublishedFailedTransactionProbe.java](r3/PublishedFailedTransactionProbe.java),
  command/output in [r3-f8.txt](r3/r3-f8.txt). A 1 kB buffer and 8 kB
  value force a real room wait. The consumer's first new flush waits on
  a latch, then throws IOException without appending bytes. A normal
  cached get returns the 8 kB value while the writer is still executing;
  its transaction time is already the lookup time, with 0 new bytes in
  the underlying stream. The writer then throws DbFailedException;
  reopening finds the previous 1-byte value. Start/join and the latches
  order the observations. Both databases close; the writer is joined.
* In 2026.1: yes; transactionEnd precedes store in that tag too.
* A fix touches the stream format, a Pub API signature, or needs a design
  choice: a visibility-contract choice. No format or signature change is
  needed to correct the document.
* Proposed fix, not made: state the implemented boundary precisely in
  docs/levels.md: a failure during putKvs never publishes its time; a
  later failure can follow publication and admitted readers may already
  have observed that state. If the stronger guarantee is wanted, defer
  visibility until all fallible commit work is complete, accounting for
  reclaim's nested transactions and callbacks.

## 3. Threads

* **Application readers.** The application starts these threads; BergDB
  starts none for a get or scan. Each owns its GetData/GetMany (the Pub
  Connection is single-threaded). getOne/getMany read volatile state,
  reclaim's first available time and the clock before traversing the Dag.
  They never take the write lock. A cold follow can wait on a node/handle
  loader and on storage; an after-load callback can wait for eviction.
  An overtaken snapshot can expire; a storage/corruption failure publishes
  FAILED. A stop can close files under an already admitted reader; close
  does not register or join readers. Interrupt behavior is checked below.
* **Application writers, including reclaim.** Callers run warm-up outside
  the write lock, using the transaction's own warmupGetData. The write
  lock serializes validation, mutation, append and reclaim's nested
  internal transactions. Writers waiting on that monitor ignore interrupts;
  buffer-room waits remember them and restore the flag. stop publishes
  STOPPING immediately; a transaction already under the lock completes,
  while waiters recheck state after acquiring it. The closer acquires and
  releases that lock before closing storage. A throwable after the go
  point fails the database; warm-up storage errors do too.
* **Db-close-N.** The first stop claims closeBegun under closeLock and
  starts this non-daemon thread. It drains a running writer, calls
  Eviction.endThread, closes storage, and publishes closeDone and notifies
  all under closeLock even if cleanup throws. Another close waits in a
  predicate loop, retaining interrupts. A first close does this work on
  its own caller, without starting the thread. closeFailure retains an
  IOException for subsequent closes. close inside the write lock avoids
  waiting for a closer that needs that lock; its special case needs no
  reader registration.

* **BufferedStream-consumer-N.** StorageManager constructs and starts one
  daemon per stream while Db is constructed, before Db.start. It reserves
  a prefix of the ring under the buffer monitor, appends it outside the
  monitor, applies a pending cut, advances cStart/streamLength and wakes
  producers/closers, then calls the durability listener outside the
  monitor. It reads the stop/close flags under that monitor, waits in
  quarter-buffer-time intervals while collecting a small batch, skips
  that wait for a sync or a quarter-full backlog, and becomes an untimed
  waiter when idle. append, flushSoon, stop and close notify it. An I/O
  error, RuntimeException or Error in a flush is retained as an
  IOException; stop and notify wake room/close waiters and the listener
  removes the failed storage. That failure reaches Db on a subsequent
  storage operation; there is no direct callback to Db.setFailed (R3-F10).
  Db's stop uses draining close, not BufferedStream.stop. close waits for
  the buffer and joins the consumer, unless called from that consumer's
  own failure listener; the trailing stream.close then reports cleanup
  failures. Ordinary interrupts continue the loop, but the stop/interrupt
  exit can bypass stream.close (R3-F6). The loop does not preserve the
  worker's interrupt flag while it continues.
* **FileStream-cut.** pretruncate, called by reclaim through storage,
  starts this daemon only when a nonempty removed-file queue has no
  worker. Under the stream monitor it reads the oldest queued DbFile;
  outside that monitor it closes/deletes that file and forces the
  directory, then removes the completed queue head under the monitor.
  It has no timer or idle wait: at an empty queue it clears cutThread,
  notifies and returns. Failed I/O, RuntimeException or Error publishes
  ioException; the next loop leaves the remaining queue for close and
  clears/notifies cutThread. Later stream operations and close report
  the failure; acknowledged earlier flushes stay acknowledged. Db.close
  reaches FileStream.close through the consumer, waits on the predicate
  cutThread != null, then closes remaining files and releases the
  directory lock. Directory/file force retries clear and later restore
  interrupts; the worker has no interruptible sleep. Its completion wait
  remembers interruptions and continues. The completion signal is a
  monitor publication, not Thread.join; after signalling the worker has
  no further stream work.
* **bergdb-evictor.** A load, a transaction end or a decreased budget
  calls wake and lazily starts this daemon. It reads resident bytes,
  watermarks, database state and writersWaiting; writes handles/slots and
  accounting in bounded batches under Db.writeLock. Request/lifecycle
  state is under evictorLock, with wanted volatile for the caller's fast
  return. It releases that lock before taking writeLock. With no request
  it waits without a timeout; wake and endThread notify. With writers
  waiting it parks briefly; afterLoad callers watch volatile batches for
  up to 2 ms. A stop/close ends work; normal close notifies and joins
  outside writeLock. A close within writeLock only notifies. An idle
  interrupt with no pending request ends it and clears the reference;
  later loads start another (005-65's explicit exception). An interrupt
  with a pending request lets the work proceed. A batch exception leaves
  a dead worker reference and no Db failure (R3-F3). A Db failure while
  the worker sleeps does not itself notify it; close does.
* **IndexBuilderImp-CreateIndex-NAME-N.** IndexBuilder.start creates
  metadata synchronously, then starts this low-priority daemon; startup's
  finishOngoingJobs starts the same kind of worker for creating indexes.
  It owns its Connection and scan position, reads primary data and index
  definition, and commits entry batches, updating IndexCreateState under
  that state's monitor. It sleeps for half a step's duration between
  batches; that sleep's intended one-second cap assigns the wrong local
  variables (section 7). A test-only EventToWaitFor can delay its start.
  There is no work-queue wait or wake. DbStopping/DbFailed/StreamIo ends
  its loop and startup later resumes from metadata. Other exceptions
  escape the worker; an interrupted STM retry does too (R3-F5), whereas
  an interrupted between-step sleep continues but loses the flag.
  Success is published before activation succeeds (R3-F2); snapshots
  read a live counter (R3-F7). Db.close does not join this worker: its
  next database access notices the state, or it can still be in its pause.
  Job.join joins it and preserves a caller's interrupt on an early return.
* **DatabaseImp-delete-NAME-N.** deleteIndexInternal commits deleting
  state and syncs on its caller, then starts this low-priority daemon;
  startup resumes deleting metadata through the same path. It owns the
  deletion Connection, scans the entry prefix and commits deletes in
  batches, then deletes metadata and syncs. It increments deletedCounter
  under the counter monitor. No timer, condition wait or cooperative
  cancellation flag is used. DbStopping/DbFailed/StreamIo end it; a
  restart resumes remaining metadata. The final sync is interruptible
  and its StreamIo catch silently ends the job. The caller's sync before
  Thread.start is interruptible too, and can leave deleting metadata
  with no worker (R3-F11). No job registry joins or cancels it during
  Db.close. Job.join joins it, preserving the caller's interrupted flag;
  getStatus uses isAlive and reports success whenever the worker ended,
  including an incomplete stop/failure. R3-F1 is the overlapping-worker
  fault. There is no finalizer to repair any of these job states.
* **DBMonitor.MThread.** Jmx.Speed.registerAndStart explicitly registers
  an MBean and starts this lower-priority daemon. It samples Db's stream,
  transaction, KV and get counters and publishes four volatile rates.
  It sleeps one second four times between samples, checking its own
  volatile stop flag. Speed.stop sets that flag and joins, holding the
  Speed monitor; it does not wake the sleep. Db failure/stop/close neither
  stops nor joins this separately owned monitor, whose statistics getters
  still work. An interrupt terminates it and leaves its reference set;
  an interrupted stop does not finish joining or retain the flag (R3-F4).
  The ordinary DbMonitor MBean has no thread; JMX invokes its getters and
  setters on JMX's own caller threads.

## 4. Locks and monitors

The orders below concern production paths followed in this review, not
arbitrary monitors an application takes in its own callbacks. Node/map
details are recorded only as needed to follow the R3 boundary.

* **Db.writeLock.** Serializes ExecuteData, Dag writers, TransSeq,
  KeyModSet, startup distance/meta changes, reclaim tables and eviction
  batches. start holds it across readSync; transactions take readSync,
  DbClock, nodes/handles, cache maps, storage/buffer monitors and eviction
  bookkeeping inside it. Getters for stream length/stats take it too.
  The evictor takes it only after releasing evictorLock. App readers do
  not take it. Reclaim's nested execute and setStartupDistance's execute
  are reentrant. Normal close takes/releases it before joining workers.
* **Db.readSync.** Serializes first-failure publication against stop/close,
  and reclaim's paired frontier writes; also supplies legacy empty
  publication blocks for writers and some getters. start and execute take
  writeLock -> readSync. stop/close release readSync before closeLock or
  writeLock; setFailed takes no writeLock inside it. No production
  readSync -> writeLock cycle was found, apart from start's reentrant
  calls while it already owns both.
* **Db.closeLock.** Protects closeBegun, closeDone and closeFailure. A
  competing close waits here with a while predicate; wait releases it.
  Neither writeLock acquisition, storage cleanup nor a worker join runs
  while this lock is held. A transaction's close/error path can take
  writeLock -> closeLock; no reverse blocking acquisition is present.
* **DbClock instance.** Serializes currentTime, transactionBegin/End and
  startup's clock seeding. Writer order is writeLock -> DbClock.
  currentTime holds it across the supplied Clock.getTime; the built-in
  clock takes no Db locks. lookupTime only reads the volatile completion
  time. No DbClock -> writeLock path is present in BergDB's clock code.
* **Reclaim.** No independent instance monitor protects its algorithm;
  its table, pendingCut and pendingCutDurableAt belong to writeLock.
  Retention, fraction and reserve setters write individual volatiles.
  Frontier writes use writeLock -> readSync, except startup already holds
  both. Readers read the individual frontier volatiles.
* **Eviction.evictorLock.** Protects worker identity, running and request
  transitions. wake starts a thread and notifies while holding it; the
  worker waits/tests wanted here. No writeLock, storage I/O or join is
  taken inside it. writeLock -> evictorLock occurs at transaction end;
  the reverse order is avoided by leaving it before a batch. endThread
  snapshots the worker under it and joins after releasing it.
* **Eviction instance monitor.** Protects statistics and the joint
  high/low/trigger setter/recomputation. A batch ends under writeLock ->
  Eviction; a setter releases Eviction before waking under evictorLock.
  It never acquires writeLock. The existing test hook runs under this
  monitor. 005-80's repaired trigger race follows this order.
* **Eviction.class.** Protects process-wide statistics only. Transactions
  take it after releasing the instance statistics monitor. totals takes
  only the class monitor; no inverse dependency was found.
* **Cache map monitors.** Serializes resolution, eviction and table
  entries. The writer/evictor take writeLock -> map. A loader resolves
  under a map, then releases it before taking a handle and doing I/O.
  The dead-handle retry can take handle -> map; there is no matching
  map -> handle acquisition: eviction uses a handle-state CAS rather
  than waiting for the loader's monitor. Registration/eviction can take
  map -> node through Residents.added/released.
* **Cache3.bigLock.** Protects the legacy size indicator and totalSize;
  getters/setters take it alone. Db.setCacheSizeIndicator releases it
  before calling Eviction.setBudget. It is not held while taking a map,
  handle, node or writeLock, and supplies no joint budget snapshot.
* **Handle monitors and node monitors.** A loader owns its handle while
  loading/installing, and can later take a parent node monitor to update
  its pointer. Values load outside the parent monitor and are installed
  under it. The writer's canonicalization uses handle synchronization;
  in-place pointer-pair changes use the node monitor. The load listener
  runs outside these monitors, so afterLoad cannot invert their order
  with evictorLock/writeLock. Installation/promotion takes handle -> node
  for Residents accounting. Ordinary pair reads release the node before
  resolving/loading a handle; no node -> handle wait was found. Residents
  adds no monitor of its own: object counts use the node monitor and
  totals use atomics. A complete internal R2 field audit is not claimed.
* **BufferedStream instance.** Protects ring contents/indices, reserved
  consumer span, lengths, pendingCut, flushTo, stop/close/failure and the
  idle predicate. Producer/consumer/reader/closer take it; consumers do
  lower-stream I/O and invoke listeners outside it. append's room wait
  and close's drain wait release it. A sync takes d1Lock/d2Lock -> buffer;
  the consumer releases buffer before its listener takes those locks,
  avoiding the apparent reverse-order cycle. Consumer.join is outside it.
* **BufferedStream.Waits.** Protects room-wait statistics. append can take
  buffer -> Waits; takeRoomWaits takes only Waits, with no reverse path.
* **StorageManager.d1Lock and d2Lock.** Each protects a durability length
  and wait/notify. computeRules acquires and releases d1, then d2; it does
  not hold both. sync waits in a predicate loop on its rule lock and can
  enter a buffer for flushSoon. Error/close uses atomic state rather than
  these locks; waiters discover it on their 500 ms polling wake.
* **FileStream instance.** Protects cut queue/worker, file-list replacement
  and directory-lock ownership. pretruncate queues work and starts the
  deleter; awaitCutThread waits here and releases it. close takes stream
  -> DbFile -> channelLock while closing remaining handles. A cut drops
  the stream monitor before DbFile.delete and reacquires it only after
  delete returns. newFile closes the old writer and forces the new file
  outside the stream monitor, then enters it for list replacement.
* **FileStream.DbFile and channelLock.** DbFile serializes append/force,
  writer-handle close and deletion; close then takes channelLock. Reads
  take neither on the fast path. Reopening a channel takes channelLock
  only; it never takes DbFile or FileStream, so no reverse order occurs.
  The operating-system FileChannel's own close/read coordination is also
  relevant to close's wait, beyond BergDB monitors.
* **FileStream.LOCKED_DIRS.** Its synchronized-set monitor protects the
  in-process directory claim. lockDir's add releases it before entering
  FileStream; unlockDir has FileStream -> set. No set -> FileStream held
  order exists. The OS byte-range lock is held for the entire stream life.
* **IndexManager.lock.** Protects nameToIndex, directory arrays and index
  state, and holds across metadata db.execute. Order: manager ->
  writeLock -> Core/storage locks. Application index selection takes and
  releases manager before execute; the Pub key transformations inspected
  do not reacquire it under writeLock. The maps replace arrays rather
  than mutate an array returned to an Action. R3-F1/F2/F9 are ownership
  and exception-safety faults despite the monitor itself being used.
* **IndexCreateState and deletion-counter monitors.** The build state
  protects progress/counter updates and status construction. A status's
  note escapes that protection (R3-F7). The deletion worker increments
  under the counter monitor but getStatus reads outside it (section 7).
  Neither monitor is held across Db calls or a job join.
* **DatabaseImp.threadLocalConnections, instance and class.** Connection
  cache accesses/clear use its map monitor; connection initialization
  happens after releasing it. stop has DatabaseImp -> map, then releases
  map before Db.stop. close clears map before Db.close. createAndStart is
  static synchronized, serializing starts of independent public databases;
  startup index jobs do not acquire that class monitor to finish.
* **Jmx.Speed and EventToWaitFor.** Speed's lifecycle methods hold its
  instance across registration or join; the worker does not acquire it,
  so ordinary stop has no self-cycle. EventToWaitFor protects its boolean
  with its own monitor and notifies all; wait releases it. Its single
  wait is not a predicate loop (section 7). Db.close does not call Speed.stop.

No unavoidable lock-order cycle was found in the above ordinary paths.
This does not certify application callbacks that themselves take external
locks, call close under a Core listener, or reenter execute during putKvs.

## 5. Publication points

* **Construction and start.** Db's final references fix lock, clock,
  cache, reclaim and storage identities. Its constructor releases
  readSync/writeLock, and start rebuilds Dag/TransSeq under those locks.
  The volatile ACTIVE write publishes startup's earlier Dag and follower
  writes to a get's state read. reclaim.initFromDb runs after ACTIVE while
  start still holds the locks; its own frontier volatiles publish that
  final part. The caller must finish start before using the Db, as its
  Javadoc requires. Pub createAndStart initializes its index manager
  before returning the Database, and Thread.start publishes definitions
  to maintenance jobs it resumes. Final-field semantics alone do not
  publish mutations made after a constructor or make a Connection shared.
* **Writer -> writer.** A transaction releases writeLock after append,
  callbacks, eviction and reclaim. The next writer/evictor's acquire
  sees ExecuteData, TransSeq, dirty/canonical bookkeeping and KeyModSet.
  KeyModSet is deliberately plain and used only under that lock, including
  its startup coverage seed. An STM check cannot run alongside add/rotate.
* **Writer -> reader clock.** All logical Dag changes in putKvs precede
  transactionEnd's volatile lastTransactionTime write. getOne/getMany
  acquire that volatile through lookupTime before traversal, even for a
  requested historical time. A reader using an earlier time traverses a
  structure whose later mutations preserve that earlier state. Node
  size/pointer publication also matters for concurrent mutations after
  that clock read; the clock is not a substitute for those per-node
  edges. Post-clock failures are R3-F8.
* **readSync releases.** The empty writer releases at Db.java 2016/2045
  still order subsequent execute warm-up and legacy synchronized getters.
  They are not an edge to ordinary gets, which no longer acquire it.
  Startup's state and clock/frontier edges replace the old reader
  acquire, as 009-02 3.2/3.3 describe.
* **Failure and stop publication.** Under readSync, setFailed first
  writes failure, then volatile FAILED. A subsequent state acquire that
  observes FAILED sees its cause. Only the first active-to-failed change
  stores a cause. stop/close publish volatile STOPPING using that same
  monitor; later admissions and a writer's recheck refuse the operation.
  They do not revoke a snapshot already admitted. There is no corresponding
  Db failure publication from the evictor's uncaught exception (R3-F3),
  or the main buffer's known asynchronous failure (R3-F10).
* **Reclaim admission and cut.** Under writeLock, the cut table's internal
  transaction is appended before firstAvailableLookupTime/Pos are written
  as volatiles under readSync. New gets read the time frontier before
  choosing their actual time. A later physical cut is admitted only when
  getDurableLength, under d1Lock, reaches pendingCutDurableAt. Thus bytes
  before the cut go only after the table/meta decision is durable.
  An overtaken reader's lower-stream exception is checked against the
  now-published time, using its **actual** snapshot time, not MAX_VALUE.
  No reader epoch/registration or promise to keep a long read alive is
  present. The two frontier volatiles are individual publications; code
  needing the algorithm's coherent table holds writeLock.
* **StartupPos.** store assigns all earlier record/bookkeeping state then
  AtomicLong.set(newSp); readers of get acquire that value. Both the writer
  and eviction's decision paths are additionally under writeLock. The
  separate evictPos volatile is assigned by releaseForEvict but has no
  read anywhere in today's source. It is not an effective delayed-release
  gate; correctness must use writeLock, trans-node pins and recorded
  positions, as today's eviction does. No test of that unused field is
  needed.
* **Live settings.** Startup distance and MetaBlock state are changed and
  read under writeLock; setStartupDistance's failed/refused attempt restores
  both under it. Reclaim retention, fraction and step reserve are individual
  volatile writes/read snapshots. Cache3's indicator uses bigLock; the
  effective eviction budget is volatile high, with high/low/trigger jointly
  written under the Eviction monitor. A batch computes its trigger under
  the same monitor, ordering it against setBudget (005-80). The Db setter
  updates Cache3 then Eviction in two separately protected calls; no atomic
  joint snapshot across those subsystems is claimed here. Cache3's old
  indicator has no production read; the effective budget is Eviction's.
* **Eviction requests.** A request's wanted=true is a volatile write under
  evictorLock. The worker acquires that lock before testing/clearing it;
  wait atomically releases the lock so a later notify cannot be missed.
  A fast-returning caller's resident/budget volatile writes precede its
  read of wanted; the worker's subsequent volatile clear and its reads of
  those quantities are ordered in synchronization order. This is the
  additional argument needed for a caller that never releases that monitor
  itself (005-65). The end of a batch writes volatile batches; afterLoad
  callers poll it. A park is not the publication edge.
* **Worker life.** Writes made before each Thread.start happen-before
  that worker's execution. A successful join, and a test's detection of
  thread termination, publish its completed writes. Db's close claims and
  results instead use closeLock release/acquire plus its predicate wait.
  FileStream's cut completion uses the stream monitor and cutThread=null
  with notifyAll; no work follows that signal. Eviction clears its worker
  reference under evictorLock and normal close joins the captured thread.
  Neither notification on its own nor an elapsed sleep publishes data.
* **Ring -> consumer and reader.** A producer copies bytes and advances
  pStart/totalLength under BufferedStream's monitor, then releases it.
  Consumer reservation and buffered reads acquire it before using those
  bytes. cSize reserves bytes while I/O runs outside the monitor; the
  producer never reuses them until the consumer advances cStart under
  that monitor. The release/next acquire, not notify alone, publishes
  room and drained state. stop/failure and their notify use that same
  predicate monitor.
  StorageManager starts the consumer before installing its plain
  appendListener and finishing Internal. No flush can occur with an
  empty new buffer. The first append's buffer-monitor release publishes
  those intervening initialization writes to the consumer's reservation
  acquire; Thread.start alone would not publish them. This argument
  depends on completing construction before any producer uses the stream.
* **Durability -> sync.** A completed lower append/force precedes
  confirmedLength.set in the listener. Atomic get in computeRules sees
  it; d1Size/d2Size increase under their own monitors and notify waiting
  syncs. A sync's acquire and while predicate are the final edge. flushSoon
  raises flushTo under the buffer monitor; the consumer checks the same
  monitor before waiting, including after a flush. The listener is outside
  that monitor. Error-state publication uses Internal's AtomicReference
  set/CAS; sync polls it in its wait loop as well as receiving normal
  durability notifications.
* **Storage list/error snapshots.** Internal.copy fills new arrays and
  state before AtomicReference.set/CAS; operations get the snapshot before
  using its arrays. A failed main stream is removed and replaced with
  ErrorStorage; later storage operations observe that failure. Ordinary
  cached Db reads do not read this AtomicReference (R3-F10).
* **Files -> reads and deleter.** FileStream builds a new DbFile array
  before volatile dbFiles assignment; readers acquire it. DbFile's final
  file/spos and volatile channel/fileLength publish its initialization and
  forced bytes. A cut sets removed files' volatile isDeleted, queues them,
  and writes firstPos and dbFiles before releasing the stream monitor or
  starting its worker. A reader with the old array still sees isDeleted;
  a reader with the new array can report below-first without finding a
  file. close publishes isClosed under channelLock before closing the
  read channel. Reopen takes channelLock and rechecks both flags, then
  publishes a replacement volatile channel.
* **Loaded objects -> other readers.** A loader fills an object, then
  publishes it with Handle.obj's volatile write. A fast follow reads that
  volatile after a plain handle pointer; final Handle.id and the default
  LIVE state make that plain reference usable (009-02 3.4). A value
  pointer uses array-element acquire/release/CAS, and its value bytes are
  final. In-place position/pointer changes use the node monitor; position
  elements are opaque, preventing a torn long. Eviction's state CAS
  arbitrates with a loader; writtenPos precedes the volatile obj=null
  publication. A stale CLOCK hint affects replacement choice only. Full
  Dag slot/array proofs and field accounting belong to R2, not this list.
* **Index metadata/maps -> callers.** The manager releases its lock after
  updating state/maps and committing metadata; directory selection and
  cached index lookup acquire it. Definition fields/IndexForDir identity
  are final and the returned arrays are replaced, not changed. Virtual
  directory hashes and index metadata hashes enter Core's write history
  under writeLock; an Action that chose mappings earlier validates those
  hashes when committing. R3-F2 lacks that generation/state dependency
  for its builder's own entry writes. R3-F9 demonstrates that monitor
  publication cannot repair a cached update whose metadata commit refused.
* **Jobs/status.** Thread.start publishes the worker's Connection,
  definition and initial scan state. IndexCreateState.update unlock ->
  getJobStatus lock publishes captured progress, but note reads outside
  that snapshot (R3-F7). The delete counter's write monitor has no matching
  acquire in a running getStatus (section 7); termination/join supplies an
  edge only once the worker has ended. Join's interrupted return preserves
  the caller's flag but supplies no termination edge for a still-live job.
* **JMX and event.** Speed's Thread.start publishes its Db reference;
  volatile stop and rates publish independent values to its worker/JMX
  clients. Speed.stop's successful join publishes termination; its
  interrupted path lacks that completion (R3-F4). EventToWaitFor.happened
  writes hasHappened before monitor release; a waiter or didItHappen
  acquires that monitor. An interrupt/spurious return from its single
  wait establishes no assertion that hasHappened became true.

## 6. The go point

The go point is `Db.executeInner`, lines 2006-2008, immediately after
`t.tt = dbClock.transactionBegin()`, inside writeLock. Everything inside
the following try, including reclaim's transactionCompleted, is under a
catch(Throwable) that calls fail. An Error is rethrown after publishing
FAILED; other failures become DbFailedException, except while stopping.

Before it: public Action execution and object conversion; execute's state
check; value/key byte-size check; warm-up reads; the second state check
under writeLock; top ordinal headroom and dirty-node byte bounds;
ExecuteData.begin; STM's read hash validation including startup's coverage
boundary; clock range, monotonic transaction time and read-time bounds.
Warm-up and the dirty-node estimate can load nodes: a storage error there
fails the database even though it is before the go point. A refused STM,
size, ordinal or clock check leaves the Dag and stream unchanged; the
temporary ExecuteData fields are replaced by the next attempt.

Publication has a verified contract mismatch: transactionEnd publishes the time
after putKvs, **before** stmRecordKeys, store, callbacks, eviction and
reclaim. Thus the comment about a putKvs failure is narrower than the
wording of docs/levels.md section 3 about every post-go failure. This
contract mismatch is R3-F8. A refused metadata transaction can also leave
the Pub layer's cached index state changed before Core's go point (R3-F9).

## 7. Doubts

* **R3-D1. A running delete status races its counter.** DatabaseImp.java
  340-343 reads deletedCounter[0] plainly; IndexManager.java 445-447
  writes it under the counter monitor. thread.isAlive returning true
  supplies no edge from those increments. A stale or, under the JMM, torn
  long can give a misleading note. A completed worker's termination/join
  does supply an edge, so this is specifically a running-status issue.
  No stale/torn result was forced on this VM. Verify with a publication
  test or a separately checked JMM interleaving; proposed repair is to
  capture the counter under the same monitor.
* **R3-D2. close does not finish index jobs.** The absence of job tracking
  and joining is established by reading, but the public close promise
  specifically says storage threads have ended. An index worker may
  still sleep or finish processing a scan after close returns. It then
  notices stopping on a Db call. Whether the intended lifecycle also
  requires those jobs joined is not settled by that public wording.
  Verify/decide the intended boundary, then hold a worker between scan
  and commit and check close/Job.join and restart together. A worker's
  abandoned result also must not say successful deletion/activation.
* **R3-D3. The index pause's cap assigns the wrong locals.** In
  IndexBuilderImp.java 350-365, msToSleep/nanosToSleep are computed, but
  the cap changes ms/nanos instead; sleep still uses the uncapped pair.
  A very slow step appears to pause for over the documented one second,
  delaying its observation of stop/close. No long step/pause probe was
  run, so this is not registered as a fault. Verify by substituting a
  test sleeper and checking the requested duration, without a timed run.
* **R3-D4. EventToWaitFor has one wait and swallows interrupts.** Lines
  41-53 use if/wait rather than a predicate/deadline loop and do not restore
  the interrupted flag. An unrelated/spurious wake can release a test
  before happened, and an interrupt clears the flag. The helper expressly
  documents immediate return on interruption; the concern is the
  unrelated wake and using its flag behavior inside an own-thread hook.
  In the non-tester
  source its only caller is IndexBuilderImp's explicitly test-only start
  hook; no ordinary database path was found to depend on it. No spurious
  wake was observed. A helper-level test should force an unrelated notify,
  then the real event, and separately check interruption/timeout behavior.

## 8. Checked and right

* The clock's latest-time acquire publishes putKvs before ordinary
  traversal; the write lock serializes STM record/check even though the
  time is published before stmRecordKeys. The following writer cannot
  validate until it acquires that lock. DbClock.testLookupTime and
  KeyModSet.testStartupBoundary pass in this review.
* A reader's failure is published without taking writeLock. A writer
  already past its go point can finish or fail as it otherwise would;
  Db.failOnStorage explicitly documents that exception to later admission
  refusal. A waiting writer rechecks state after acquiring writeLock.
* The startup-distance setter holds writeLock across the meta value and
  its transaction, restores on refusal/failure and avoids a transaction
  for the value already in force. Its state/no-op regression passes.
* A batch's final trigger calculation shares the monitor with setBudget,
  and no setter holds that monitor while waiting for writeLock. The
  deterministic 005-80 regression test passes.
* Buffer room and close waits are predicate loops and continue through
  interrupts, restoring the caller's flag. Success and failure notify
  those waiters. Consumer callbacks occur outside the buffer monitor,
  which avoids the sync rule-lock/buffer cycle. The quarter backlog
  regression passes; the stop/interrupt exception is R3-F6.
* A normal close drains the active writer before closing storage. A
  failed final flush is retained under closeLock and reported by repeated
  close, also after stop. testCloseReportsFinalFlushFailure passes.
* A physical cut queues oldest files and forces each prefix removal in
  order; close waits for the queue worker before releasing the directory.
  testCutOnItsOwnThread passes. A read that meets a closed file fails
  alone without poisoning the later cleanup; its regression passes.
* Reclaim publishes the logical frontier before the physical cut and
  waits for durable cut metadata. It registers no readers; an overtaken
  read uses its actual snapshot for expiry classification. getTrans
  treats an explicitly below-cut transaction as expiry and wraps parse
  corruption within its failure catch. These paths were read, not run as
  a reclaim stress or gate here.
* Primary/secondary Pub iterators freeze an actual lookup time for their
  batches; secondary object loads use that same time. The one-Connection-
  per-thread rule is explicit in Connection's class Javadoc. Database's
  thread-local connection map is synchronized and each index worker owns
  its own Connection.
