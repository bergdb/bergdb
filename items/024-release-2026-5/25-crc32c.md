# 024-25. The node checksum: CRC32C

Created 2026-11-11 by Frans Lundberg. Status: open.

CRC32C (`java.util.zip.CRC32C`, 32 bits) in place of Fletcher-16 as the
node checksum, part of record format 7 (release 2026.5's format change;
024-21). No release has written format 7, so its meaning may still
change; this subitem changes it.

Frans's decision (024-17, section 8, "Decided, the limits"), 2026-11-11,
17:41: "I want be a bit more conservative, possibly increasing in a
future version. So, use: L1 = 500, L2 = 111, L4 = 8 MiB, L5 = 32 MiB.
The rest as recommended." The recommendation it takes (024-17, QL9): "The
node checksum CRC32C in place of Fletcher-16 with 2026.5's format change
(F6: 45 times faster, 32 bits)? Recommended: yes; it decides whether a
16 MiB commit is 135 to 250 ms or about 50. Decided: yes."

Decisions taken here are cited as "024-25, CD1", questions as "024-25,
QC1".


## 1. In short

Written 18:31, updated 19:22; section 10 has the exact state.

* **The change.** Every node's checksum is CRC-32C of its bytes but the
  checksum's own 4, stored in bytes 8 to 11 of a node header that grows
  from 8 to 12 bytes. Key nodes keep their size (the 4 bytes come from
  their 5 reserved ones; the fields move), a top node is 8 bytes longer
  (it is made of longs), a value or delete node 4. The node formats go
  from 2, 2, 4 to 3, 3, 5; the record format stays 7, and a start still
  refuses format 6 (2026.4) and earlier.
* **Rough numbers** (section 6): the checksum 5.6 ms a MB before, 0.12
  after (46 times); a key node of 544 bytes 3.0 us before, 0.05 after.
  A commit of an 8 MiB value (L4) 49 to 56 ms before, 2 to 10 after; a
  get of it 53 ms, 4 after; a restart over six of them 0.52 to 0.55 s,
  0.16 to 0.22 after.
* **Tests** (section 5): six commits of changed tests and limits, each
  kind its own: field offsets, format bytes, CorruptStreamTester's pinned
  copies, 019-33 out of CST's known blind spots, CST's node field range,
  level1's SS limits (a value node 4 bytes longer: SS 1.51 to 1.53).
* **Gates** (section 7): all pass on the head `e1a87bec`: before-commit,
  level1 to level4 full, unlinkfuzz, conformance small, medium, reclaim,
  evict, drain, CST's full set; StreamDigest: all 12 configurations
  change (48 of 48 digests). level1 needed its SS limits raised (QC2).
* **Review** (rev25, section 9): land with fixes; R1, R2, R4, R7 fixed.

## 3. The layout, before and after

**CD1. A 12-byte node header, the checksum in bytes 8 to 11, the same
place in every node type.** The header was size (4), type (1), format
(1), checksum (2). A 32-bit sum needs 2 more bytes; nodes are aligned (a
top or key node is a run of longs, its size a multiple of 8; a value
node's size a multiple of 4, `StoredValueNode`'s alignment of 2015), so
a node grows by 4 or 8, not 2. Options:

* (a) **chosen**: bytes 6 and 7 become zero (unused, covered by the sum)
  and the sum is bytes 8 to 11 in every node. Key nodes put their fields
  in the 5 reserved bytes they had (19 to 23): no growth; top nodes, all
  longs, grow by one long; value and delete nodes by 4.
* (b) the sum at the node's end: no field moves, but every key node
  grows by 8 (alignment), the bulk of the index's bytes; rejected.
* (c) a 3-byte size field or type and format in one byte, to keep 8
  bytes: limits a node to 16 MiB (L4 = 8 MiB now, "possibly increasing
  in a future version") or changes how every reader finds the type;
  rejected.
* (d) the high 16 bits in each type's own reserved bytes: the sum in two
  places, by type; rejected.

**The sum**: CRC-32C (Castagnoli; RFC 3720) of bytes 0 to 7, then 12 to
the node's end; little-endian in bytes 8 to 11. Written by the writer
when the node's other bytes are (a value node in `toBytes`; top and key
nodes by `StoredTrans.Serializer` after their longs are copied to the
record's bytes: `toLongs` leaves the field zero and does not sum, so
there is no copy of the longs to bytes for the sum alone). Checked on
every read before the parse (`NodeStream.checkChecksum`), as before; a
node size below 12 is refused before it (`checkChecksum`,
`StoredTrans.Parser.next`).

| Bytes   | Top node before / after    | Key node before / after   | Value node before / after |
|---------|----------------------------|---------------------------|---------------------------|
| 0 to 5  | size, type, format         | the same                  | the same                  |
| 6, 7    | checksum / zero            | checksum / zero           | checksum / zero           |
| 8 to 11 | h, 0, ordinal / checksum   | prevPos / checksum        | id / checksum             |
| 12...   | ... / zero 12-15, h 16,    | ... / leaf 12, n 13-14,   | ... / id 12, offset 20,   |
|         | 0, ordinal 18-23, id 24    | 0, prevPos 16, id 24      | L 24, value 28            |
| size    | 40 + 16h / 48 + 16h        | 32 + 16n / the same       | 28 + L + 8k / 32 + L + 8k |

Delete nodes: 24 + 8k / 28 + 8k. The creation record (`Db.CREATION_LENGTH`
less the meta block) 136 / 144 bytes.

**CD2. Node formats 3, 3, 5** (were 2, 2, 4). `StoredTrans.RECORD_FORMAT`'s
Javadoc: "A node's own format byte changes with its layout too." The
record format stays 7: no release wrote 7, and 024-21 and 024-23 changed
its meaning without a new number in the same way. A database written by
`main` with format 7 before this change is refused at its start with a
`StreamChecksumException` (checked 18:29 with a database made by
`08659847`), not with the format's message: the sum is checked before
the format byte. Acceptable for a format no release wrote (QC1).

**Cost in bytes**: 4 a KV put or deleted (L5's "28 bytes for a put" of
024-17, 5.3, becomes 32: at L1 = 500, 2,000 bytes a transaction at
most), 8 a top node version; key nodes as before, so 024-17's and
024-24's bounds on dirty index nodes do not change.
