# 022-04 Report: the C clone at release 2026.4

Created 2026-11-09 by Frans Lundberg. Status: open (the candidate, the
long runs and the tag to be added).

The report of 022-02's port of the C clone (`c/`) from Java release
2026.3 to release 2026.4: what changed in C, what shows that C matches
2026.4's Java, the faults that the port found in C and in Java, C's
departures, the size and the time. 2026.4 has no tag yet: C was ported to
`main` as the session pinned it, five times, the last at `e875a34`
(2026-11-09 17:18, section 8.1). The release candidate is cut from
`main` at about 20:00, and the tag comes at Frans's word after the
night's checks (006-17, section 3c). 022-02's steps 0 to 3 and its
decisions D6 and D7 landed between 12:36 and 13:49, three re-pins
between 13:58 and 15:49, on `int.git`'s branch `2026.4` (`8e088a7` to
`ddd75cc`), and a fourth with 021-18 after step 5; this report and
`c/readme.md`'s "Which Java" are step 5. Section 8 is left for the
candidate, section 9 for the long runs (022-02's step 4), and 022-02 stays
open until the tag (its step T). The details are in 022-02's log and in
each landing's commit message.


# 1. In short

* **C matches the pinned Java in all that the port compared**: at every
  landing the gate against the pin passed, with `cross.sh quick` and
  `writecheck` at 0 differences; the corrupt-stream set, 6,253 damaged
  copies of the pinned Java's own streams, gave the same status, text and

  Java's vectors written again from each pin, all thirteen files equal;
  Java's new tests of the Core ported: 27 more unit tests (383 to 410) and
  4 more functional tests (27 to 31).
* **No byte changed**, as 022-02 expected: C at the end of the 2026.3 port
  against the candidate (step 0's negative control) showed no difference
  in any harness. What the port changed shows in the tests it ported, each
  failing with its fix taken out, in two new kinds of Java's vectors and
  in the corrupt set's new bases.
* **What changed** (section 2): the four needed changes of 022-02's study
  (the keys by 021-04's rule, 021-05 and 021-06, with D3; 019-47's
  admission at a start; 021-11's links by node id), D4's optional parts,
  D7's forces of a new file and D6's messages, and with the re-pins the
  Core's later fixes: 021-12, 021-14, 021-15, 020-27's C1 to C3, 020-24's
  U1-12, 020-23's Z1 and 021-16's Q2.
* **Found in Java by the port** (section 5): 021-14, a read near
  `Long.MAX_VALUE` that passed `BufferedStream`'s check, and 021-15, a
  start's refusal texts that named a node by its identity hash, each

* **Departures** (section 6): one new, C's API cannot say Java's `GetN(0)`
  (a count of 0 is none); NOMEM a refusal and two others stand from 2026.3;
  D7 and D6 closed two.
* **Size and time** (section 7): 7,164 lines added and 504 deleted in 70
  files of `c/`, 3,285 of them Java's vectors; steps 0 to 3 were 1,482
  lines without the vectors, where 022-02 estimated 650 to 1,100, and

* **Left**: the candidate (section 8), the long runs (section 9), the tag

# 4. Faults of C

## 4.1 Those that 2026.4 fixed in Java

C's port of 2026.3 followed 2026.3's Java line for line, so it had the
Core's faults that 2026.4 fixes, where its code is like Java's. Each is
now fixed in C with Java's test ported, each failing before its fix:

* **021-06**: `bergdb_bkey_to_ikey` gave an ikey for any bkey: 0x31 gave

  with the byte 0 gave bytes that no UTF-8 has.
* **021-05**: `bergdb_ikey_to_bkey` took any bytes but 0xFE and 0xFF, a

* **019-47**: a value over 1 MiB of the startup section's first

* **021-11**: a pointer that names a node of another type was linked by

* **021-12**: a damaged key node version from before the startup section

* **020-27's C1 to C3**: `GetN` of 0 gave every pair inside C (not through

* **020-23's Z1**: with a clock that goes back, a time below the last one

* **021-14**: C refused a read near `Long.MAX_VALUE` already (D6's check

## 4.2 C's own

* **A new file's forces** (D7): one write of C's 10 MB buffer could make
  several files with no force of the directory between them; a file system
  that made a later name durable before an earlier one would then leave a
  gap after a power loss, which both opens refuse. Shown by the power
  model's new mode; theoretical on APFS, which keeps namespace operations
  in order.
* **`StreamIoException`'s text** (D6): C's own words where Java's is the
  inner exception's message, and a database's stream read with
  `FileStream`'s texts where Java's `Db` reads through `BufferedStream`.
* **A directory in place of `bergdb.lock` or of the last file** (D6's
  `corrupt.sh`): C refused with `IOException` and texts of its own, where
  Java's `RandomAccessFile` throws `FileNotFoundException`, "PATH (Is a
  directory)"; now Java's (`plat.c`), test `t_append.c`'s
  `append_dir_open_is_a_directory`.

No fault in C's bytes was met: the cross runs showed no difference before
the port or after it.


# 5. What the port found in Java

The session gave each finding to coord-1109, which registered the faults
as entries of 021 and had them fixed in Java the same day; each fix is in
the pin of 15:22.

* **021-14** (low; found by reading, in D6's port of `BufferedStream`'s
  check; fixed in `78c6718`): `BufferedStream.read` computed its last byte
  as `position + length - 1`, which overflows for a position within
  `length` of `Long.MAX_VALUE`; the check against the stream's length then
  passed, and the read threw an `ArrayIndexOutOfBoundsException` or
  returned bytes of the ring buffer, where the stream's contract names
  `EOFException`. C's port of that check (`stream_as_storage`) refused
  such a read. Java's fix found the pattern in `MemoryStream`,
  `StrictStream`, `DummyStream` and `NodeStream.checkReadSize` too, and
  showed that a damaged stream whose checksums are right can carry such a
  pointer to a read.
* **021-15** (found while porting 021-12, in the pin of 13:04; fixed in
