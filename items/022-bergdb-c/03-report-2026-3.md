# 022-03 Report: the C clone at release 2026.3

Created 2026-11-09 by Frans Lundberg. Status: open (step 5's runs to be
added).

The report of 022-01's port of the C clone (`c/`) from Java release
2026.2 to release 2026.3 (the tag `release-2026.3`, `9a0bf5e`,
2026-11-06), by 012-18's study: what changed in C, what shows that C
matches 2026.3, the faults that the port found in C and in Java, the
known cases, the departures, the size and the time. Steps 0 to 4 landed
on 2026-11-09 between 10:21 and 12:15 (`d1c5bfe` to `3e3b704` on
`int.git`'s branch `022`); this report and `c/readme.md`'s "Which Java"
are step 6. Step 5, the long runs, runs in the night to 2026-11-10;
section 9 is left for its results, and 022-01 stays open until they pass.
The details are in 022-01's log and in each step's commit message.


# 1. In short

* **C matches 2026.3 in all that steps 0 to 4 compared**: at every
  landing from step 1 on, the gate against 2026.3 passed with `cross.sh
  quick` and `writecheck` at 0 differences; the corrupt-stream set, 6,247
  damaged copies of 2026.3's own streams, gave the same status, text and
  message in Java and C (two known classes counted); power loss: C's
  images and Java's started alike by both, no acknowledged byte lost;
  Java's vectors written again from 2026.3; Java's new tests of the Core
  ported: 30 more unit tests (353 to 383, step 6's among them) and 1 more
  functional test.
* **What changed** (section 2): all eleven of 012-18's needed changes
  (the format change 015-87, the byte changes 015-54, 015-50 and 015-55,
  the start's refusals of 015-72, 015-75, 019-01, 019-34 and 019-32, the
  file stream's 005-47 and 015-06) and D4's optional parts (015-31,
  015-68, 015-70's test, `bergdb.h`'s notes, the corrupt-stream set);
  the C API without `retain_duration` and `BERGDB_SYNC_STRONG` (D2).
* **Faults of C** (section 4): every fault that 2026.3 fixed in Java and
  that C's port of 2026.2 had, each fixed with Java's test ported; and
  C's own: no force at a file switch or at an open, aborts
  or unchecked casts on a damaged node, and two refusal texts.
* **One fault of Java** (section 5): 021-11, a pointer linked by node id
  not checked for its node's type, found by reading in step 2 and fixed
  in Java after 2026.3; C refuses such a pointer at the read, and at the
  start with 2026.4 (022-02).
* **Size and time** (section 8): 4,840 lines added and 558 deleted in 83
  files of `c/`, about half of them tests, where 012-18 estimated 1,500
  to 2,000; from the copy to step 4's last landing 1 hour 54 minutes,
  with up to three workers at once, where 012-18 estimated 4 to 6 hours
  of an agent's coding.
* **Left**: step 5's runs (section 9); the open points for Frans
  (section 10); then 2026.4 (022-02).

# 4. Faults of C

## 4.1 Those that 2026.3 fixed in Java

C's port of 2026.2 followed 2026.2's Java line for line, so it had the
faults that 2026.3 fixed in the Core, as 012-18 read them in its code.
Each is now fixed in C with Java's test ported; the new tests of steps 2
to 4 were each shown to fail before their fixes, and step 0's negative
control showed 015-87's and 015-54's differences (section 3.6):

* **015-87**: reclaim's settings were options of the open, not kept in
  the stream; a 2026.3 stream's settings were read and kept, but C ran
  with its own options' values.
* **015-54**: pSafe at the end of the user's record, before the call's
  own records.
* **015-50**: a reclaim step with no stop at the value limit, and
  `check_size` for internal transactions too: a step over the limit
  failed the database inside a user transaction's go point.
* **015-55**: no times kept for reclaim at the end of the clock.
* **015-72**: a record whose size field is larger than its content was
  read.
* **015-75**: three of the start's checks as an assert's
  `AssertionError`, three missing (the startup position's alignment, the
  first meta block, after the record).
* **019-01**: a meta block's version read as an unsigned short.
* **019-34**: a last-transaction position outside the stream refused
  with `IllegalArgumentException`, and not before recovery could write.
* **019-32**: a damaged node with its checksum right met an assert and
  aborted the process, on in both builds, or was cast unchecked to the
  type expected, a read of wrong memory in the release build.
* **015-06**: the first file made at the open, so a refused creation left
  an empty stream file.
* **015-31**: a cut at the stream's length failed the stream ("Bug");
  reclaim never cuts there.


## 4.2 C's own

* **No force at a file switch** (012-18, section 3.1, step 10): a power
  loss between syncs could leave a short file before a newer one, which
  both opens refuse (`BadDirStateException`). Java's `FileStream` forces
  every append (on by default), so the gap was C's alone; 2026.3's
  switch force (005-47) is for Java with per-append forcing off. Found by
  reading in 012-18, shown by the power model's new mode, fixed in step
  3.
* **No force at an open for writing**: the port of 2026.2 lacked Java's
  OPEN force, so the durable length at an open was claimed unforced, and
  a start's cut (`rc_init_from_db`, `sdb.c`) could delete front files
  after a decision that a process that died had written and not forced.
  Fixed in step 3.
* **Casts of a followed node under an assert** (step 2): beyond Java's
  checks, where C cast a followed node to the type it expected, a check
  with the exception that Java gives at that place (a
  `ClassCastException` with the JVM's text in `dag.c` and `topds.c`; an
  `AssertionError`, as Java's under `-ea`, for `getmany.c`'s asserts,
  getOne's on a klong's node and `set_node`'s `assertOk`), so that C never
  reads a node as another type and never aborts where Java throws. The
  Dag's own errors go to `opdata`'s new `err`.
* **Two refusal texts** (step 4, found by the corrupt set's first full
  run, 129 of its 139 message differences): the start's refusals of the
  records' order and times now end with `StoredTrans.toString`, as
  Java's `DbStarter` (C named tpos and tt only), and a start's
  `validateStreamNode` gives `KeyNode.checkIncreasingTime`'s whole text.

No fault in C's bytes was met beyond 012-18's list: before the port,
every byte difference against 2026.3 was of 015-87 and 015-54 (section
3.6), and after it none.


# 5. What the port found in Java

**021-11** (registered by coord-1109; done): 019-32's check that a
pointer names a node of the type it expects is made where a pointer is
followed, but not where the Core gives a pointer the handle of the node
that its position names, by node id (`NodeCollection.linkToCanonical`,
the start's rule 4, and `resolvePointers`, the writer). A damaged pointer
whose node's checksum is right, naming another type's node, was linked,
and a later read threw a `ClassCastException` (an `AssertionError` under
`-ea`) instead of the start's `StreamFormatException`. Found by reading
in step 2, where C's port of `linkToCanonical` showed it (`t_ncoll.c`'s
`ncoll_link_to_canonical_another_type`); not reproduced in Java by the
port. Java's fix, after 2026.3, found it wider than reported (three
sites) and added `CorruptStreamTester.testFound021_11` and
`NodeCollection.testResolvePointersChecksTheType`; it is in 2026.4's
candidate (`36e003f`). C refuses such a pointer at its cast, at the read,
with Java's `ClassCastException` (`t_dag.c`'s `dag_wrong_pointee_type`);
the start's refusal comes with 2026.4 (022-02, section 3).

The corrupt set found no new fault of Java in its 6,247 copies.


# 6. Known cases

**014-01's zero fill.** A damaged record size makes recovery's walk from
the middle of the record zero-fill the stream to a garbage size
(megabytes, new files), and then the start refuses the record's last
byte ("Bad lastByte"). Java and C do the same, the two directories
alike; it breaks
`corrupt.sh`'s rule that C writes nothing into a database it refuses (2
of step 2's 200 header variants). The corrupt set counts it as known,
as harness 6.1's tester does (`KNOWN`, Frans's decision): 22 of its
6,247 copies, both directories alike. A copy whose fill would pass 1 MB
is left out, as the tester leaves it out (101 of the set's); a fill to 2
GB makes Java's start throw an `OutOfMemoryError` (a record of 2^31 - 1
bytes) where C starts. Whether to check the size before the fill is a
matter for both (section 10).


# 7. Departures from Java

`c/readme.md`, section 11, has them with C's design's older ones (one
caller and no thread, durability at a sync or a close, a cut made in the
call that decides it, and the rest). Those of the port to 2026.3:

1. **NOMEM is a refusal** (019-10): C's failed allocation before a go
   point or in a read gives `BERGDB_NOMEM` and leaves the database as it
   was, where 2026.3's Java fails the database at any `Error`. Java's
   reason (an `Error` may be the application's, and the JVM is then
   unsound) does not hold for one checked allocation of the library's own;
   012-14's decision, kept by D4; the allocation failures in turn show
   that each refusal leaves nothing behind.
2. **The settings' refusal text** (015-87): cut at C's limit of 240 bytes
   with the value's bytes as they are, where Java decodes them as UTF-8;
   C's errors are fixed byte buffers, and damage need not be UTF-8. The
   harness compares the exception's name.
3. **A new file and the directory forced at the next sync, close or
   cut**, where Java's `openForRw` forces both before the file takes
   appends: a file system that made a later name durable before an
   earlier one would leave a gap, which both opens refuse. APFS keeps
   namespace operations in order, so on F53 the case is theoretical; the
   fix, if wanted, is one force of the directory per new file (022-01,
   step 3).
4. **The unforced tail since the last force**, by C's design (no thread):
   Java's per-append forcing, on by default, forces each append within
   about 20 ms. A power loss can lose more in C, never an acknowledged
   byte; a hole within a file, outside 014-01's contract, has more room.
5. **`StreamIoException`'s text** names the inner exception and goes on
   in C's words, where Java's carries the inner exception's message
   (012-14, section 6.4, open); counted as known by `corruptset.sh` (10
   copies).
